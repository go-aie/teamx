# 朋友聚餐，一起点外卖

你负责拍板，三位 Agent 分别关注选菜搭配、预算份量和口味需求。给出固定的模拟菜单，让他们围绕同一份订单讨论、纠错和替换，再用人数或预算变化检查是否真正更新了方案。

这里的菜品、价格和费用都是练习数据，不代表真实商家的报价。成员只讨论订单，不联系商家、不购买或付款。配置没有预设最终订单、发言顺序或必须发生的争论。

## 三位成员

| 成员 ID | 名称与职责 | 应该带来的贡献 |
| --- | --- | --- |
| `xiaolin` | 小林 · 选菜搭配 | 提出一份具体组合；接到意见后删菜、换菜或调数量，保留大家愿意吃的搭配 |
| `laochen` | 老陈 · 预算份量 | 独立核算单价、数量、米饭和配送费；检查最新人数与份量规则，指出具体差额 |
| `xiaoman` | 小满 · 口味需求 | 检查不吃辣等明确要求，区分硬约束与偏好；用现有菜单给出替换，不凭空增加忌口或服务 |

三位成员是讨论分工，不决定用餐人数。没有额外主持人；任何成员都能纠正关键错误，也可以在没有新增贡献时沉默。

提示词沿用书店案例的经验：不为赞同或确认另发一条消息，不各交一份完整方案；优先替换和删减；不把多数赞同当成核实，不为展示角色价值不断制造新问题。用户要求最终清单且未指定成员时，小林可以整理，其他人仅纠正关键遗漏。

## 启动和新建房间

先按[主 README](../../../README.md#快速开始)准备 DSH、模型凭据，并配置`.teamx/config.toml` 中的默认 runtime。从 TeamX 根目录执行：

```sh
go build -o /tmp/teamx ./cmd/teamx
export OPENAI_API_KEY='替换为你的模型 API Key'
/tmp/teamx serve --config .teamx/config.toml \
  --listen 127.0.0.1:8090 --max-turns 24
```

1. 打开 **http://127.0.0.1:8090/**，点击左侧「＋」新建房间，选择「朋友聚餐 · 一起点外卖」。
2. 点击「创建并进入」，三位成员使用本团队的角色指令和公共 runtime，私有会话各自独立。
3. 新房间没有公共消息；开场消息和完整菜单仅填入草稿，检查后点击「发送」。

初始任务是四人、180 元含配送、全单不辣、至少一道荤菜和一道素菜，先按三道不同的菜及每人一份米饭讨论，汤可选。开场消息明确给出菜品分类与辣度、标价包含打包费、整单配送费 8 元，没有优惠或赠品，辣菜不能改成不辣；完整数据以 [team.json](team.json) 的 `opening_message` 为准。

工作区自动建在 `<data_dir>/rooms/<房间ID>/workspaces/<成员内部ID>/`。`prompts/` 提供角色指令，`.teamx/config.toml` 提供模型与 DSH 配置。

从书店案例开始另一项任务时，新建本案例的房间；书店房间完整保留，可从左侧列表切回。消息、成员、预算、会话与草稿分别隔离。项目配置从 `.teamx/teams/` 读取团队；从其他工作目录启动时可用 `--config /绝对路径/config.toml` 指定同一份配置。

## 怎么参与和判断

先观察是否出现一份具体订单，以及其他成员是否围绕它做有用的检查。首份订单已经满足要求时，其他成员可以沉默，不必为了产生互动故意挑错。

之后可选下面一条继续，不必全部发送。

**减少预算，观察做减法：**

> 预算改为 120 元，其他条件不变。请修改刚才那份订单，说明保留、取消或替换了什么，重新算上米饭和配送费。不要给我三份不同方案。

看成员是否真的修改菜品和合计，而非只说“控制预算”。本菜单下条件可以满足，不需要编优惠或省略费用。

**在 120 元预算下增加偏好，观察如何处理冲突：**

> 我更想吃清蒸鱼，但预算不增加，也还是想要三道不同的菜。看看能否做到；做不到就告诉我需要放宽什么，不要擅自放宽。

此时最低组合是鱼 58 元、番茄炒蛋 24 元、时蔬 20 元、四份米饭 12 元和配送 8 元，共 122 元。成员应指出至少差 2 元，并询问或建议取舍；不能把辣菜说成可改辣，也不能悄悄减少米饭或菜的道数。这个算式是操作者的检查依据，没有写进角色提示词，也不要求成员使用固定话术。

**也可以另试增加人数：**

> 现在总共 6 人，预算改为 200 元，按四道不同的菜和每人一份米饭讨论，其他要求不变。请在当前订单上调整，不要重新开始一轮点子接龙。

看菜的道数、米饭和总价是否一起更新。份量按本次练习的明确规则判断，不把模拟规则包装成对真实食量的保证。

**最后收尾：**

> 小林，请整理一份最终候选订单，列出品名、数量、小计和含配送费的总额；如果还有条件冲突请明确标出。其他人只纠正算错或漏掉的要求，没有就不用回复。本轮到这里，不实际下单。

| 观察项 | 可以直接检查的结果 |
| --- | --- |
| 是否接住同伴意见 | 修改发生在同一份订单上，能看出哪道被替换、为什么改变 |
| 是否算对 | 每项单价乘数量可复算，计入米饭与一次配送费，没有虚构折扣 |
| 是否接住新条件 | 使用最新人数、预算、菜的道数与口味要求，不恢复已取消的菜 |
| 是否诚实处理冲突 | 条件无法同时满足时明确说明，等待用户取舍，不冒称符合全部要求 |
| 是否适时停下 | 不发送赞同接龙，不因同伴确认又追加菜；无关键遗漏就沉默 |

公共消息由模型显式调用 `send` 发布，普通输出保持私有。页面点击成员信息区可查看最近完成回合的私有回复；沉默仍可能执行模型回合并消耗预算。这是观察真实协作的案例，系统没有自动核对订单内容，提示词也不保证模型每次算对或按固定条数停止。

## 再次体验

暂停、取消和回合预算沿用[Room 运行说明](../../../internal/room/README.zh.md)。`--max-turns 24` 是创建房间时确定的每成员回合预算，切换、轮换或服务重启均不续额；成员之间的消息也可能触发回合；不是本次订单的金额上限，也不是每轮公开消息条数上限。

比较提示词效果时保留相同开场与条件变化。修改角色指令后重启服务，再从页面新建房间。旧房间继续使用创建时保存的角色，不被新案例覆盖；「重新开始」也不会重新加载角色配置。
