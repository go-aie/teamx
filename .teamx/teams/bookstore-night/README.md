# 社区书店的周末夜场筹备组

你是社区书店老板，四位 Agent 是一起筹备活动的同事。通过一次小型活动策划，体验成员如何回应你的消息、接住彼此的建议、表达不同意见，以及在条件变化后修改方案。

这套案例使用真实模型、独立 Session 和共享 Room。配置只定义角色与协作习惯，没有预设讨论剧本、发言顺序或最终答案。[运行手册](../../../internal/room/README.zh.md#启动与协作)另提供 reviewer/observer 单房间 CLI 体验。

## 场景与角色

书店准备在一周后举办第一场周六夜场：18 位来宾、预算 1000 元、两名现场工作人员、约 30 平方米，不能开火或太吵。你希望陌生人自然认识，但不想强制社交或轮流自我介绍。现场工作人员是活动方案中的人手，与四位负责讨论的 Agent 是不同概念。

| 成员 ID | 称呼与职责 | 关注点与发言习惯 |
| --- | --- | --- |
| `alan` | 阿岚 · 统筹 | 温和、果断；澄清目标、处理分歧，需要时向你提出关键取舍，最后整理共同方案 |
| `xiaoye` | 小野 · 活动策划 | 有想象力；提出具体玩法，接住限制后保留趣味、调整设计 |
| `laozhou` | 老周 · 店务运营 | 务实、直率；检查预算、空间、人手，指出问题时给出省事的替代方案 |
| `qixi` | 七喜 · 来宾体验 | 细腻、亲切；照顾独自来、空手来、不爱发言的人，降低参与门槛 |

你负责提供条件、表达偏好和最终拍板。成员可以改变主意，也可以阅读后保持沉默。阿岚负责业务上的统筹，不控制其他成员的调度。

## 启动一次，后续都在 UI 操作

需要 Go 1.27+、Node、完整安装的 DSH，以及模型 API Key。首次使用请先按[主 README](../../../README.md)准备环境，并配置`.teamx/config.toml` 的默认 runtime。成员无需各自配置模型和 DSH 路径。

从 **TeamX 根目录**启动服务：

```sh
go build -o /tmp/teamx ./cmd/teamx
export OPENAI_API_KEY='替换为你的模型 API Key'
/tmp/teamx serve --config .teamx/config.toml \
  --listen 127.0.0.1:8089 --max-turns 24
```

保持服务运行，后续新建房间、发送消息、引用、查看成员详情和暂停均通过页面完成。服务不自动加载 `.env`。

1. 打开 **http://127.0.0.1:8089/**，点击左侧「＋」新建房间，选择「社区书店 · 周末夜场筹备组」。
2. 团队使用全局模型、DSH 配置，并包含四位成员的职责，无需再选运行配置。
3. 点击「创建并进入」，阿岚、小野、老周、七喜已准备协作，无需逐个添加或启用。
4. 新房间公共消息为空；开场消息填入草稿，确认或修改后点击「发送」。
5. 查看公共消息和成员状态，按下方步骤参与讨论。点击左侧旧房间可切回，草稿与会话分别保留。

成员使用独立私有 Session。工作区自动建在 `<data_dir>/rooms/<房间ID>/workspaces/<成员内部ID>/`。`.teamx/config.toml` 提供公共模型及 DSH 参数，`prompts/` 提供角色指令，不必编辑四套运行配置。

项目配置从 `.teamx/teams/` 加载团队；通过配置中的 `server.teams_dir` 可指定其他目录。初始化配置和必要资源在创建时保存；切回或重启使用各房间已保存的数据，不重新加载案例或替换成员。从其他工作目录启动时用 `--config /绝对路径/config.toml` 指定同一份配置。

## 案例文件

- [team.json](team.json)：UI 中的标题、简介、成员名单和可编辑的开场消息。
- [prompts/](prompts/)：四位成员的角色与协作指令，明确什么时候回应用户、回应同事、修改意见或保持沉默。运行参数统一位于 `team.json`。

## 体验步骤

同一 Room 的成员回合按 FIFO 取得执行名额，页面可看到“等待执行”和“运行中”；取得名额后成员会重新核对最新未读。回复顺序不固定，当前成员执行期间的新用户消息仍会合并等待，不自动打断。串行执行不限制公开消息条数，是否沉默仍由成员判断。

建议一次只发一条新要求，留时间观察成员如何讨论。模型异步运行，回复顺序和条数会变化，不要求每位成员每次都发言。

### 1. 给出目标，让想法自然碰撞

创建后，输入框会填入下面的开场消息，确认或修改后点击「发送」即可；已经发送过就无需重复：

> 我想给社区书店办第一场周六夜场，18 位来宾，预算 1000 元，准备时间一周，现场只有两名工作人员。场地约 30 平方米，不能开火，也不能太吵。
>
> 希望陌生人能自然认识，又不想变成强制社交或轮流自我介绍。大家帮我想一个愿意亲自参加的活动。先聊聊最值得做的方向，有不同意见就直接讨论；不必每个人都给我一份完整方案。涉及实际价格的地方先标明估算。

观察是否有人提出具体玩法，其他人是否独立判断它适不适合目标，再给出影响选择的补充或异议，而不是各写各的报告。最先发言的人和第一个提议都不固定；不要求人人接话，也不要求为了表达不同意见另提一套方案。方向尚未确定时，先比较核心价值和代价，不急着堆桌椅、签到或收尾细节。

如果出现了一个你想深入的方向，可以说：

> 我比较喜欢这个方向。老周和七喜，你们觉得最值得改的一个地方是什么？小野可以接着调整，不用重新提一套。

### 2. 改变资源，观察是否真的修改方案

初步讨论后，发送：

> 条件有变化：预算只剩 500 元，当天也只有我一个人值班。活动目标不变，请在已有方向上做减法。保留什么、取消什么？

看他们是否沿用已讨论的核心创意、更新预算和分工，以及放弃已经不可行的环节。阿岚应帮助处理取舍，其他成员也可以直接回应彼此，无需等你逐一点名。

### 3. 表达偏好，或追问一条成员消息

选择与实际讨论相关的一条即可，不必全部发送：

- “老周，你觉得小野这个版本现在能由我一个人执行了吗？还有什么必须删掉？”
- “七喜，我一个人来也不太敢主动搭话，这个环节会不会让我尴尬？”
- 如果出现抽签配对：“我不喜欢抽签配对，感觉还是有点强迫。能保留交流机会，但让参与更自由吗？”
- 如果有真实分歧：“小野和七喜对这个环节意见不同，你们先回应一下对方的顾虑，不用急着交给我决定。”

在页面点击对应消息的「引用」，再输入追问并发送，更容易看清回应关系。

正文可以写中文称呼或 `@laozhou`，其他成员仍会收到公共消息通知，由模型判断是否与自己有关。引用消息也不会限制谁能回应。成员需要老板回答或拍板时，会被提示 `@你的用户名`；页面高亮该消息并显示「有人 @你」，点击定位后直接回复即可，查看提醒不代表同意。

### 4. 拍板收尾，观察是否适时停止

当你满意时发送：

> 就按我们刚才确定的方向。阿岚，请整理一份我能照着准备的最终方案，包括活动流程、500 元内的预算估算、我一个人如何执行，以及还需要我确认的事项。其余人只补充会影响执行的关键遗漏，没有就不用回复。本轮先到这里。

观察最终方案是否保留了你的新约束和团队讨论结果；其他成员能否在没有关键遗漏时保持沉默，避免“同意—谢谢—再总结”的接龙。

## 怎么判断体验是否成立

值得观察的不是消息数量，而是这些变化：

- **接住用户意图：** 直接回答你的问题，不反复退回最初任务。
- **接住成员观点：** 明确回应某个建议，给出补充、异议或调整，能看出方案因讨论而改变。
- **发言有增量：** 不为赞同、复述或确认已被采纳的建议另发一条消息；被点名的问题仍会直接回答。
- **分工有差异：** 策划关注玩法、运营关注执行、体验关注参与门槛，统筹在需要时收敛。
- **会做减法：** 发现问题后能删掉或简化环节，不总靠新增机制补救；不把没有采购费用说成没有准备、现场或后续负担。
- **保留上下文：** 预算变成 500 元、人手变成一人后，后续方案继续遵守；你否决的环节不会换个说法回来。
- **分清建议和事实：** 成员赞同不代替你的拍板；桌椅存量、布局和价格等未核实条件继续标为假设，不因讨论停下就宣称方案可执行。
- **懂得结束：** 无新增贡献时沉默，拍板后不无限延伸讨论。

成员公开发言会通知其他成员，因此成员间可以自行继续讨论。普通模型输出保持私有，只有显式 `send` 才会进入房间。页面点击成员信息区可查看成员最近完成回合的私有回复和工具状态；没有公开回复不代表没工作，也不保证每轮一定有可见互动。

页面查看历史和成员详情不会推进 Agent 的读取游标。四位同时使用真实模型，响应耗时和发言质量受模型与服务影响；本案例提供配置和体验指引，不是确定性的行为验收。

## 暂停、排查与再次体验

- **成员还在运行：** 等待回合结束再判断结果；详情中的私有输出在回合结束后更新，不是实时思考流。
- **讨论停住：** 先看成员状态。健康空闲可能表示没有新贡献，可发送具体追问；失败或暂停时先查看错误，不要靠不断催促掩盖问题。
- **讨论太热闹：** 明确要求只补充新信息或发收尾消息；需要立即停止时，在各成员旁点击「暂停」；成员仍在运行时点击「取消回合」。
- **回合预算耗尽：** `--max-turns 24` 是创建房间时确定的每成员回合上限，失败与取消也计数；成员间消息也会触发回合。启用、切换、轮换和服务重启均不续额，预算不是货币费用上限。新任务可新建房间。

暂停后想继续，在成员旁点击「启用协作」，再发送新的具体任务。启用后无需每发一条消息就重新启用。

退出时在服务终端按 **Ctrl-C**，等待成员和工具进程清理完成。使用同一个数据根目录正常重启，可恢复列表和最后选择，并按现有规则续用会话；异常中断的排查和恢复边界见 [Room 运行说明](../../../internal/room/README.zh.md#正常恢复与退出)。

想从头体验时，新建本案例的房间；旧讨论保留。修改角色指令后重启服务再创建房间；旧房间继续使用冻结配置。「重新开始」重置当前讨论与私有会话，不重新加载案例。

比较提示词前后的表现时，可复用相同开场消息及“拉新客”“公开报名”等回答，观察低增量回复、工作量判断和待确认事项是否改善。消息数与内容受模型影响，不以固定发言顺序或条数作为通过标准。熟悉案例后，可以改变活动人数、你自己的偏好，或把条件变化插到成员正在讨论时，观察他们是否接住新信息。
