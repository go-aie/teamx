# 对话式平台接入方案

状态：C1、C2、C3、C4、C5、C6 已实施（2026-11-11）。C3 已通过单账号真实浏览器／飞书／模型 Agent 的“对话发起 → 授权 → 保存 → 用户主动继续”验收；C4 已完成混合 Inbox 的类型、投影、消费关联、准入、回收与恢复，本地生产者和异常路径分别验证。C5 的连接结果订阅、可靠交付与异步自动接续已实施，并在同账号真实 OAuth 验收中确认连接保存后无需新聊天即可自动进入下一回合。C6 已通过两条单账号真实组合链路：“复用已核验账号 → 账号／群选择 → 自动关注”，以及“新 profile／真实 OAuth → 保存连接 → Inbox 自动接续 → 群选择 → 自动关注”。第二真实账号按用户要求暂不验；真实并发故障和竞争时自然语言反馈去重仍未实测。实施记录见 [连接 CLI](implementation/conversation-platform/CONNECT.zh.md)、[成员配置 CLI](implementation/conversation-platform/MEMBER-CONFIG.zh.md)、[最小对话连接](implementation/conversation-platform/CONNECTION-UI.zh.md)、[Inbox 类型扩展](implementation/conversation-platform/INBOX-EVENTS.zh.md)、[异步自动接续](implementation/conversation-platform/ASYNC-CONTINUATION.zh.md)、[完整对话接入](implementation/conversation-platform/SELECTIONS.zh.md)。

## 1. 首版目标与边界

采用「统一 CLI 操作＋Skill 编排＋可选 Inbox 续接＋对话轻交互」。首版只完成飞书连接及为当前 Agent 配置指定群关注；保留现有「设置 → 平台」模态框作为完整管理入口，右侧栏继续用于 Agent 详情。

目标体验：用户说「连接飞书，关注产品讨论群，需要我处理时在这里提醒我」，Agent 检查连接、发起授权、查询候选、配置订阅并核验结果；只在需要授权、真实选择或必要字段时展示对话按钮／小表单。仅要求添加平台时完成连接即可，不顺带开启通知、工具或发送能力。

同一操作支持三种接续，使用相同操作 ID、状态和回执：

| 方式 | 行为 | Inbox 依赖 |
| --- | --- | --- |
| 同回合等待 | 有界 wait，结果就绪后在当前回合继续 | 无 |
| 异步自动继续 | 订阅操作结果后结束回合，经 Inbox 进入新回合 | 有 |
| 用户主动继续 | 用户稍后发言，Agent 查询原操作再继续 | 无 |

短等待尝试一次有界 wait；授权／扫码等长交互默认异步，用户始终可以主动继续。等待超时不取消操作，自动接续受成员启用状态和现有 Inbox 准入约束。

**首版不做**：通用任务工作流引擎、通用事件总线、动态表单引擎、browser use、事件优先级／独立消费游标，以及 GitLab 扩展。群关注只改变明确的接收范围；平台工具配置不改变现有外部写入授权规则。

## 2. 职责与核心不变量

| 模块 | 负责 | 开发边界 |
| --- | --- | --- |
| 平台操作服务 | 授权、账号核验、连接保存、配置及回执 | 复用现有适配器与配置锁；不固化“连接后关注哪个群”等业务流程 |
| TeamX CLI | 发起、查询、等待、取消、设置结果通知 | 服务客户端，不直接操作凭据文件；wait 只观察既有操作 |
| 接入 Skill | 理解需求、选择命令和接续策略、核对结果 | 不能代替代码完成身份、版本、幂等和凭据约束 |
| 对话组件 | 固定交互、用户提交、进度与结果展示 | 只存轻量交互引用，变化状态由服务提供 |
| Inbox 通知适配 | 按订阅可靠交付内部操作结果 | 复用序号、批次、消费确认；类型差异集中封装 |
| 原设置 | 完整管理、高级调整、异常处理 | 通过 HTTP 复用相同服务，不另建业务逻辑 |

实施必须保持：

- 成员调度、暂停、执行预算、Session 轮换及失败恢复语义不变，不新增第三种回合输入。
- 平台连接仍由服务全局共享；通知和工具配置绑定完整 Room／Agent／Membership 身份，同名替换成员不继承旧操作或事件。
- 操作结果、事件交付、Inbox 消费和原需求完成是独立事实；任何一种确认不能代替其他确认。
- 连接及查询能力可在未连接平台、未开启平台工具时使用；原 human 管理接口的检查不直接放宽。

## 3. 最小操作协议与 CLI

以下命令为拟定接口，保留现有 `platforms upgrade` 等语义，具体字段以实现时帮助和 JSON 契约为准：

| 入口 | 契约 |
| --- | --- |
| `teamx platforms skill` | 基础只读 Skill 入口，不依赖平台工具绑定 |
| `platforms list`／候选查询 | 返回当前身份可见的连接、账号和群候选，支持搜索／分页，不暴露凭据 |
| `platforms connect start` | 接收 provider、name、稳定 operation-id、真实用户 source-seq；快速返回操作 ID、阶段和交互引用 |
| `platforms connect status` | 纯读原操作及回执；支持按原请求查询关联操作以恢复进度 |
| `platforms connect wait` | 对原操作做有界等待，返回结果或 pending；首版在 CLI 内按有界节奏查询 status，不新增后端等待调度机制 |
| `platforms connect cancel` | 显式停止原操作未完成部分并结清，保留已发生效果 |
| `platforms connect notify` | 设置 inbox／none；start 也可带通知选项，通知策略独立于固定业务入参 |
| `platforms connect acknowledge` | 保存精确结果版本的处理回执，供同步返回／主动继续／晚到事件核对；不代替 Inbox 消费或原需求完成 |
| 成员通知／工具配置命令 | 封装现有配置服务，修改明确范围、保留无关设置，返回可核对回执 |

### 3.1 单个连接操作

业务步骤固定为：准备官方配置／授权 → 核验指定 profile 和账号 → 保存 TeamX 连接。只有最后一步确认后才报告 connected；已有可复用连接先查询，避免重复创建。

最小持久化记录包含：操作 ID、原请求关联、完整成员与操作者身份、服务读取的真实用户依据、固定业务入参摘要、版本、阶段、分项结果／错误码及交互引用。通知偏好与待投递记录独立保存。复用已有 onboarding 与平台配置结果，避免另建重复的账号／订阅权威状态。

阶段至少区分待用户操作、执行中、已完成、已取消、已过期、失败和结果未确认。部分成功用分项回执说明，不把“已配置应用”“已授权”“已保存连接”混为一体。记录操作与原请求的关联即可，不持久化通用流程图。

### 3.2 正确性要求

- 同一操作 ID、相同固定入参返回原结果；改变业务入参报冲突。后续配置步骤也使用稳定操作 ID，不能用新 ID 重发未知操作。
- 服务持有授权进程与超时，CLI 退出、wait 到期或观察请求取消不等于 cancel。status 纯读，不重新授权或触发保存；wait 的整体与单次 HTTP 请求超时分别有界。
- 新增受控 Agent 操作入口，校验当前成员和真实用户指令；消息依据由服务读取并保留必要证据，不接受 Agent 自报 human 身份或以外部评论作为授权。
- 服务端账号／群候选携带稳定 ID 与账号版本，提交前复查；已提交操作的目标不可通过改草稿悄悄替换。
- 授权和配置继续走已有串行保护、共享连接影响检查及结清逻辑，不另起原生 CLI 登录进程绕过锁。
- 操作与通知成败分别记录。订阅时操作已经完成，仍可按同一结果版本补发稳定事件；取消订阅不承诺撤回已入队事件。
- 临时 OAuth 会话不要求跨服务重启原样恢复。重启后先查已保存结果，必要时重新授权，不为恢复功能额外持久化 Secret、Token、device code 或临时授权链接。

## 4. 对话交互与 Skill

新增独立于平台工具绑定的接入 Skill，复用现有内置只读 Skill 机制。主 Agent 指南只增加发现入口和使用时机，完整流程按需读取：

检查已有连接 → start 并展示交互 → 有界 wait／订阅 Inbox／用户主动继续 → status 核对 → 查询或选择群 → 调用成员配置命令 → 核验并反馈。

首版固定组件只覆盖授权按钮／二维码、账号与群候选选择，以及名称等少量字段；由后端给出类型、字段和候选，不执行模型生成的 HTML、脚本或任意表单描述。

- 消息保存稳定交互引用，状态、草稿和授权会话数据由服务查询；不通过反复改写公共历史表达进度。
- 按交互 ID 保留组件实例、输入与焦点，避免现有消息重绘销毁表单。手动编辑与命令更新共享草稿版本，延迟更新不得覆盖新输入。
- 交互先于 wait 发布；命令等待期间用户仍可授权或提交。页面可直接展示操作结果，无需等 Agent 续接。
- 提交校验交互版本、账号候选及操作者，保存真实操作回执；重复点击或多标签页提交只应用一次，不伪造用户聊天消息。
- 原设置通过 HTTP 使用同一服务。进入完整设置处理关联操作时共用结果和版本，关闭页面不隐式取消由对话发起的操作；主动取消仍需清楚反馈。
- Skill 先查原操作，再决定下一步。同步返回、主动继续及晚到事件都依据同一批回执处理，不重复配置或反复发送完成反馈。
- 纯进度变化只更新界面。明确指令不重复确认；能力不可用或 Inbox 阻塞时如实提供主动继续入口，不承诺立即自动唤醒。

## 5. Inbox 扩展：独立评审的核心改造

本节只用于异步自动接续，不作为核心 CLI 的前置依赖。首版仅增加内部操作完成／失败及用户选择结果，不扩展到任意任务、定时器或通用事件路由。

### 5.1 信封与集中分派

`InboxEntry` 显式区分 `platform_notification` 和 `task_event`：

- 平台条目保留现有 `notification.Item`；内部条目仅保存事件 ID、操作 ID／结果版本、原请求引用、事件类型及结果引用。
- 两种载荷互斥，未知类型拒绝。已有无类型字段的平台条目按现有格式读取并校验，不静默清空或改写队列。
- 内部事件由服务生成并绑定完整成员身份，不虚构平台账号、订阅、外部对象，也不调用远端引用解析。

在 Room 内增加少量私有类型处理函数，集中提供载荷校验、公共元数据提取、读取投影、消费关联检查及保留／回收判断。公共收发、批次和游标代码调用这些函数，避免各处直接判断具体操作或平台。首版使用封闭的两类分派，不建设动态注册框架。

平台条目沿用原有准入、引用解析和 followup 关联；内部条目只关联本地操作事件记录，不强制创建普通事项。Agent 读视图及人类预览显式展示条目类型，错误类型不能落入默认平台处理。

### 5.2 交付、消费与回收

1. 操作结果先可靠保存。有订阅时生成不可变事件及待投递标记，以稳定 DeliveryID 投递，并以 Inbox 持久化回执确认交付；任一步中断均按原 ID、同一载荷核对和重试。
2. 消费确认前先持久化对应关联：平台条目沿用原 followup 关联，内部条目保存操作／事件关联，再推进既有消费游标。预览不消费，消费不标记原需求完成。
3. 内部事件未消费前不被平台通知的过期策略自动跳过。消费且关联回执持久化后，按事件保留策略回收正文，**不等待“持续关注某群”等长期任务结束**。回收仍遵守既有前缀边界，不另开独立游标；可查询的操作结果与必要去重回执保留。
4. 事件只是继续处理的信号。Agent 收到后查最新操作及更新后的用户意图，已处理步骤跳过；回合失败后按既有失败恢复规则继续，不重投已消费事件来强制重试。

### 5.3 共享队列边界

保留现有有序批次、准入、暂停、公平性及预算约束。外部通知核验阻塞时，不绕过它推进游标，也不只放宽 `AutomaticBlocked`；展示“操作已完成，等待 Agent 接续”及阻塞原因。用户可发言触发原操作查询，不改变被阻塞的 Inbox 消费状态。

容量不足时保留待投递状态并反馈；暂停或成员退出不丢弃已保存结果。同名新成员不接收旧事件。通知不可用不把成功连接改成失败，多个观察者收到同一结果也不得重放后续操作。

## 6. 开发阶段与验收出口

将原 C0 的操作契约并入真实连接开发，作为 C1 内的子步骤，不单独建设通用基础框架。按以下六个可独立验收的增量实施，未增加首版功能范围：

| 阶段 | 交付范围 | 验收出口与本阶段边界 |
| --- | --- | --- |
| C1：连接 CLI | 飞书连接服务、start/status/wait/cancel、真实用户依据、关联操作查询及仅覆盖连接的基础 Skill；同步确定后续需要的最小操作／交互契约 | 模拟授权覆盖保存、取消、过期、部分成功和未知结果，CLI 退出不取消后台；无平台工具绑定也能读取 Skill。无 Inbox，不要求完整对话 UI，不宣称真实端到端接入已完成 |
| C2：成员配置 CLI | 已核验连接的群搜索／分页、通知和工具配置命令、相应 Skill 步骤，复用既有配置服务与回执 | 明确候选 ID 后能准确配置、核对结果，保留无关设置和既有接收起点；多候选返回可选择内容，不擅自猜测。业务链路可独立通过 CLI 验证，不依赖对话选择器或 Inbox |
| C3：最小对话连接 | 连接交互引用、授权按钮／二维码、进度／结果展示、稳定渲染及原设置服务复用；先跑通单账号连接 | 真实浏览器＋飞书＋Agent 完成“对话发起 → 授权 → 保存 → 同回合或主动继续”；等待期间可授权，新消息刷新不破坏交互。不包含群选择表单、复杂字段修改或异步自动接续 |
| C4：Inbox 类型扩展 | 集中类型分派、内部事件读写、Agent／UI 投影、消费关联、准入、清理与恢复；使用服务内测试生产者验证 | 混合条目可完整读取、确认、恢复和回收，旧平台消息回归通过，暂停和调度语义不变。不接真实操作的通知订阅，不发布只能写入却无法消费／恢复的半成品 |
| C5：异步自动接续 | 操作结果通知订阅、待投递记录、可靠交付与恢复、Skill 异步策略，以及三种接续并存的竞争处理 | 无新聊天或平台通知时，经 Inbox 自动继续原连接；订阅交接、已完成结果补投、晚到事件不重放后续步骤，暂停／阻塞有准确反馈。基于 C4，不继续扩展通用队列能力 |
| C6：完整对话接入 | 复用 C2 的候选／配置命令，增加账号与群选择、少量字段修改、完整 Skill 流程及设置回流 | 真实完成“连接飞书并关注指定群”，覆盖多候选、草稿冲突、重复提交及三种接续；原设置回归通过。不再补建基础命令或 Inbox 核心协议 |

依赖关系：C2、C3、C4 均以 C1 的最小契约为基础；C5 依赖 C3＋C4；C6 依赖 C2＋C3＋C5。默认按 C1 → C2 → C3 → C4 → C5 → C6 顺序推进，先看到 CLI 业务能力和最小对话体验，再进入 Inbox 核心改造。接入 Skill 按阶段暴露已实现命令，C5 前不承诺自动唤醒。

### 6.1 C1 提前固定的最小契约

只固定操作 ID、原请求／成员关联、结果版本、阶段及错误分类、交互引用；为后续通知保留以操作 ID／结果版本定位的稳定依据。交互引用先支持连接授权，候选和字段组件后续按已约定引用方式增加，不提前实现通用交互／事件系统。

### 6.2 C4 内部开发顺序

信封与旧数据读取 → 类型校验和 Agent／人类投影 → 消费关联及确认 → 准入与回收 → 混合队列恢复。可以分开发和评审，但必须全部通过后才允许正式产生内部事件，避免“能写入、不能消费或重启加载”的中间状态。真实操作事件生产者在 C5 接入。

### 6.3 每阶段必含的异常验证

- C1：重复 ID／改变入参、wait 超时、CLI 中断、取消后晚到结果及结果保存后重启，均不重建连接或误报成功；原 human 接口与凭据边界保持。
- C2：账号版本变化、同名群、成员替换、配置版本冲突和未知提交结果，不配错目标、不覆盖无关配置、不重放未知动作。
- C3：交互先于 wait 可用，切换房间、刷新、重复点击和原设置关闭不会串目标或误取消对话操作；模拟 DOM 与真实浏览器分别验证。
- C4：平台／内部条目混合批次、旧数据、错误类型、消费确认中断、准入阻塞、容量不足、暂停与回收均独立回归；消费事件不等于长期业务完成。
- C5：订阅前、订阅中、订阅后完成均不丢结果；Inbox 交付中断、消费后中断和 Session 轮换可恢复，主动继续／同步返回／晚到事件不重复执行或反馈，失败回合不自动重试。
- C6：多账号、多候选、手动／自然语言字段冲突、多标签页与过期表单、取消及高级设置回流通过；原设置的添加、编辑、授权、核验和撤销均回归。

可靠性验证随阶段完成，C6 只做剩余交互及组合验收，不承接之前遗漏的核心正确性工作。组件、模拟适配器、真实浏览器及真实平台／Agent 的证据分开记录。只有 C6 完成才宣称首版完整体验通过；GitLab 与其他通用能力另行评估。

阶段编号仅用于方案和实施记录，长期代码、测试与文件按领域或行为命名。

## 7. 代码落点与复杂度

| 当前代码 | 实施落点与复用 |
| --- | --- |
| `internal/room/cli.go`、`cli_help.go` | 增加受控接入命令；wait 复用纯读查询；保留既有命令语义 |
| `platform_lark_auth.go`、`platform_lark_setup.go`、`internal/platform/lark/` | 保留官方 CLI、后台会话、配置锁及核验；整理为 CLI／设置共用服务，操作日志只记录公开阶段和回执 |
| `platform_onboarding.go`、`platform_lark_chats.go`、通知／工具服务 | 复用固定入参、分项回执、群搜索和配置版本；每个后续配置独立提交，不复制原权威配置 |
| `internal/platform/tool/skills.go`、Agent 指南 | 复用只读 Skill 嵌入方式，增加不依赖平台绑定的发现入口 |
| `state.go`、`web/{app.js,index.html,style.css}` | 轻量交互引用及固定组件，局部解决消息重绘；草稿与界面状态从操作服务投影 |

| `member.go`、既有回合检查点和 DSH／ACP | 复用 Room／Inbox 输入、暂停、预算和轮换；不为平台接入增加特别调度分支 |

可行性高。C1/C2 主要是服务封装、受控命令与配置回执；C3 提前验证最小 UI 和真实授权链路；C4 是中等到中高复杂度的核心改造，需要独立评审；C5 聚焦通知适配与接续竞争；C6 聚焦选择／字段交互及组合验收。三种接续共享协议，工作量不应按三套流程相加。

完整飞书产品仍需为混合 Inbox、对话渲染及真实授权验收预留投入；此前 12–20 个工作日仅作粗预算，在 C1、C3 和 C4 的关键假设验证后按剩余改动重估，不能将新增阶段数直接换算为新增工期。若实现要求新增通用任务引擎、在调度器判断平台类型、改写业务授权语义或引入动态表单框架，应先收敛设计，不能将其作为本功能的顺带重构。
