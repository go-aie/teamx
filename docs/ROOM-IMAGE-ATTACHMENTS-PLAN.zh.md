## 1. 目标与范围

让用户在 Room 输入框粘贴图片，或通过「+ → 添加图片」选择图片，发送纯图片消息或文字加图片消息。发送后图片可预览，Agent 通过现有 inbox_read／history read 读取。

首版覆盖托管 Room、默认助理私信和单 Room 模式，沿用 TeamX 绿色视觉风格。支持 PNG、JPEG、WebP 和每条消息多图。

本次不增加通用文件上传、拖拽上传、图片编辑／自动压缩、GIF／SVG、外部图片 URL 导入、Agent 主动上传发图、跨 Room 附件共享或独立附件管理页面。已有平台图片格式及行为不因此收窄。

核心取舍：

- 图片是 Room 消息的结构化附件，文件归 Room 数据目录所有。
- 上传产生草稿对象，消息提交才形成正式引用；Room 原生消息发布仍是唯一权威。
- Agent 不增加工具、必填参数、预取步骤、读取游标或新的图片注入流程。
- 文件读取来源可以不同，图片预算、去重、内容块输出和读取确认继续共用已有能力。

## 3. 用户交互

### 3.1 客户端来源与设备差异

新增的用户图片来自当前打开 TeamX 页面的客户端。桌面端是用户电脑上的图片文件或剪贴板截图；手机端是系统选择器交付的照片／文件，或浏览器粘贴事件实际提供的图片。浏览器得到 File 后上传字节，服务端验证并保存，后续人类预览与 Agent 读取使用保存的对象。

~~~text
电脑／手机的文件、照片或剪贴板
  → 当前浏览器中的 File 与本地缩略图
  → HTTP 上传
  → TeamX 服务端 Room 附件对象
  → 消息引用、跨客户端预览、Agent 既有读取
~~~

「添加图片」打开客户端系统选择器，与 TeamX 服务端工作目录无关。手机访问另一台电脑运行的 TeamX 时，选择的是手机可提供的照片／文件；请求不包含可让服务端打开客户端文件的路径。

| 行为 | 桌面端 | 手机端 |
| --- | --- | --- |
| 选择图片 | 「+ → 添加图片」打开电脑的文件选择器，可多选 | 同一入口调用系统选择器，由系统／浏览器提供可用的照片或文件入口；多选能力以实际选择器为准，可分次追加 |
| 粘贴图片 | 处理输入框 paste 事件暴露的图片文件，面向截图等场景 | 支持浏览器实际暴露图片文件的粘贴事件；不把长按菜单出现“粘贴”等同于浏览器一定提供图片 |
| 无图片粘贴能力 | 文件选择入口始终可用 | 相册／文件选择是必须可用的主路径；不能要求手机必须通过剪贴板上传 |
| 选择取消 | 保留原草稿，不产生失败条目 | 同左；页面重新获得焦点不视为发送或重新选择 |

实现统一使用文件输入（multiple，accept 指定 PNG／JPEG／WebP），由真实用户点击直接触发，不通过服务端列目录，也不在触发选择器前等待网络请求。不强制 capture 或承诺专门拍照入口；系统提供的额外来源由系统处理。

粘贴以 ClipboardEvent 提供的图片 File 为准，兼顾 items／files 的可用形式并去重；不使用后台轮询或自动读取全局剪贴板作为前置条件。移动端未提供图片文件时保留普通粘贴行为，用户仍可通过「添加图片」完成上传。

系统选择器的 accept 是筛选提示，真实文件格式仍由服务端校验。若手机交付 HEIC／HEIF 等首版不支持的文件，明确提示选择或另存为 PNG／JPEG／WebP；不能假设系统必定转为 JPEG，也不能只改扩展名伪装支持。首版没有格式自动转换。

手机切到系统选择器／其他应用或网络暂时中断，不视为上传成功或发送成功。返回后按条目实际状态恢复；需要重试时复用附件 ID。手机和桌面复用同一 addFiles、上传接口与发送合同，差异限于图片获取和触控／键盘交互。

### 3.2 添加与编辑

1. 「+」打开简短菜单，首版只有「添加图片」，调用隐藏的多选文件输入。桌面和移动端含义一致，工作目录仍由目录按钮打开。
2. textarea 的 paste 处理剪贴板中的图片文件。只有实际接管图片时才阻止对应默认行为；普通文字粘贴保持原样，图文同时存在时文字仍插入光标处。忽略 HTML 中的远程图片 URL。
3. 两种入口调用同一 addFiles 流程。读取本地 File 后立即显示缩略图并自动上传，按选择顺序排列；上传完成顺序不改变发送顺序。
4. 缩略图显示上传中、已就绪、失败／需重新选择三类状态，提供删除及失败重试。仅在用户点击发送后才发布 Room 消息。
5. 待发送附件放在输入框上方，限制显示高度并允许换行／滚动；保留引用区，避免移动端发送按钮被推出视口。菜单支持键盘、Esc 和焦点返回，删除按钮有可读名称。

「+」和发送按钮不能再占用同一个互斥位置。输入文字、选择图片后「+」仍可用；工作目录模块不再控制「+」的 enabled／aria 状态。关闭目录弹层及返回焦点的代码改为使用目录触发器。

### 3.3 发送规则

- 有非空文字或至少一张就绪图片才可发送；移除 textarea 的 required，前后端统一此条件。
- 存在上传中、失败或待重新选择的附件时，发送按钮不可用，并显示具体原因；用户可删除问题附件后发送。不能静默忽略失败图片。
- 沿用现有文字 16 KiB、提及、引用和输入法 Enter 防误发规则；图片不转换为占位文字，也不改变提及偏移。
- 点击发送后冻结文字、附件顺序、引用、提及、operator、Room 身份和 client_message_id。等待期间不能修改该次请求。
- 回执成功后清空对应草稿并刷新消息；回执不确定时保留原请求，重试不能重新上传或生成新消息 ID。
- 「放弃重试」仍提示原消息可能已经提交，保留可编辑草稿；下一次主动发送生成新消息 ID。附件可被新消息再次引用，不引入“一张图只能发一次”的状态。

### 3.4 草稿与消息展示

草稿继续按 installation、room_instance、operator 隔离：

- 已上传附件只把 ID 和展示元数据加入现有草稿持久化，不保存 File、Blob、Base64 或带 epoch 的预览 URL。
- File、上传 AbortController、临时 object URL 仅保存在内存中。删除、替换或释放草稿时撤销 object URL；会话切换后的异步结果只更新原草稿，不能写入当前 Room。
- 本地缩略图使用 URL.createObjectURL。当前页面 CSP 的 img-src 为 'self'，需要在 internal/web/handler.go 中仅扩为 'self' blob:；脚本及其他来源策略不变。
- 同一页面切换会话保留未完成附件。刷新后，已上传附件通过批量状态接口恢复；只有内存 File 的条目提示「请重新选择图片」，不显示为已上传。
- 普通草稿恢复可使用当前服务身份查询附件；已经提交过的 pending 发送仍保留原 epoch，不自动换身份重发。
- 附件过期或缺失时标明原因，用户可移除或重新选择；pending 请求中的失效附件不能直接替换，先按现有不确定发送流程核对／放弃。

消息正文按附件数组展示缩略图，点击复用现有放大、缩放、旋转和下载交互。结构化附件直接渲染为 DOM，不要求用户正文包含 Markdown 图片语法，也不放宽 Markdown 对任意相对 URL 的限制。

会话列表、引用摘要和复制消息摘要在文字为空时使用「[图片]」或「[图片 ×N]」。该摘要仅用于显示，不写回消息 text；复制图片本身不在首版范围。图片加载失败不隐藏原消息。

## 4. 数据模型与存储

### 4.1 消息字段

RoomMessage 新增可选 attachments 数组，元素使用服务端确认的不可变描述符：

~~~json
{
  "seq": 42,
  "text": "看看这个报错",
  "attachments": [
    {
      "id": "img_0123456789abcdef0123456789abcdef",
      "kind": "image",
      "name": "screenshot.png",
      "mime_type": "image/png",
      "size": 182400,
      "width": 1280,
      "height": 720
    }
  ]
}
~~~

说明：

- 附件 ID 只标识当前 Room 内的对象，不表示读取权限。请求、存储类型和 Agent 投影分别定义，避免复用大结构导致客户端可覆盖可信字段。
- /v1/send 的附件输入仅为 attachments: [{"id": "img_..."}]。客户端不能指定本地路径、下载 URL、MIME、尺寸、上传者或其他 Room。
- 上传元数据保存 RoomIdentity、上传 operator、创建时间、文件 SHA-256 及完整描述符。文件名仅展示，按 basename 清理并限制 UTF-8 字节数为 256，不参与路径拼接。
- 数组顺序定义展示／图片位置。同一消息拒绝重复 ID；不同消息允许复用同一 Room、同一 operator 上传的对象。
- 首版仅 human 普通消息可带本地附件；Agent、integration、内部 event 和 durable publication 不能借此上传或附带未授权文件。
- PostMessage 输入、RoomMessage、read 投影、日志克隆和返回切片都保持明确所有权；新增附件切片不能与可变草稿或候选共享。

旧消息缺失 attachments 按空数组处理，不迁移历史数据。增加字段不意味着旧二进制可以继续读写新数据；升级后禁止用旧二进制写入含附件的 Room，不为此建立双写兼容层。

### 4.2 文件布局与发布

~~~text
<room-dir>/
  attachments/
    objects/
      img_<id>/
        meta.json
        data
    tmp/
      <upload-temp>/
~~~

对象目录一旦发布，meta.json 与 data 不再修改。文件名由受限 ID 派生，使用私有目录／文件权限，拒绝路径穿越、符号链接及非普通文件。

客户端首次选择图片时生成随机附件 ID，上传重试复用该 ID。它同时是上传幂等键，无需额外的 upload_id → attachment_id 持久表。同 Room／operator／ID、同文件内容及规范化名称返回同一描述符；同 ID 不同内容或名称返回 conflict，禁止覆盖。

上传流程：

1. 校验服务身份、operator、Room 生命周期及配额，预留本次容量；客户端 Content-Length 只作早期拒绝，实际读取仍受硬上限约束。
2. 在 tmp 中接收，按真实格式检查、DecodeConfig 获取宽高并先校验像素，再做完整解码校验，计算 SHA-256。已有 ValidateImage 不能单独证明文件完整，需在上传模块补此检查；昂贵解码保持有界并发。拒绝截断／无法解码的文件；首版不重编码、不压缩、不保留路径。
3. 写入元数据，同步文件和临时目录；在并发去重检查后原子 rename 为对象目录，再同步父目录，最后才返回上传成功。
4. 未确认完成的对象不能用于首次消息提交。发生发布结果不确定时，按原 ID 重新核验并完成必要同步后返回；失败只使该上传不可用，不把普通上传错误写成整个 Room 的消息存储 uncertain。

临时文件和孤儿对象可以多留一段时间；不能把未发布完整的对象当成上传成功，也不能在消息落盘前返回发送成功。

同 ID 的并行上传串行检查或返回 busy，由客户端持原 ID 重试，不重复发布和计费。启动时重建对象及临时文件的容量统计；成功发布／失败取消后同步更新预留与实际使用量，不能只依靠进程内计数。读取对象时核对元数据、实际字节数和 SHA-256，损坏结果按不可用处理。

### 4.3 默认限制

首版尽量对齐现有图片输入默认值：

| 限制 | 首版值／规则 |
| --- | --- |
| 格式 | PNG、JPEG、WebP，按真实内容判断 |
| 每条消息图片数 | 默认最多 4 张 |
| 单张上传大小 | 默认 2 MiB |
| 每条消息图片总大小 | 默认 4 MiB |
| 单张像素 | 默认 16 Mi 像素 |
| 每个 Room 文件总量 | 1 GiB，包含草稿、正式对象、接收中预留容量 |
| 每个 Room 对象数量 | 最多 4096 个，包含草稿和接收中预留对象 |
| 未引用上传有效期 | 创建后 24 小时；过期对象若已有正式引用则继续保留 |

若当前 image_materials 的图片数、单图字节、总字节或像素配置更小，新上传／发送采用对应更小值。首版不新增设置页面；通过 /v1/info 的附件能力摘要将有效限制提供给前端。

这些限制防止默认情况下单张新图片天然超过模型预算，不承诺一个回合读完所有图片：同回合其他消息占用、历史读取单独上限、文本模型和序列化预算仍可能导致遗漏，必须复用现有覆盖说明。

未来调低配置不能使旧消息结构失效或删除旧图；存量预览按上传存储硬上限校验，模型读取仍按当前执行预算决定是否供给。超过首版上传限制时给出明确提示，不偷偷压缩或把全局 Agent 图片预算放大。

## 5. HTTP 与消息提交

### 5.1 三个附件接口

| 接口 | 输入与用途 | 权限 |
| --- | --- | --- |
| POST /v1/attachments/upload | 查询参数携带当前 ServiceInfo、caller_id、attachment_id；multipart/form-data 仅一个 file 字段 | 当前 human operator |
| POST /v1/attachments/state | 普通 ServiceInfo／human caller JSON 信封及 ids，最多 4 个；批量恢复草稿 | 当前 human operator，且对象属于该 operator |
| GET /v1/attachments/content | 当前 ServiceInfo、caller_id、attachment_id；正式消息另带 seq | human 草稿预览仅上传者；正式预览验证 seq 引用 |

上传请求示意，实际编码使用 URLSearchParams 和 FormData：

~~~text
POST /v1/attachments/upload
  ?room_id=...
  &room_instance=...
  &service_epoch=...
  &caller_id=...
  &attachment_id=img_...
Content-Type: multipart/form-data; boundary=...

file: <图片文件>
~~~

上传响应包含完整附件描述符和未引用对象的 expires_at。state 按 ID 返回 available／expired／missing／unavailable 及可用描述符；正式引用仍存在的对象不因创建超过 24 小时返回 expired。整体身份错误拒绝整个请求，不泄露其他 Room 的存在情况。

content 只提供图片字节，不支持任意路径和外部 URL。正式图片必须核对当前仍保留且对调用者可见的消息确实引用该 ID。草稿图片只允许上传者查看。动态使用当前 epoch 构造 URL，不把它作为持久附件身份。

沿用当前同源与身份校验、Cache-Control: no-store、nosniff 和实际图片 Content-Type。文件名写入响应头时正确编码，禁止换行注入；不增加执行 token 或 Agent 可调用的上传／content 入口。

### 5.2 路由与生命周期

当前 roomManager.serveRuntime 会将 POST body 先按 128 KiB JSON 读取，service.ServeHTTP 也有同样的普通 JSON 分支。因此：

- 托管入口在普通 serveRuntime 之前单独分派上传，根据查询参数定位当前 service，释放管理锁后交给 Room 附件 handler；大文件不能整体进入管理层内存或 JSON 解码。
- service 的附件分支仍在现有同源检查和请求并发控制之后处理，并在普通 JSON 分支之前接管上传／content／state。
- 上传 body 上限为有效单图上限加 64 KiB multipart 开销；限制字段、文件数量和元数据长度，使用有界流式读取，不调用不受限的 ParseMultipartForm／ReadAll。
- 请求接纳、停止及重启使用现有 closing／restarting、changes 和托管 busy 边界。不能在 Room 已删除后创建附件目录；关闭必须等待已接纳文件操作结束。
- state 可沿用普通管理转发，但服务内使用独立小请求结构，避免把所有附件字段扩入通用 apiRequest。单 Room 同样走该 service handler。

上传、预览和草稿查询都不追加 Room 消息、不改变会话排序、不唤醒 Agent、不推进任何读取状态。

### 5.3 发送与幂等

~~~json
{
  "room_id": "room-id",
  "room_instance": "room-instance",
  "service_epoch": "current-epoch",
  "caller": {"kind": "human", "id": "owner-id"},
  "client_message_id": "original-message-id",
  "text": "",
  "attachments": [{"id": "img_0123456789abcdef0123456789abcdef"}],
  "reply_to": 0,
  "mentions": []
}
~~~

发送层按上传元数据解析可信描述符，检查 Room、上传者、格式、数量、字节及对象可用性；Room Actor 继续负责序号、原生发布、提及／引用和回执。

同 author + client_message_id 的幂等比较增加有序附件 ID 列表。相同请求返回原 receipt；顺序、ID、文字、引用或提及冲突沿用现有 conflict。幂等比较不依赖预览 URL、客户端上报尺寸或临时 File。

文件先持久化，消息后提交。Store.SaveRoom 在自身提交串行边界内，对本次新增消息的附件复核完整对象存在且身份／描述符一致，再准备日志和发布 Room root；文件清理与此检查采用同一互斥边界。这避免「发送前已检查，落盘前被清理」产生悬空引用。

检查仅针对新增引用，不能因旧图片后来损坏而让所有文字消息和成员状态保存失败。对已经提交的重复请求优先返回原回执，不能因为原图后来不可用而创建新消息。上传成功但消息未提交时，只有草稿对象；消息提交而回执丢失时，正式引用已经保护对象，原请求重试复用既有消息。

附件发布归属通过 Room 消息引用计算，不在 meta.json 再写 committed=true，不建立跨文件事务或第二套消息回执。

## 6. Agent 读取：扩展来源，共用现有能力

### 6.1 正式读取和历史读取

保留现有调用路径：

~~~text
inbox_read 选择当前 Room 流
  → prepareRoomPage
  → roomInputNotices（扩展为也收集 RoomMessage.attachments）
  → prepareInputMaterials
  → 现有图片预算／去重／缓存／MCP 图片块
  → 现有 Room 原生确认与交付恢复

history read 选择保留的 Room 消息
  → historyReadMaterials
  → 同一个 roomInputNotices
  → 现有 History 图片预算／结果缓存／图片块
  → 保持只读，不推进消费
~~~

Agent 不需要再查 attachment state、下载 HTTP URL 或提供附件 ID。一次原有读取调用就返回该消息文字、附件摘要、实际图片块及供给／遗漏说明。Agent 仍自主选择输入流；发图不会额外强制启动执行。

### 6.2 三处适配

1. **收集与投影**：roomInputNotices 保留平台 Source 分支，并增加本地附件分支；不能继续用 Source == nil 跳过普通人类消息。projectRoomMessage、inputRoomBody、history 消息投影按同一规则携带有用的附件摘要，禁止输出磁盘路径和预览凭证。
2. **来源分派与校验**：在现有 materialAttachments 的读取／复核边界组合本地 resolver。平台来源仍由原 manager 校验连接、账号和通知；本地来源只依据真实成员、当前执行、Room 消息关联、可见性及已选择范围。单 Room service 也必须装配本地 resolver，不能依赖只有托管模式才设置的平台回调。
3. **身份与覆盖**：现有两类去重实现都加入明确的来源类别。本地去重键至少包含 room_id、room_instance、attachment_id；平台键保持现有账号／订阅／来源身份。不能用空 platform.SourceRef、文件名、文件摘要或附件 ID 单独代替作用域。

附件数组下标从 1 开始作为稳定图片位置；同一图片在多条消息出现时可复用图片块，但每条消息仍保留自己的关联和覆盖说明。History 与正式读取沿用各自的去重／缓存寿命，不新建跨回合已读图片表。

本地读取必须验证 attachment_id 来自所选消息，不能只验证 File 存在。正式页沿用当前执行及固定页范围；History 沿用 attachmentRange、原生保留快照和 pinHistoryRoom，补上准确的附件关联证据。下载完成后到结果提交前的复核，同样支持本地来源。

### 6.3 共用边界

继续复用：

- 图片真实格式、字节、像素检查，以及模型 image modality 判断。
- 正式读取每执行图片预算、ClaimMaterials、PrepareMaterial、MaterialSeen、固定结果和交付确认。
- History 既有单次／单执行预算、缓存及保留期检查，不把 History 改成正式消费。
- 序列化响应上限及供给／遗漏／不可用原因；不能报告 supplied 却只返回 ID 或 URL。
- 取消、成员移除、服务关闭及执行代际检查。

本地图片字节通过 resolver 返回既有图片块，不新增 DSH／ACP 协议，不在 RunPrompt、恢复提示词或模型启动阶段旁路注入。若仍维护旧 CLI 兼容路径，只接入同一适配，不新造第三条图片准备链。

图片中的文字是消息附件内容，不自动成为指令或授权。附件来源标签准确区分 Room 用户附件和第三方通知，继续遵守原消息作者及现有授权规则。

## 7. 回收、并发与异常

### 7.1 引用决定保留

对象满足以下任一条件就不得清理：

- 仍被原生已发布、尚未清空的 Room 消息引用。
- 正在上传／首次消息提交或图片读取中，具有有效临时保护。
- 上传完成未满 24 小时，尚可作为草稿引用。

已读、Agent 执行完成、Session 轮换、Workspace 更换都不构成删除图片的依据。创建时间超过 24 小时的对象若已有消息引用，仍可在同 Room 再次发送；它的保留依据是引用。

正式引用集从已提交的物化 Room 消息建立，可在现有原生提交后维护可重建的内存集合；不得只扫描 room.json 中的 Messages，因为 InputLog 模式该数组为空，也不得把历史可见性索引中只含 seq／时间的 records 误当成完整附件来源。

### 7.2 回收触发与互斥

首版在服务启动恢复后、上传容量不足时及消息清空成功后执行有界回收，无需新增常驻定时器。未到下一次触发前允许过期对象暂留。

- 引用集更新、对象发布、首次提交最终复核及删除决定统一在 Store 的串行边界协调；使用内部已持锁 helper，禁止持有 Store.mu 再调用会重入的 LoadRoom／SaveRoom。
- 大文件接收／读取和图片解码在共享锁之外。上传先预留容量，失败／取消释放；图片读取先固定关联和获取短暂保护，再在锁外读文件，最终复核后释放。
- 不得持管理锁等待 Store、Room Actor 或文件 I/O，也不得持附件锁跨越会等待 SaveRoom 的 Actor 调用。实现时写明固定锁顺序；临时保护由实际操作结束释放，不能仅随 HTTP 请求取消提前释放。
- 现有 History pin 和正式未确认页保护继续阻止相关消息被清空。已保存的正式读取结果继续由既有交付恢复负责，不因增加附件另建回放日志。
- 回收分批限制工作量，引用状态、提交结果或存储完整性不确定时跳过删除。不得因额度不足强制删除仍被引用的图片。

清空／重新开始只在原生消息清空提交成功后让无引用图片进入可回收集合；未满有效期的孤儿可以保留到到期。重新开始时清除当前页面相关附件草稿、取消尚未发布的上传，不把旧草稿自动发送进新讨论。删除 Room 沿用现有关闭及目录删除流程，等待文件操作结束后整个附件目录一起删除。

### 7.3 异常降级

| 情况 | 行为 |
| --- | --- |
| 上传失败或取消 | 不创建消息，保留可重试条目；清理未发布临时数据 |
| 上传完成、发送前退出 | 保留草稿 ID；刷新后可恢复；无引用到期后回收 |
| 消息提交／回执不确定 | 原 ID、原请求重试；有疑义不清理对象或自动重发 |
| 草稿过期 | 明确标示并要求移除／重新选择，不静默跳过 |
| 文件丢失、校验不符 | UI 显示不可用，Agent 返回明确原因，消息正文仍可读 |
| 旧图片损坏 | 不自动删除消息，不阻断无关文字写入和其他正常附件 |
| 达到总量／对象数限制 | 先做有界回收，再返回具体容量提示；不无限接收或自动清历史 |
| 服务关闭、成员移除、历史范围失效 | 按既有身份／执行／范围规则拒绝或取消，不凭先前下载成功继续交付 |

## 8. 实施步骤

采用三个开发阶段加一个最终验收里程碑，依赖顺序为 1 → 2 → 3 → 4。每阶段完成自身测试并给出可评审结果；前面阶段完成不等于整个功能已交付。

| 阶段 | 可独立评审的结果 | 完成所需证据 | 此时尚未完成 |
| --- | --- | --- | --- |
| 1. 附件存储与消息合同 | 接口可完成上传、消息关联、取图及原 ID 重试 | 存储／HTTP／消息及生命周期组件、集成和相关并发测试 | Agent 本地图片适配、用户输入框 |
| 2. 既有 Agent 读取适配 | 同一条消息由正式读取与 History 返回图片块 | 已有读取路径的集成、预算、权限、恢复与平台回归测试 | 用户输入框、真实模型效果 |
| 3. 客户端完整交互 | 桌面／手机共用的选择、粘贴、草稿、发送和预览 | 前端逻辑及浏览器交互测试；注明模拟服务或真实服务 | 完整真实链路、真机及真实模型验收 |
| 4. 完整链路验收 | 客户端发图，人类可预览，Agent 用既有工具理解并回看 | 真实后端、桌面浏览器、真机能力记录、真实 DSH／模型证据 | 首版明确排除的能力 |

三个开发阶段按功能责任划分，工作量不要求相同。阶段 1 较重，但文件持久化、消息关联、发送重试和回收共同保证引用完整性，不拆成可分别宣称完成的“只上传”和“只写消息”阶段。阶段 2 虽然代码增量可能较小，仍需单独证明未改变正式交付与 History 的语义。阶段 3 聚焦客户端行为，避免把真机／模型环境问题混入前端实现完成的判定。

不再按桌面／手机、选择／粘贴或单图／多图分别设实施阶段，它们共用同一附件草稿和上传流程。最终验收前，各阶段都只在测试或隔离 Room 中验证新增链路；不提前把半成品入口接入日常使用，也不为分阶段实施增加临时工具、兼容路径或持久功能开关。

### 阶段 1：附件存储与消息合同

范围覆盖第 4、5 节及第 7 节中本地附件存储负责的生命周期。完成对象持久化、上传幂等、三个附件接口、有效限额摘要、消息字段、纯图片校验及发送幂等。回收及临时保护机制在此建立，阶段 2 再接入实际 Agent 读取。

阶段内可按以下顺序开发和检查，无需为每个检查点单独划新阶段：

1. 对象存储、完整性、配额及幂等；上传专用路由和草稿状态／图片读取接口。
2. 消息附件合同、可信描述符、纯图片有效条件和原请求重试；覆盖内嵌 Messages 与 InputLog。
3. 正式引用集、过期回收、发布不确定和关闭／清空／删除并发保护。

交付标准：在隔离 Room 中通过真实 HTTP 接口上传并提交图片消息，能按正式消息引用取图，重启后仍可恢复。丢失上传／发送回执不产生重复对象或消息；跨 Room／上传者引用被拒绝，清空失败或提交不确定时不会误删图片。托管与单 Room 路由、两种消息存储及旧纯文本回归通过。

此阶段不用前端临时页面验收，不添加 Agent 上传／下载工具，也不把 Agent 理解图片作为通过条件。

### 阶段 2：既有 Agent 读取适配

以阶段 1 的真实附件对象和消息合同为输入，完成第 6 节的共用收集器、本地 resolver、消息投影、来源去重及读取前后校验。实际 Agent 读取接入阶段 1 的临时保护与回收边界。

交付标准：现有 inbox_read 的 Room 流返回正确图片字节、位置和覆盖信息，正式交付确认后可通过 history read 回看，History 不推进消费。证明模型能力、预算、文件损坏、执行失效、保留范围和同图多消息行为符合第 6、7 节；正式结果重放及现有平台图片回归通过。覆盖真实本地文件及实际 MCP 结果编码，不能只断言生成了附件 ID。

此阶段不要求完成输入框，也不新增工具、参数或读取游标。组件／集成通过可以确认适配完成，真实模型识图结论留到阶段 4。

### 阶段 3：客户端完整交互

完成第 3 节的桌面／移动端共用流程、可持续添加图片的「+」、本地预览与 CSP、纯图片和文字多图发送、消息预览、摘要及草稿恢复。阶段内先打通选择文件 → 上传 → 发送 → 预览，再在同一 addFiles 流程接入粘贴，最后补齐切换、刷新和失败重试；这些都是本阶段必须完成的内容。

交付标准：前端逻辑和浏览器测试覆盖第 3 节的正常及异常行为，桌面与窄屏布局均可操作，工作目录与原文字发送回归通过。浏览器测试可以使用现有模拟服务，但报告必须标注服务类型；窄屏模拟不代表真机选图和粘贴能力已验收。

此阶段同时补充简明用户说明，明确客户端图片来源、手机粘贴的能力差异和首版格式／大小限制。

### 阶段 4：完整链路与真实验收

复用前三阶段实现及测试，不再新增产品范围。使用真实 TeamX 后端及隔离 Room 验证：

1. 桌面浏览器粘贴和选择图片，经真实上传、发送、刷新／服务重启后仍可预览；发送回执不确定时重试不重复。
2. 手机访问另一台主机运行的 TeamX，记录真实 iOS Safari、Android Chrome 的选择、取消、分次追加和返回页面行为。分别记录图片粘贴可用性；粘贴不可用时，选图路径必须完成同一功能。
3. 支持图片的真实 DSH／模型通过原 inbox_read 识别刚发送的测试图，消费后通过原 history read 回看；核对实际调用和图片块，不接受仅从提示词或文件名推断的识图结果。
4. 验证真实读取与清空／取消的保护关系、已发布引用保留及过期孤儿回收；再次确认相关文字消息和平台图片路径无回归。

交付标准：第 9 节矩阵所需证据齐全，记录测试环境、后端类型、模型、浏览器／设备及未验证项。缺少真机或真实模型环境时，保留具体未完成项，不能用窄屏模拟、组件成功或另一路径的成功替代。阶段 4 是本方案完成条件，不能在前三阶段结束后默认省略。

真实验收使用独立测试 Room 和无敏感内容图片；需要执行时再按届时授权和环境实施。组件通过、模拟浏览器通过、真实浏览器通过、真实模型通过分别记载，缺失任一必要证据不得写成全部完成。

最终用户路径应当是：粘贴／选择 → 看见待发送图 → 发送一条消息 → 人能预览 → Agent 用已有读取能力理解；整个过程不要求用户或 Agent 管理附件路径、额外授权或额外下载步骤。
