# 多房间独立运行方案

状态：第 1–4 步代码及文档已实施；组件、HTTP、前端、真实 DSH 双房间并行／恢复／退出验证已通过。真实浏览器切房及双标签页验收仍受工具来源权限门禁阻断，完整验收尚未交付。证据与剩余边界见[多房间验证边界](../internal/room/README.zh.md#当前待验项)。

## 目标与范围

切换房间只切换查看对象，原房间的 Agent 回合、工具、通知投递和后续协作继续运行。不同房间可以并行；每个房间内部仍沿用现有单执行名额、成员启用状态和回合预算。

暂停或取消成员、轮换 Session、重新开始讨论、应用 Workspace、删除房间和服务退出，才按各自语义影响执行。查看房间不自动启用已暂停成员，也不重试失败或中断回合。

本次不扩展同房间成员并行，不增加自动回合重试、跨房间协作或全局执行配额。

## 实施前绑定点

| 位置 | 当前行为 | 改造方向 |
| --- | --- | --- |
| `internal/room/management.go` | 单一 `active *service`，普通请求全部转发给它 | 按 Room 身份管理和路由多个运行实例 |
| `internal/room/activation.go` | 激活时取消全部工具、关闭旧房间；恢复和退出只处理一个房间 | 打开目标房间，不停止其他房间；逐房间恢复与结清 |
| `internal/room/tools.go` | 成员工具鉴权依赖 `m.active` 和全局 `busy` | 校验调用所属实例及该房间状态 |
| `internal/room/platform_notifications.go` | 仅活动房间可直接接收入房投递 | 向订阅所属且可接收的实例投递 |
| `internal/room/workspace_management.go`、`deletion.go` | 生命周期操作依赖唯一活动实例和全局操作槽 | 操作只占用、停止和重建目标房间 |
| `internal/room/web/app.js` | 查看对象跟随服务级 `active_room_id` | 每个标签页独立保存查看对象 |

因此不能仅删除切房时的 `old.close()`，否则后台房间的请求和工具仍会被拒绝或路由错误。

## 核心设计

### 1. 分离界面选择与运行实例

- 管理器使用 `runtimes map[RoomIdentity]*roomRuntime`；每项拥有 `service`、生命周期状态和操作完成信号。Room 内的 Actor、调度器、Store、DSH Session 与 Workspace 继续独立。
- 浏览器按标签页保存 `selectedRoom`，建议使用 `sessionStorage`。目录轮询不强制其他标签页跟随选择；运行实例不持有“当前查看房间”语义。
- 初次进入房间调用幂等的打开操作：已有健康实例直接返回其 `ServiceInfo`；尚未打开则检查并组装目标房间。打开失败只影响目标，当前页面及其他房间继续工作。
- 已打开房间在切走后继续驻留；DSH 仍按成员需要懒创建。首版不做空闲自动卸载，也不因再次查看改变实例 epoch。

### 2. 所有请求按所属房间路由

- Room API 根据请求中的 `RoomID + RoomInstance` 查找实例，再由实例校验 `ServiceEpoch`、Caller 和 Membership；覆盖 GET 查询、POST、工具流及 Workspace 凭据入口。
- 不给旧请求改写身份，不把找不到实例的请求转发到正在查看的房间。普通请求不隐式启动替代实例；打开操作是独立入口。
- 成员工具、通知投递、重启讨论和 Workspace 操作均使用同一实例查找规则。通知是否可投递取决于所属实例能否接收，与页面是否选中无关；未打开房间仍可采集并保留待投递通知。

### 3. 生命周期按房间隔离

- 同一房间的打开、删除、Workspace 应用、重新开始等冲突操作串行；每个房间有独立的 `busy / operationDone`，不同房间可以同时操作。
- 根目录索引写入仍在短临界区内串行；网络、进程等待和长操作不持有全局锁。全服务退出、索引提交结果不确定仍可阻止全局变更。
- 删除、重建和工具取消按完整 Room 身份限定范围。连接凭据轮换等共享资源变更仍影响实际引用该连接的调用，不能简单缩小成当前房间。
- 注册实例前预留该房间的打开操作，避免重复组装；只有 worker、工具、Session 和 Store 均结清后才能移除实例并允许重新打开。清理失败保留归属和诊断，只阻断该房间。

### 4. 持久化、恢复与退出

- 用多房间运行归属记录替代单一 `owned_room_id`，在组装及启动外部执行前持久记录归属。界面选择不作为恢复执行的依据。
- 启动时逐房间核查运行归属、未完成操作及成员协作状态：正常停止且原本启用的成员可按既有规则恢复调度；异常、中断或结清证据不足的执行保持阻断，禁止自动重放。
- 已启用成员的房间应能在无人查看时恢复运行；没有启用成员且无需恢复处理的房间按需打开。一个房间恢复失败不妨碍其他健康房间启动。
- 退出时先冻结所有房间的新执行，再对全部实例发起停止并在统一期限内汇总结清结果；一个失败不跳过其他实例。未结清资源继续保留归属，不提前释放根目录锁。
- 明确升级索引格式：旧 `active_room_id` 仅可作为首次查看的默认值，旧 `owned_room_id` 转为单项归属。迁移不推断其他房间已正常关闭，也不清除历史操作、预算和中断证据。

### 5. 接口与 UI

- 建议将 `/v1/rooms/activate` 收敛为 `/v1/rooms/open`，保留操作 ID 去重及结果查询；打开不承担停止其他房间或设置全局选择的职责。
- `/v1/rooms` 返回每个房间的运行状态和可用 `ServiceInfo`，区分目录状态、运行状态与页面选择；生命周期进度和错误按房间展示。
- 创建成功后的 UI 仍可打开并进入新房间；重复打开同一房间不重复恢复成员或消费预算。
- 保留按房间隔离的草稿、引用和未确认发送，以及迟到响应检查；多标签页可分别查看 A、B，后台更新不覆盖当前页面。
- 实施完成后同步更新现有概念、架构、运行手册和 roadmap 中的单活动房间说明，并移除旧的唯一活动实例路径。

## 建议实施顺序

1. **实例与路由**：定义运行实例表、房间操作槽、打开接口及索引迁移；先覆盖重复打开、身份拒绝和两个实例的 API 路由。
2. **执行与平台链路**：迁移工具、通知、凭据、Workspace、讨论重启和删除的归属判断；取消切房关闭逻辑，验证 A 执行时打开 B 不影响 A。
3. **恢复与退出**：实现多房间恢复、归属保留和全部实例结清，验证故障只阻断所属房间。
4. **界面与验收**：改为标签页选择，清理旧接口及单活动假设，更新文档，完成下列验收。

以上是同一改造的内部步骤；仅替换实例表或取消 `close` 不算交付完成。

### 第 1 步交付边界

- 新增 `runtimes map[RoomIdentity]*roomRuntime`，打开操作按房间预留 `busy / operationDone`；组装不持有目录锁，不同房间可以同时打开。相同 `open_id` 返回原回执，失败后须使用新 ID；同房间另一打开操作进行中返回 `busy`。重复打开健康实例返回相同 epoch。
- `POST /v1/rooms/open` 请求包含管理器 `service_epoch`、human `caller`、`room_id`、`room_instance`、`open_id`；返回 `running / completed / failed` 回执，完成时携带 `service`。`GET /v1/rooms/open?service_epoch=…&caller_id=…&open_id=…` 查询结果，不重放操作。
- 普通 Room POST 按请求中的完整 `ServiceInfo` 路由，再由实例校验 Caller 与 Membership。`GET /v1/info` 须携带 `room_id`、`room_instance`、实例 `service_epoch`、`caller_id` 查询参数；无身份请求被拒绝。人类 CLI 在管理模式下须显式指定已打开的 `--room`，从目录取得实例身份；查询不会隐式打开房间。
- `/v1/rooms` 的每项新增 `runtime_status`（`closed / opening / ready / failed`）、可用 `service` 和 `runtime_error`；目录状态仍由原 `status` 表示。打开不设置 `active_room_id`。
- `rooms.json` 升为版本 2，新增完整身份的 `owned_rooms` 和 `opens` 回执。版本 1 的 `owned_room_id` 转入归属集合，`active_room_id` 不推断归属；旧激活路径暂保留兼容字段并同步记录归属。未完成打开在重启后标记失败，保留归属，不自动重放。
- 打开只组装与挂接成员，不自动恢复调度或消费预算。旧 `/activate`、工具、通知、凭据及生命周期执行器在后续步骤迁移；旧激活不能跨入新实例，新打开实例的删除、Workspace 应用与讨论重启暂返回 `busy`。现有 UI 仍走旧激活流程。
- 退出会等待打开操作并关闭已注册实例，防止本步新增资源泄漏；多房间恢复、统一冻结和完整故障结清仍属第 3 步。真实 DSH 并行、切房与双标签页验收仍待后续步骤完成。
- 本步验证通过：`go test ./...`、`go vet ./...`，以及 `go test -race ./internal/room -run 'TestRuntime|TestManaged|TestRoomManager|TestWorkspace.*(Apply|Retry)' -count=1`。新增组件测试覆盖重复/并发打开、双实例 GET/POST 路由、身份拒绝、失败隔离、版本迁移、提交结果未知和退出时保留操作归属；既有 UI HTTP 测试通过，不代表真实 DSH 或人工浏览器验收。

### 第 2 步交付边界

- 成员工具、工具流、实时成员名册和 Workspace 私有凭据入口统一按完整 Room 身份查找实例，再核对实例 epoch 与 Membership。切走后的原实例仍接受所属成员的调用；错误实例、epoch 或 Membership 不会改写或转发到所查看房间。工具绑定修改也只受所属房间的操作槽约束。
- Events／To-Do 通知按订阅所属实例投递；已打开的后台房间仍采用可接收实例的轮询语义。未打开房间继续采集并保留待投递通知；目标房间正在重建、删除或重启讨论时暂缓投递，不影响其他房间。订阅配置与同步检查改为所属房间的操作槽。
- 新实例首次打开后按既有规则恢复成员启用意图；暂停、失败、中断、预算耗尽及后端阻断仍由原恢复检查处理。重复打开或选择健康实例直接复用，不再次恢复调度、不更换 epoch／Session、不重置预算。旧 `/activate` 暂作为现有 UI 的选择入口，共用打开执行器，不再取消工具或关闭其他房间；并发激活各自保存回执，迟到完成不覆盖较新的选择。
- Workspace 应用／重试、讨论重启和删除使用目标房间的 `busy / operationDone`。停止调度、结清工具／通知／Session、配置准备和服务重建的等待均在目录锁外执行；同房间冲突操作被拒绝，其他房间仍可打开、执行或进行生命周期操作。删除及重建只更新所属实例；清理失败保留所属实例及错误，阻止同房间绕过清理重新组装。
- 讨论重启在成员暂停后结清所属工具，再轮换 Session；Workspace 与删除也显式取消并等待所属工具。共享连接轮换继续按连接引用结清所有相关房间的调用，不缩小为当前查看房间。
- 新增组件测试覆盖 A 长回合中打开并选择 B、两房间各自执行、后台 Agent 消息及工具调用、重复选择保留实例／Session、后台通知及凭据、工具结清范围、共享连接轮换、跨房间生命周期并行及并发激活回执。现有单活动假设测试已更新，同房间冲突与身份拒绝检查保留。
- 本步验证通过：`go test ./... -count=1 -timeout=10m`、`go vet ./...`、覆盖 `TestRuntime`、`TestManaged`、Workspace 应用／重试和工具生命周期的定向竞态检查，以及最终修改后的并发激活、生命周期隔离和 Workspace 应用入口补充竞态检查。现有应用入口与 HTTP handler 回归通过；DSH／模型组件使用受控替身，工具结清测试使用本机进程。
- 第 2 步结束时仍保留旧 UI 选择字段与单房间启动恢复入口；多房间启动恢复、统一冻结和全部实例故障结清由第 3 步实施。第 4 步仍负责标签页选择、旧接口清理、全量概念文档同步，以及真实 DSH 并行／退出和人工浏览器切房／双标签页验收。组件测试和现有 UI HTTP 测试不代表这些真实验收已完成。

### 第 3 步交付边界

- 启动入口改为 `restoreRuntimes`，按目录中的完整 Room 身份预留操作槽，独立检查成员名册、`collaboration.json`、回合和 Session 证据。已启用成员的房间无需被页面选中即可恢复；未执行且没有启用意图的房间、已全部暂停且已结清的房间保持按需打开。恢复过程中同房间不能重复组装，不同房间的慢检查或组装失败不互相等待；错误保留在所属房间的 `runtime_error`。
- 恢复继续沿用既有启用意图、预算和 DSH 安全检查：暂停、失败、中断、预算耗尽或后端证据不足的成员不会自动执行，持久化的 `running` 回合转为 `interrupted`。查看已恢复实例仍复用 epoch 和 Session，不重复恢复成员或更新预算。
- 未完成的打开、激活、Workspace 应用和删除保留原回执及归属，不自动重放，只阻断所属房间。新旧打开入口的回执增加共同递增的 `sequence`，使后来的显式成功重试可取代旧失败的恢复阻断；历史回执仍保留。旧回执没有顺序信息时保守检查，不根据界面选择推断执行归属。
- `owned_rooms` 是完整身份的运行归属；版本 1 及过渡版本 2 中的 `owned_room_id` 在写入迁移时并入集合并移除。`active_room_id` 仅保留为旧 UI 的默认查看对象。索引新增按房间记录的 `shutdowns`，保存实际结清结果与错误；新组装前先持久保留归属并移除上次结清回执。未组装房间不产生推断性的正常停止记录，历史操作、预算和中断证据不会被迁移清除。
- 退出先关闭全管理器接纳入口，并通过所有实例共享到调度器和成员的冻结标记阻止新的执行与排队交接；再并行停止各房间的服务、工具和通知查询，同时取消已接纳的房间操作上下文（包括 Workspace 准备任务），并等待打开与生命周期 worker。全部等待使用同一退出期限，一个失败不跳过其他实例。退出期间才完成组装的实例不能恢复调度，Workspace 重建也不能发布可执行的替代实例。
- 结清错误按完整 Room 身份汇总并写入归属回执。即使其他服务已释放各自 Store，只要仍有工具、查询、worker 或服务未结清，根目录锁仍保留；后续可再次等待结清。无法确认索引提交结果时保留原磁盘证据，不伪造成功回执。上次退出的失败回执阻止所属房间自动恢复，其他健康房间仍可恢复；根索引结构或跨文件一致性校验失败仍按既有全局保护处理。
- 组件测试覆盖无人查看的双房间重启恢复、暂停与预算保留、未启用房间懒打开、慢恢复和失败隔离、异常回合及损坏协作状态、未完成操作不重放、跨入口显式重试、成员／工具／通知查询超时仍结清其他实例，以及未完成打开退出时保留根锁和归属。受控 DSH／模型组件和 HTTP handler 测试不代表真实 DSH 或浏览器验收。
- 本步验证通过：最终版本 `go test ./... -count=1 -timeout=10m`、`go vet ./...`；覆盖 `TestRuntime`、`TestManaged`、Workspace 应用／重试和服务退出的定向竞态检查；操作取消上下文接入后的退出、Workspace、通知及跨入口重试恢复补充竞态检查。`go test -tags=e2e ./internal/room -run '^$'` 仅验证真实验收入口可编译，未执行真实 DSH、GitLab 或浏览器验收。
- 第 4 步仍负责标签页选择、旧接口与单活动 UI 假设清理、全量概念文档同步，以及真实 DSH 双房间并行／退出和人工浏览器切房／双标签页验收。

### 第 4 步交付边界

- 页面以 `sessionStorage` 保存完整房间身份，各标签页独立选择；轮询只更新所选房间的实例观察。选择健康实例直接复用，切走、关闭页面及其他标签页的选择不改变执行；旧索引选择仅作为初次查看建议。
- 创建后衔接 `/v1/rooms/open`；打开使用稳定 `open_id`，丢失响应和刷新只查询原回执，不自动重发。重复点击不产生第二个操作；用户已选其他房间时，迟到完成及刷新后回执不覆盖较新的选择。草稿、引用、未确认发送、Workspace 与成员活动保持房间隔离。
- 目录每项提供独立 `busy`、安全成员名称、运行状态及错误，页面按所属房间限制变更。顶层 `active`、`active_room_id`、`activation`、`members` 和旧 `/activate` 入口已移除，管理器不再持有唯一活动实例。后续按用户选择重建，历史激活回执、旧选择／归属字段及迁移已删除；当前索引只支持 v3，查看选择保存在浏览器。
- 人类 CLI 支持显式 `--room` 及原 ROOM 位置参数，管理模式查询不会打开实例。现有 HTTP／handler 验收入口迁移到每项 `service`，概念、架构、运行手册、Agent runtime 和 roadmap 已同步。
- 自动验证及真实 DSH 结果分别见[多房间验证边界](../internal/room/README.zh.md#当前待验项)。真实验收覆盖双房间工具同时执行、后台公共发言、原 Session／预算保留、后续输入调度、无人查看的双房间重启恢复、运行工具时退出并结清全部房间，以及中断回合重启后不重放。
- 浏览器工具在读取页面之前仍拒绝该来源，返回已保存权限或托管策略阻断；用户已设置默认始终允许并添加精确来源例外，重置工具会话后错误仍存在。未取得页面、切房或双标签页浏览器证据，不能把 DOM／HTTP 测试当作真实浏览器验收。

## 验收条件

- A 长回合中切到 B，B 可执行；A 持续接收工具结果、发送公共消息并正常结束，之后仍按未读通知调度，未新增取消错误或重复执行。
- A、B 可以同时各执行一个回合；同一 Room 内仍最多一个执行者。A → B → A 不重建 A 的健康实例或 Session，不重置成员状态和预算。
- 后台房间的 CLI、工具、凭据和通知投递均命中原房间；错误 RoomInstance、epoch 或 Membership 被拒绝，迟到响应不能污染当前页面。
- A 的 Workspace 应用、讨论重启、取消、删除或恢复失败不停止 B；并发重复打开及打开/删除竞争不产生第二个实例或遗留未记录的进程。
- 两个标签页可分别停留在 A、B；草稿、发送回执及成员活动保持隔离，关闭标签页不取消执行。
- 正常重启可恢复多个房间的既有协作意图；异常退出不重放中断回合。服务退出确实结清全部房间，失败证据和资源归属可查。
- 分别提供组件/竞态测试、真实 DSH 双房间并行与退出记录、浏览器切房及双标签页证据；模拟测试通过不代替真实运行验收。
