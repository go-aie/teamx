## 1. 当前目标与范围

第二阶段集中解决三件事：已有平台／工具有明确的扩展入口；所选扩展代码与资源可以按需编译交付；现有 DSH 经收敛的后端合同运行，为后续同样基于 ACP 的 Codex 接入留下边界。

与 Space 联合实施时，优先交付显式装配和选定服务的生命周期，为个人／多用户提供可组合实现；完整选择性构建及资源裁剪仍是本方案的后续独立目标。User／Space／Room、授权、目录与业务存储共享同一内核，不为个人／多用户各写一套插件化业务模型。

| 事项 | 本阶段工作 | 完成条件 |
| --- | --- | --- |
| 扩展入口 | 纯工厂、必要公开合同、显式 Compose；已有平台／工具拆成可选包 | 正常默认入口接入，最小外部 Go 扩展能参与装配 |
| Gordis 装配 | 对选定服务使用进程内 Plugin，负责启动、Ready 和关闭排空 | 默认启动／关闭和失败清理形成闭环，无新增动态热替换入口 |
| 按需编译 | 复用 Gordis Build，生成入口、检查选择、交付必要资源 | 默认完整组合与代表性裁剪组合实际构建、检查并运行 |
| Agent 准备 | 用 DSH 验证工厂、ACP 能力与生命周期边界 | 不新增 Codex runner、配置、进程或入口；DSH 行为保持 |
| 存储 | 复用现有本地文件存储 | JSON 快照／JSONL 正文、路径、格式、owner 和恢复语义保持 |

本阶段不做存储插件化、公共存储 Provider／Lease、数据库或数据迁移，不做跨进程插件、RPC、运行时安装／卸载／热替换、插件市场或新 Profile 配置体系。现有 DSH 和工具运行子进程的方式继续保留，它们不是本阶段要实现的通用进程插件机制。

Gmail 等新平台可在扩展入口稳定后另选任务。本阶段不以真实 Gmail 账号或真实 Codex 接入为完成条件，也不以未来功能代替现有调用验证。

## 2. 两阶段关系与成本控制

第一阶段在现有功能和数据上形成领域、应用、传输及持久设施的真实包边界；本方案增加可选实现装配和构建交付。与 Space 的实施顺序统一后，按真实消费者穿插推进，避免先按全局单所有者完成全部插件化，再重做空间作用域；也避免多 Space 先复制初始化路径，之后再拆一次。领域状态机、存储和运行协议继续保持各自 owner，不一次全面改写。

当前采用按分支交接：P0 分别核对平台与 Agent 切片的调用、恢复、撤权和关闭链。未迁移的 Room／Inbox／Member／配置 owner 可以继续提供已验证的命令／查询适配，但其访问、锁和结清责任必须明确；若还需跨包直接改字段、转移第二个 owner 或重做持久证明，先限定并完成相应 R 准备单元。暂缓 R1b、R2、R4、R5b.2 或 R7／R8 不自动阻断，也不自动放行。此安排只改变所选切片的进入方式，不把第一阶段整体标为完成，不提前抽象全部文件存储。

P0、P1a、P1b、P2n、P2t 和 P4a 已完成，不重复实施。S1 先形成个人默认部署组合，使用普通 Go 工厂及明确依赖；S2 复用原 manager 生命周期完成多空间，不要求先引入 Gordis。独立 P3 优先评估持有真实 worker、取消及排空责任的通知运行服务，复用 notification.Manager 和 P2n；只有薄适配能保持原关闭协议及唯一 owner 时才实施，不以纯描述 Bind 充当资源服务。若需重写核心关闭或转移多个持久 owner，暂缓 P3，保留可交付 S2。完整 P2r／P5 及 P4b 按实际需求独立推进。

当前主要成本是隔离 Provider 的传递依赖、公开外部扩展实际需要的类型、处理裁剪后的配置与历史 codec 依赖。多存储一致性、通用 RPC 和第二后端真实接入已移出，不再为这些目标建立空接口或预备实现。

收益以新扩展少改公共代码、所选实现可独立验证、未选择实现不进入相应依赖与资源闭包衡量。Gordis 只接管确有需要的服务生命周期；领域 Actor、Repository 和每个业务对象不机械包装成插件。

## 4. 装配关系与运行责任

| 层次 | 内容 | 权威 |
| --- | --- | --- |
| 构建选择 | 工厂包、版本、工具与资源 | 配方／生成入口 |
| 静态能力目录 | Provider、来源、工具、codec 和配置描述 | 所选工厂与 Compose |
| 部署组合 | 身份来源、目录访问、原生／隔离执行、Computer 环境取得及资源策略参数 | 启动装配层；个人原生 DSH 无 SRT 前置，S3／S4 补轻量共享托管实现，精细硬配额后置 |
| 进程内服务 | 所选能力的启动、Ready、资源和关闭 | TeamX 装配与受限 Gordis 生命周期 |
| 业务对象 | Platform 连接、订阅、Room、Member、Session、Grant | 现有领域 owner 与持久合同 |

一个 Plugin 类型不等于一个账号，一个实例也不必等于一个 Room 或 Member。优先在平台实现服务等明确资源边界接入；订阅、成员执行和存储 owner 继续由原应用服务管理。服务设置和成员 Runner 配置仍是选择／绑定事实，不另维护一份 Profile。

先对静态选择好的进程内服务使用依赖、Ready 和清理能力，不开放插件重启、安装或热切换。已有业务启停继续走原命令，不等同于卸载实现。

启动失败清理已获取资源；关闭时封闭新准入，按既有合同取消或等待已受理工作，排空后再关闭底层资源。Scope 资源责任与领域提交、工具结果、后端持久接收证明分开，不能以框架停止替代业务结清。实际跨调用持有贡献时才使用 generation 租约，不给纯查询机械增加租约。

Plugin generation、RoomInstance、MembershipID、Platform Generation、Session generation 和 Grant 保持不同含义。应用服务接收必要的类型化合同，不接收全能 Host／Scope 或通用 service locator；不建立第二套业务 owner。

Space runtime epoch 也独立保留。插件类型及纯描述可以共享，连接、凭据上下文、通知运行资源、Computer 客户端及未完成操作按空间装配；同一个类型不意味着所有空间共用可变单例。S2 先用原生命周期验证空间独立，Host／实例布局到独立 P3 实施时再按真实资源范围验证；未实施时不创建预备 Host。Space 的创建／归档按业务生命周期实例化或停止所选服务，不开放运行中安装、任意插件重启或热替换入口。

SpaceRuntime 直接拥有一份现有 roomManager，后者继续管理 Room 集合及业务关闭协调；通知 Manager 等专项对象保留自己的 worker／排空责任。不再新增一层 manager 镜像 Room、Session 或未完成操作，不将整个 roomManager／Store 塞进插件，也不以插件逆序清理替代核心并行关闭协议。

个人与多用户的实现选择集中在启动层，业务调用只接收必要身份、SpaceContext 和窄能力。用户数上限、额度等优先做类型化参数；注册／Ready 不赋予空间访问权，个人入口也执行共用 owner 检查。多用户必需认证／隔离实现缺失时明确失败，不允许通过空插件或回退个人实现获得表面可用。Gordis Scope 的可见性不代替 User／Space 授权或 OS 文件隔离。

认证、用户管理和资源授权分别组合。认证模块的首次消费者、CSGClaw 源码参考及托管验证边界见[空间方案第 9.1 节](WORKSPACE-AND-MULTI-USER-ANALYSIS-PLAN.zh.md#91-在统一用户模型上开放多账号登录与管理)：OpenCSG 实现只处理登录协议并输出受验证外部身份，本地 User 映射、会话、auth version、准入与撤权结清仍由共用宿主负责。完整用户管理界面通过同一命令操作本地用户状态，可配内置或第三方认证；认证提供商不能直接授予 Space 或部署管理权限。Room／Inbox／History／Agent 不判断提供商，不因替换认证而改其核心协议。

未来 Gordis 认证插件贡献实际认证工厂及必要资源，认证类型不强塞进平台通知／工具的 Provider 描述。静态注册与工厂校验零远端访问，真实登录时才使用配置固定的端点；实例与 Scope 仅管理实际持有的资源，不为了套用通知服务 P3 创建空 worker。宿主拥有登录尝试、身份绑定和会话持久状态，插件 generation 不替代用户 auth version。切换提供商按受控配置／身份绑定流程处理，不开放运行时热替换；未完成 Gordis 接入前不预建公共认证 API 或通用 Host。

个人／托管差异按能力合同组合，不各自包装整套业务插件。模块与策略的对照见[空间方案第 5.5 节](WORKSPACE-AND-MULTI-USER-ANALYSIS-PLAN.zh.md#55-部署组合与按空间实例化)：认证来源、用户初始化／准入策略、GitLab 应用目录与 OAuth 交换能力、应用管理入口及执行环境分别选择。先用普通 Go 工厂满足真实消费者，后续 Gordis 薄适配只贡献相应工厂／能力和实际资源；额度或初始化规则可保持类型化策略，不制造空插件或通用服务定位器。

DSH 后端与执行环境分开：复用已有 `agent.Factory`／`Host` 及 ACP／Session 协议，S3b.1 在实际接点形成原生执行、SRT 执行的最小合同。个人默认原生 DSH，不检查或启动 SRT；多用户 Linux 选择经 S3 验收的 SRT，实现缺失或隔离不可用时拒绝，不回落个人路径。启动、运行检查、恢复、轮换和模型验证使用同一选择；执行模块持有进程／代理等实际资源，原 Session、Store 锁、输入消费与结果确认仍由原 owner 负责，不复制两套 DSH 后端或仅改启动命令。

后续 Gordis 执行插件只贡献工厂和实际资源生命周期，不把 Session 变为插件实例，插件 generation 不替代 DSH 本体、执行策略或 Session generation。复用 S3a.1 独立机制证据，在 S3b.1 的 Go 模块实际接入中闭合 DSH 兼容，不预建通用框架或等待 P3／完整 P4b。S3b.2a 只闭合首发工具、未选入口禁用及基础保护；S3b.2b 托管 Git 代执行独立后置，不能通过调用个人实现绕过。基础额度／超时保持类型化策略，精细硬配额后置，不制造空资源插件或弱化数据／执行隔离。

GitLab 的个人实现读取所属空间私有应用，托管实现读取控制面应用目录并经受限服务交换／刷新；公共编排固定 User／Space／应用版本与操作 ID，所属空间原 owner 校验并提交 grant。共同合同返回应用引用和公开元数据，托管 Secret 不返回空间或 Agent。应用管理权限由所选能力提供，个人自建／导入、授权与刷新路径定向回归；未选托管 GitLab 的组合不开放该入口，不借个人配置兜底。替换模块不要求改 Inbox／History／Agent／Room 核心协议，注册或 Scope 也不代替授权／结清。

GitLab 应用／纯 API（S4b）、核心代执行 Git 仓库操作（S3b.2b）与已验收沙盒内 Git 分别声明。S4b 不自动注册托管 clone／fetch／push 等能力；S3b.2a 按所选目录／能力策略关闭多用户的 UI、直接 API／CLI、自动仓库准备与工具转调路径，基本文件操作和个人原 Git 保留。S3b.2b 后续经真实正常入口适配与对应 S5 验收后才启用，授权、凭据租约和 unknown／结果 owner 继续共用；未来可作独立 Git 执行能力贡献，不复制平台账号或业务状态。

后续 S4c.2 作为独立迁移命令模块按需装配，未来可贡献 Gordis 命令入口，不创建常驻迁移服务，也不为首发预建迁移框架。命令仍调用原唯一 owner 的停用、结清、登记与恢复合同；它的可选交付不削弱普通版本升级和备份恢复。S4c.1 永久删除与 S4d 用户管理分别保留自己的状态责任，不并入认证插件。

## 5. 扩展目录与作者入口

```text
  platforms/lark/

```

不新增公开 `storage/` 或 `builtin/storage/`。输入／身份值类型仅在外部平台扩展实际需要时公开，不为未来 Codex 或存储预迁全部类型，不建立公共 `common/types`。

可选工厂包已导出 `func Extension() extension.Extension`；外部本地工具使用公开 `platform.Tool` 声明。`extension.Compose` 与 `boot.Run` 已接入普通入口，`teamx extensions check` 提供零资源静态检查。工厂不读取凭据、不启动 Host、Actor、连接或子进程；Compose 检查标识、能力、schema 与冲突，启动阶段才获取资源。

当前公开 Composition 主要承载平台、工具和通知贡献，不是已完成的部署组合或 Gordis 运行容器。S1 提取现有个人启动真实需要的内部合同，身份／目录／执行实现不强塞进平台 Provider 描述，也不提前公开整套用户管理 API。S2 沿用明确的原生命周期，选定资源到独立 P3 才经集成适配接入 Gordis；领域代码不反向依赖 Gordis，纯 Compose 仍不获取资源。第一批无需创建 buildconfig、插件市场或第二份全能 registry。

默认 `cmd/teamx` 显式组合现有标准能力，自定义生成 main 组合所选工厂。`boot` 和通用服务不隐式导入标准全集。外部生成 main 不能导入 TeamX 的 `internal/app`，因此公开启动入口和注册描述必须一起接入；具体实现仍可复用本 module 的内部组件。

P1a 已将通用目录／解析留在 `internal/app/platforms`，内置汇总移至 `builtin/platforms`；通用 `SourceBindings` 已删除。P1b 公开子包的 `Extension()`，完整描述和专用查询绑定封装于 `internal/app/builtinplatforms`，不向作者暴露通知、图片或动作内部类型。受管、单 Room／Store、离线投影与升级传递同一外层选择，普通入口仍显式选择完整组合；最小外部本地工具已通过公开入口发现与执行。Room 和实际产品仍包含具体 Provider 依赖，尚未完成产品裁剪。

当前默认能力还包含已开放的飞书本人／指定群图文发送及 GitLab 图文评论／讨论回复。P1a 的工厂迁移应保持现有联合 schema、可选图片能力与通知投影，不按早期纯文字装配恢复旧定义；静态能力声明、运行权限观察和实际动作实现仍是三层不同事实。

## 6. 平台可选装配与保存内容

第一阶段 R3b 静态描述继续作为唯一来源。本阶段把 Provider 专用工厂、来源／工具和必要应用适配隔离为可选包，公共合同不自行枚举全部内置 Provider。

工厂分别声明连接、来源、codec、工具、引用／动作和配置／展示入口，不要求每个 Provider 实现全部能力。注册不提供账号访问权；真实调用继续核验 PlatformID、成员绑定、授权、凭据代际与精确目标。

配置、诊断、展示也须有可发现入口，不能只抽采集器，却要求新增平台时修改多个通用 handler。优先复用既有 schema、操作和视图适配，不在本阶段建立能自动呈现任意 OAuth 的 UI 系统。后端与专用前端的支持范围分别报告。

P1b 已用最小外部本地工具验证公开装配与执行，见[实施与证据](implementation/architecture/extension-assembly.zh.md)；P2n／P2t 已接通已有飞书通知／工具的完整运行适配，见各自实施记录；P2r 最后处理该 Provider 的剩余依赖。外部通知作者合同在 P2n 按实际需要验证，不用内部来源绑定测试代替外部可实现性检查。测试扩展不需要真实账号和远端业务写入。Gmail 等产品任务后续再验收账号、订阅、可靠投递、History 与展示。

停止采集、撤回工具和移除历史 codec 分开处理。当前 Repository 遇到已有分区缺少 codec 会拒绝打开，本阶段保留该保护并提供明确的启动前依赖检查，不能跳过分区、删除正文或重置消费。

确需分别裁剪时，把纯本地 codec／历史投影放在独立工厂，可保留历史读取而不选择采集／工具；若同包仍引用全部实现，就不能宣称依赖已裁掉。保存正文读取继续不依赖远端在线，不增加运行中卸载 codec 或未知来源预览的新协议。

## 7. 多 Agent 准备：以 DSH 验证 ACP 边界

后续 Codex 按用户明确的 ACP 路线单独接入。本阶段只准备后端构造与能力入口，不新增 Codex runner、配置、进程或业务入口，不修改 DSH 持久格式，不支持运行中切换后端。

| 准备面 | 本阶段工作 | 后续 Codex 任务 |
| --- | --- | --- |
| 工厂与选择 | DSH 经明确工厂构造，仍仅接受当前 DSH 配置 | 注册 Codex，接入其进程、配置与核验 |
| ACP 基础 | 区分通信／初始化／能力与 DSH 特有行为，记录复用点 | 核对实际 ACP 能力、错误与通知差异 |
| 私有状态 | DSH 状态解释集中于适配，成员算法经必要合同使用 | Codex 自有引用、恢复、关闭与轮换 |
| 执行与证明 | 保留取消、结清、图片和正式输入持久接收行为 | 验证实际接收证据和恢复，不以同用 ACP 代替验收 |
| 模型与观察 | DSH 模型验证、活动投影集中于适配 | 按真实能力实现支持项，不强求参数全集相同 |

已有 ACP 组件的全部行为并非都属于 ACP 通用保证。TeamX 输入桥接、持久摘要匹配和部分会话扩展仍须按实际实现验证；成功返回 ACP 响应或 MCP 结果不能单独确认消费。

只按 DSH 的真实调用提取最小工厂、生命周期和能力合同，不预建通用多后端框架。没有第二个真实消费者时，不要求把 `agent/dsh` 整体改名为 ACP 内核或复制一套通信；必要共用通信提取可在 Codex 任务确定后完成。

沿现有 DSH 执行、取消、恢复、轮换、观察和关闭路径验收。成果称为后端／ACP 边界已准备，不能称已支持 Codex 或已完成双后端兼容。

R5b.1 已在原 Room 包接通私有生命周期合同；P4a 承接真实工厂与跨包调用边界，P4b 补齐能力归属和实际后端验收，不重做已经稳定的状态机。`storedSessionBackend` 与正常成员构造必须来自同一所选工厂，关闭 Room、恢复及模型应用不能旁路硬编码回 DSH。只迁实际需要的值类型和能力，保留当前只接受 DSH 的配置与持久字段。完整成员状态机搬迁 R5b.2 不是本分支的自动前置；合同不足时先完成明确的依赖收敛。

P4 交付后端扩展边界，不自动表示 DSH 已由 Gordis 管理。若后续采用 Gordis 管理 DSH 实现服务，复用 P3 的完整生命周期验收方式另列切片；Member／Session 的业务 owner 与持久接收证明仍由原实现负责，不能把每个 Session 机械转换为插件实例。

## 8. 按需编译与交付

空间主线的 [S5.0 打包与安装接入](WORKSPACE-AND-MULTI-USER-ANALYSIS-PLAN.zh.md#s50-实施单先交付可验收的安装包)先扩展既有 standard 归档、SRT 固定依赖及安装校验，复用已有 Node；辅助程序随包／宿主前置和实际路径在该单元闭合。个人原生 DSH 不因包中包含 SRT 而承担其运行前置。此项不要求本节 Gordis Build／生成 main、全平台 SRT 矩阵或可选依赖裁剪，后续 P5 的代码／资源闭包出口保持独立。

复用 `gordis/build`，提供 TeamX 薄适配和生成入口，例如后续的 `teamx-build`，该命令尚未实现。应用拥有工厂、默认组合、元数据与资源规则，构建库负责解析、编译、记录和交付。参考 Custom Adapter，不复制 Qi 历史构建引擎；构建期库不进入产品运行依赖。

当前固定基础包括文件存储和 DSH 所需运行能力，可选编译先面向平台通知、工具及相应 codec／资源。本阶段不要求交付完全不含 DSH 的可运行产品；将来接入 Codex 后，再验证相应后端选择与裁剪组合。

构建选择决定进入程序的原生代码，启动配置只启用已编译能力。`enabled=false` 不等于未编译。聚合工厂引用的全部实现进入依赖闭包，独立裁剪的实现须有独立工厂包，无需每包独立 Go module。

### 8.1 交付要求

- 默认组合显式选入当前正式能力，普通构建和原 CLI／HTTP／MCP 保持；自定义组合只导入所选工厂。
- 应用适配、前端入口、工具程序、Skill、嵌入资源随选择列出。通用 Web 可保留，能力项按实际目录展示；无法裁剪的专用资源如实记录。
- `boot`、通用服务和公共目录不通过默认工厂重新引入被排除实现，编译器不替应用消除显式传递依赖。
- 装配检查不启动模型／采集，不读取凭据，不修改数据；公开依赖版本与临时本地源码验证分开，不要求相邻 checkout。
- 运行配置与现存数据的能力依赖在启动前检查；构建不能预知未来所有数据。缺少旧 codec 时明确失败，不初始化空数据来掩盖问题。

### 8.2 代表组合

以 DSH 和文件存储为固定基础，至少实际构建默认完整组合，以及排除一个既有 Provider、保留另一平台通知／工具的组合；另验证加入最小外部扩展的构建。先隔离对应 Provider 的全链路依赖，不能仅删除一行注册声明。

检查生成入口、`go list -deps`、嵌入／交付资源、帮助／工具发现／配置入口，并验证受影响的本地启动与操作。旧配置或历史依赖被排除能力时，在隔离数据中验证明确错误，不对日常服务试错切换。

只有已验证组合进入发行清单，不承诺任意排列。体积与启动速度的收益以实测为准，当前首先交付可选择的依赖／资源和明确的扩展入口。

- 刷新受影响构建、回归与已知失败；区分实际失败、超时、未覆盖和真实后端证据。源码已通过的检查不因旧记录继续写失败，专项通过也不升级为全仓通过。保存现有证据，不覆盖历史基线。

**完成标志：** 有能直接指导下一单元的范围、依赖、正常调用点及验证清单；不为通过 P0 创建空包、全仓接口图、Gordis 封装或重启日常服务。

### 9.3 P1a／P1b：从唯一描述来源到真实外部装配

P1a／P1b 已完成，分别见[目录解耦记录](implementation/architecture/platform-catalog.zh.md)与[公开装配记录及验证](implementation/architecture/extension-assembly.zh.md)。以下保留各单元的范围与验收要求。

**P1a——先解耦，仍使用当前完整组合。** 将目录校验、纯解析与 Provider 实现分包；内置汇总由外层显式持有，通用目录不导入内置汇总。移走通用 `SourceBindings` 中列举的 GitLab／飞书具体类型，专用依赖由对应实现侧绑定；需要的宿主操作使用实际窄合同，不替换为 `any`、全能 manager 或 service locator。工厂和描述校验不读凭据、不启动连接／Actor／子进程。正常完整入口实际使用新结构，删除对应旧描述与重复选择。

验收以通用目录／解析包的 `go list -deps` 不包含具体 Provider、默认能力集合和来源／codec 一致、按需账号读取与错误行为不变为准。此时旧 Room 与其他装配仍可能直接导入 Provider，应列出剩余引用；不宣称产品裁剪完成。

默认集合以实施时源码为准：飞书 self／群发送含图片、普通回复仍为文字；GitLab 评论／讨论回复含图片，但纯文字不因联合 schema 而被一律限制为直接 Room 指令。保留静态注册与运行实现的一致性检查，工厂不得为了判断图片可用性读取真实账号或探测权限。迁走 `SourceBindings` 不代表同步迁移 P2n 的 Admit／加载／关闭合同。

**P1b——再公开实际需要的最小入口。** 公开最小工具扩展需要的描述、值类型、Compose 与启动入口，复用 P1a 及现有受控工具执行。选择一个无远端业务写入的本地工具 fixture，外部 module 能编译、在隔离服务被发现并执行，且不导入 TeamX internal；普通 `cmd/teamx` 使用同一装配路径并保持全部原命令。公开合同不能暴露仅本 module 可实现的私有方法或 internal 参数；不复制第二套 registry。

P1b 只承诺工具作者入口；外部通知的额外合同随 P2n 实际需要公开，不一次公开整个输入存储内核。外部 module 单独执行构建／受控验收，允许明确的临时本地模块映射，但发行使用真实版本，不依赖相邻 checkout。仅有描述可编译而没有正常列表／执行接入，不算完成。

优先复用已有无账号工具运行机制，不要求平台账号或 Workspace；成员工具绑定、身份与准入仍是必需边界。当前平台 Definition 要求 Provider／ToolType 一致，独立本地工具应作为工具贡献参与装配，不为迁就该结构伪造 Provider 或账号。公开面只覆盖该工具实际使用的描述／启动合同；不得将带有内部图片、动作状态或 notification Repository 类型的整体 Definition 原样公开。普通入口、显式单 Room、离线读取与升级继续接受同一外层选择，避免隐式完整默认工厂覆盖显式选择。请求文件仍由 CLI 所在进程读取，服务端不读取客户端提供的路径；零资源装配检查不通过 `newRoomManager` 间接启动日历或其他资源。

### 9.4 P2n／P2t：补通知和工具的完整运行边界

P2n 已完成，见[运行绑定实施与验证](implementation/architecture/notification-runtime.zh.md)；P2t 已完成，见[工具运行边界与验证](implementation/architecture/tool-runtime.zh.md)。以下保留各自范围与验收要求。

**P2n——飞书 messages 通知运行绑定。** 来源、准入、加载恢复检查及其执行依赖由显式适配绑定，通用通知初始化不再靠新增 `case "lark"` 接入该实现。收敛所选来源对连接、订阅快照、配置版本及目标投递的实际依赖，保留原 manager 门槛与唯一状态 owner；通用 Host 不接受整个 manager／Store。新增来源不应要求向通用参数结构补一个 Provider 专用字段。

验证正常启动、重开、停止采集、账号／代际变化、配置应答丢失、pending 投递恢复、撤权、取消与关闭排空；正式收件后才确认来源，保存内容读取仍不依赖远端在线。另用最小外部通知 module 验证公开来源／宿主合同能实际实现和投递到隔离 Inbox，不导入 TeamX internal。需要改变订阅操作编排时，只实施该来源的具体 R6b 操作；共享 lease／配置 owner 不拆成两份。工厂／Compose 检查仍零启动，获取运行资源发生在启动侧。原配置 UI 和授权流程可以通过同一 owner 的适配保留，依赖清理列入 P2r，不把它们计作已经可裁剪。

继续使用当前 SearchSource、搜索／回填与已保存状态格式，不退回旧轮询来源；来源、通知投影和 codec 使用同一所选描述。回流分类覆盖已有图文消息，本人自聊及群内本人内容不能因新工厂丢失原排除／context_only 语义。Room 附件是独立本地材料来源，不要求平台工具或远端账号；原附件 pin、清空／回收保护、Store 关闭次序不随通知绑定改变。codec 仍是可选声明，但用于实际持久收件／输入验收的外部 fixture 须按当前投递合同提供必需能力；已有磁盘分区缺 codec 仍明确拒绝，不能为 fixture 新增静默降级或省略旧数据保护。

**P2t——飞书内置工具调用族。** 以现有 help／read／actions 整个分发族为本次 R6a.2 单元，将解析后的应用调用与 HTTP framing 分开。实际执行接入平台运行适配，保留现有动作业务服务／记录的 owner；不在此迁 Followup 或重写动作协议。绑定、账号、凭据代际、执行前后证据仍在同一准入同步关系内核验，全部调用复用 R6a.1 的 Calls。

验证原列表、精确入口、help 的按需读取差异、read 与 actions、错误投影、流式输出、成员移除、绑定变更、撤权、晚到结果、取消后等待及关闭重试。不能只迁普通读取，留下该调用族的取消／结果复核由传输层修改内部字段。其他工具／附件／原生读取调用族保持原适配，不将 P2t 记为整个 R6a.2 或 R6 已完成。

当前 actions 基线还包含以下职责，随本调用族验证，不另起功能阶段：

- 保留内置 `actions resolve/execute --help`、候选 locator、动态 input_schema、精简投影与字段诊断；`--request-file -` 等 CLI 输入处理与根动作入口共用合同。`actions read --id` 在 Session 恢复期间仍可只读查询原完整回执，不要求先启动新执行或重新上传。
- 图片只接受已有 `{message_seq, attachment_id}` 引用。字节读取、发布／对象 pin、精确执行身份与释放由原 Room 宿主提供；只收敛当前调用所需的窄操作，不公开 service／Store、不增加附件解析工具。该宿主也被 GitLab 图文使用，保持同一实现并验证兼容，不在 P2t 搬迁 GitLab 调用族。
- 图片上传权限是原连接的独立观察，缺图片权限不关闭原文字发送；已保存图片可读不代表获得远端上传／发送权限。self／指定群／普通回复保留各自原目标和授权边界，不为统一接口扩大支持范围。
- 准入后保持同一固定账号、取消上下文和绝对期限；完整文字、有序图片字节摘要、目标及授权在最终发送前再次核验。不得丢失经宿主传入的最终 dispatch 检查。上传期间不持有 Store／附件生命周期锁；取消不等于上传进程、账号 pin、Room 源保护和 Calls 已全部结清。
- 同 ID 重试、重启后的原回执查询及 unknown 保持原策略，不重新上传或补发；已知远端结果不因晚到撤权而丢失。图文正文必须整条发送，失败不自动降级为文字或图片子集。

若迁移需先改共享 Room 图片宿主合同，应作为 P2t 内一个真实接入的准备切片验收，再切换调用族；不因此展开通用材料系统、完整 Followup／账本 owner 或 R4 迁移。组件／本地集成和故障注入覆盖上述边界；仅在改变实际平台协议、进程或后端行为时沿明确授权做相应隔离真实验收，不重复历史全部发送样本。

### 9.5 P4a／P4b：DSH 工厂与后端边界

P4a 已完成，见[工厂与宿主合同实施及验证](implementation/architecture/agent-factory.zh.md)；P4b 尚未实施。以下保留各自范围与验收要求。

**P4a——一个真实 DSH 工厂，所有相关入口使用。** 从 R5b.1 的实际合同提取跨包所需部分，公开仅实现后端工厂所必需的类型／能力；具体 Session 状态与 DSH 私有字段留在适配。宿主显式提供检查点、执行绑定、输入／材料、模型与观察操作，不能传整个 service／Store。正常成员构造、关闭 Room 的状态读取／恢复核验、轮换和模型应用取得同一工厂的能力，移除对应固定构造旁路。默认只选择 DSH，配置与持久格式不变。

通过现有实际入口验证构造零执行、原状态读取、正常执行与关闭结清；隐藏具体后端类型的集成 fixture 继续验证调用经合同发生。R5b.2 不自动纳入；若必须直接访问成员／输入内部字段，先列明并收敛该依赖，不为了跨包移动重写正式输入链路。

**P4b——能力归属与端到端对照。** 集中现有 DSH 模型验证、私有状态、活动投影、恢复和材料映射；明确哪些属于 ACP 通信、哪些是 DSH 扩展和 TeamX 持久接收桥接。沿 P4a 工厂验证原执行、取消、手动／自动轮换、故障及正常恢复、图片、History、模型应用与 Store 所有权。影响真实后端时在隔离目录完成代表性真实 DSH 对照，不用 fixture 或编译代替实际进程退出／恢复证明。

这两项不新增 Codex、不把 DSH 通信整体改名为通用 ACP 内核，也不代表 DSH 服务已受 Gordis 管理。后者需要单独完成 P3 模式的真实服务接入与验收；当前不预建无消费者的 Agent Plugin 层。

### 9.6 P2r／P3／P5：按需继续完成平台闭环

**P2r——剩余依赖逐操作隔离。** P0／P2n／P2t 留存的引用清单是本项输入；“迁完飞书”本身不是一次实施单。推荐按连接核验、现有配置／能力查询、订阅配置、授权与刷新／撤销、其余投影／升级／资源分别检查，每次选一个完整操作及全部相关入口。查询／编排仍可调用原唯一 owner 的合同；共享 token lease、flight 或配置记录若需转移，必须以其完整生命周期为单元，不能按列表强拆 owner。

后端专用实现、配置展示及升级等传递引用均有明确落点后，再用一个不导入飞书工厂的真实产品入口核对 `go list -deps`。仍含飞书实现时列出具体阻碍并继续逐项处理，不用 `enabled=false` 或目录级测试声称已经裁掉。保留默认组合的全部功能，独立裁剪所需历史 codec 时先验证其纯本地依赖闭包。

**P3——独立接入一个有真实资源责任的服务。** 优先评估空间通知运行服务，进入条件及出口见[空间方案第 11.6 节](WORKSPACE-AND-MULTI-USER-ANALYSIS-PLAN.zh.md#116-独立-p3-实施单保持业务关闭权威)。先核对原启动、Ready、恢复、冻结准入、取消、并行等待及 Store 释放关系；只有能通过窄适配完成真实资源管理、原业务关闭协议及唯一 owner 不转移时才实施。正常入口实际使用，失败清理、晚到结果及关闭超时重试可验证，不为纯描述目录发明空资源。Call 完成、通知提交与 Session 持久结果证明依原协议结清；Scope 退出或清理返回不能替代它们，不开放安装、任意插件重启或热替换。

复用 notification.Manager 的实际资源合同及 P2n 绑定；原 roomManager.shutdown 继续协调冻结、取消、Room／通知的并行等待及最终存储释放。`CancelRoomLocked`／`WaitRoom` 等接点不是待删插件旁路，Gordis 只在原协议规定的位置接入资源启停和完成／失败反馈，仅移除由新适配完整替代的重复调用。不能先销毁 Room 仍需等待或查询的服务，再依赖插件停止顺序补救。

关闭超时保留原对象、句柄、目录锁及操作证据，并按原合同重试；不因 Scope 已退出就宣称资源结清或释放分配。归档恢复／正常重开必须在旧实例结清后构造新的 roomManager／通知 Manager，加载原持久状态并更新 runtime epoch；当前通知 Manager 已 Stop 后不支持原对象 Start，不能把插件重新激活等同于复用 stopped 对象。原 User／Space／Room／成员身份、profile 和 Session 恢复合同保持。

Gordis 依赖在 P3 核验并记录版本，不要求 S1／S2 先添加；临时源码验证和发行依赖分别报告。若窄适配无法保持上述关闭权威、需要转移多个持久 owner 或修改输入消费证明，则暂缓该 P3，不回退 S2、不阻挡 S3。选定服务通过只声明其 P3 完成，不扩大为所有 Provider 可选或全部服务已迁移。

**P5a——生成入口与 Go 依赖选择。** 复用 Gordis Build 薄适配，实际构建默认完整、排除飞书而保留其他已有平台通知／工具、加入最小外部工具三种组合。生成 main 只使用公开入口；核对实际产品依赖、帮助／工具发现和隔离启动，不依赖运行配置禁用来代替编译选择。所选 Gordis 组合必须已有 P3 证据。本单元只交付代码构建闭环，未验证资源／旧数据兼容前不列为可发行裁剪组合。

**P5b——资源、打包及数据能力校验。** 按相同组合核对工具程序、Skill、嵌入资源、专用前端和打包清单，不能裁掉的资源明确记录。启动前依据隔离旧配置和保存分区检查必需能力；缺少 codec 明确失败且不改变正文、消费或创建替代空数据；若交付“只保留历史读取”的组合，单独验证其 codec 工厂与依赖。发行清单只包含真正验证的组合，不对任意排列作承诺。

### 9.7 收益评估与停止规则

每个单元将以下对照附在实施记录，不另建评分或长期指标系统：

| 要回答的问题 | 可复核证据 |
| --- | --- |
| 新能力是否少改公共代码？ | 以最小外部工具、来源绑定或 DSH 工厂为真实例子，列出需要修改的位置；区分实现、装配、配置和传输适配，不只数文件 |
| 依赖是否真正可选择？ | P1a 检查通用包，P2r／P5 检查真实产品入口的 `go list -deps`；区分这两种结论 |
| 状态责任是否仍然单一？ | 原 owner、锁、writer、Calls、授权和关闭链前后对照；无重复可变缓存、双写或第二个 Actor |
| 行为与验证成本是否可控？ | 原入口及对应错误／撤权／恢复对照，新模块局部测试与必要跨模块验证；列明真实模型／平台／浏览器证据和未覆盖项 |
| 适配是否抵消了收益？ | 原分支／重复实现实际删除，剩余薄适配只有转换和装配；若需要大量内部字段回调，先收敛当前边界 |

如果下一项必须同时搬迁多个 owner、修改存储／消费协议或扩大到新平台／新后端，保留当前可运行停止点，另定具体准备单元。每项通过不自动要求开展下一项；暂缓工作及原支持功能有明确记录。日常服务切换和真实平台业务写入不属于本方案文本调整或纯工厂验证的成果。

### 9.8 联合实施的交接与完成责任

当前已完成范围及下一实施单元以空间方案文首记录为准，历史第一批定义见[第 11.3 节](WORKSPACE-AND-MULTI-USER-ANALYSIS-PLAN.zh.md#113-第一批实施单默认空间与最小组合)，后续严格按其第 11.2 节执行；不先清完本方案所有剩余 P 单元。S1／S2 是里程碑，按空间方案细分的完整行为单元实施，不按字段、接口或文件拆空阶段。本节只约束专项交接，不复制批次顺序表：

- **第一批按 S1a／S1b 分别验收，不宣称 P3。** S1a 可保留现有 manager 结构，但实际入口须经过正式 User／默认 Space 授权；S1b 再完成普通 Go 工厂、个人默认组合、运行时和配置归属的统一装配。两者均通过才声明 S1，不为“预留插件”创建无资源 Plugin、公共用户 API 或通用 Host 容器。
- **第二批按 S2a／S2b 产品出口判断完成。** S2a 创建／切换与独立使用从首次接入就完成凭据、资源和异步作用域，沿用原关闭安全性；S2b 增加归档、结清后新实例恢复和相关超时／中断处理。两者均通过才声明 S2；P3 另记未实施、暂缓或通过，不影响 S2 与后续空间阶段。
- **P3 独立验证真实生命周期。** 可与 S2 同期开发，但必须保持原业务关闭协调，验证启动、失败清理、超时重试、旧对象保留及新实例恢复；适配需要重写核心协议时暂缓，不制造第二层关闭权威。
- **P2r 只按实际阻碍取完整操作。** 某个来源／账号／连接操作的窄适配准备完成，只记该操作，完整 Provider 的可选依赖仍以真实产品入口检查为准。P2r 全部完成不是单服务 P3 的一刀切前置；P5 发布所需的代码／资源依赖闭包要求保持。
- **P4b 和 P5 按需独立。** 前者不被 S3 自动包含；后者在选择性构建／发行有需求时交付，不要求个人／多用户先发布两种二进制。共享核心＋独立执行主线复用已取得的 S3a.1 独立证据，下一步 S3b.1 闭合实际 DSH 兼容与恢复，前置与出口按空间方案。SRT 机制通过不等于生产组合通过，也不要求先完成 Gordis 插件、每空间业务 worker 或完整 P4b。
- **执行与首发工具先接通，Git 和严格资源策略后置。** S3b.1 形成原生／SRT 与原恢复／关闭合同；S3b.2a 只验所选首发工具、未选托管 Git 全部入口禁用和基础保护；S3b.3 不依赖 S3b.2b。托管 Git 后续经独立能力与实际部署验收启用，个人原 Git 保留。精细硬配额不阻挡轻量组合，必需隔离缺失仍拒绝；共享资源竞争可影响全服务，不宣称公平或独立可用性。
- **S3b.3 仅做后续独立增量验收。** 不改变正在实施的 S3b.2a；待其完成后复用 S3b.1／S3b.2a 的有效证据，只补尚缺的正式共享服务双空间串联、实际外部模型及受影响能力检查。相关实现／策略／依赖或条件变化、失败及未解决缺口才触发定向补测，不重跑完整执行故障矩阵或默认 Room／全仓回归；保留原隔离、恢复与结清出口，不把重复测试当作阶段完成条件。
- **S4a 先模块化，认证 Gordis 插件后续独立交付。** 参考 CSGClaw 的 OpenCSG 自有 SSO，不把 JWT 解码或编码回跳状态当作完整身份验证；真实入口通过可信身份校验、并发回调隔离、本地用户／会话、最小准入及撤权结清验收。验证受控替代实现能在同一宿主合同工作、个人未选择模块时无远端依赖，不将纯可替换性宣称为 Gordis 集成。原内置凭据与完整管理界面保留为 S4d，可配第三方认证；第三方组合发布不等待 S4d，内置组合需其自身 S4／S5 证据。
- **S4b 与 Git 执行分别交接，S4c 分项后置。** 基础路线为 S3b.1 → S3b.2a → S3b.3 → S4a → 所选 S5。GitLab 应用／纯 API 选 S4b，核心 Git 仓库操作另选 S3b.2b 并补相应真实验收；不能因账号授权完成就自动开放 Git。S4c.1／S4c.2 独立后置，S5 仍验证新部署、同组合升级与备份恢复。未来 Gordis 模块／命令按真实贡献接入，不转移 grant、用户／会话或业务结清 owner。
- **S5.0 是实机验收前的交付实现。** 执行合同稳定后可与 S4a 同期准备，冻结候选须包含已通过出口的首发代码及所选能力；固定归档／摘要、SRT 依赖、安装配置与针对性 smoke 后才进入 S5a。systemd／HTTPS、真实登录和所选能力仍由 S5a／S5b 证明，依赖有效性不由“安装了插件”代替。该单元不等待 Gordis P5，不提前发布或切换日常服务；个人原生路径和既有 standard 内容保持。
- **一次实现、分项证据。** 共用测试只运行必要次数，两个方案可引用同一有效记录；S2 和 P3 的完成状态独立，不能由多空间可用推导插件化，也不能由 P3 通过推导多用户安全或按需发行已完成。

Computer C4 首版、C5 本机 Docker 托管和发布验收按其自身记录独立推进，不作为首次 P3 的试验对象，也不追加空间／Gordis 前置。联合实施只在空间阶段接入它已有的控制与结清合同，不改其已完成范围或替它宣称未完成的发布门槛已通过。

## 10. 验收、完成与后续任务

### 10.1 必需验证

- 公共合同不反向依赖实现，所选工厂决定依赖，生成入口不导入 TeamX internal。
- 工厂、Compose、帮助和装配检查零业务资源启动，不读凭据、不改数据。
- 类型、账号、成员权限分别核验，贡献清理不替代业务 owner 结清。
- JSON／JSONL、格式、目录锁、健康围栏、幂等、pin 和恢复行为保持。
- 默认平台／DSH 保留 History 图文／预算、输入证明、取消／恢复／轮换与关闭，按影响执行 race 和恢复测试。
- 代表构建实际排除指定实现依赖与所声明资源，旧数据缺少能力时明确失败。

### 10.2 完成判定

| 完成项 | 可宣称的结果 |
| --- | --- |
| P0 | 当前基线、平台／Agent 各自进入条件与验证限制已记录；无生产扩展或裁剪实现 |

保持现有功能和数据的兼容回退；外部扩展版本与配方留有记录。日常服务切换属于后续采用，不以重启或修改配置替代实现验收。

Codex 按 ACP 另定实现与真实验收范围，Gmail 等新平台按具体通知／工具任务交付。存储替换、跨进程插件与动态安装／热替换当前不排实施单元，出现明确需求时再设计，不维护待启用框架。
