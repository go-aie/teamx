# GitHub 活动通知提案

状态：待实施。本文保留后续设计方向，按当前[平台架构](platform-architecture.zh.md)修订落点，不代表已支持 GitHub 或完成 API/目标实例验证。

## 范围

面向受管房间和 GitHub.com，主动轮询 PR 新建、关闭、合并、重新打开、head SHA 变化，以及 PR 普通评论和行内评审评论的新建。提供类型、源/目标分支和忽略账号过滤。监听由用户显式开启，不要求公网地址、Webhook、Workspace 或本地 clone。

首版不包含正式 Review 状态、评论编辑/删除、通用 Push、Actions/Checks、Enterprise Server或历史回放。平台操作工具与通知分别接入；写回开发/评审闭环不作为通知首版前提。

## 接入方式

| 部分 | 建议职责 |
| --- | --- |
| `internal/platform/github/` | Go 账号/仓库核验、单页查询、字段归一化、具体状态 schema、Runner 和消息模板 |
| 公共连接服务 | 引用实例、账号与凭据，按 provider 核验；不复用 GitLab 数字用户 ID 假设 |
| 公共通知服务 | 复用任务、状态保存、收件箱与投递，不另建 Room 专属 worker |
| Room / 页面 | 独立配置连接及仓库、显示积压/错误、提交 integration 消息及回执 |
| 可选独立 GitHub 工具 | 优先评估 gh，直接使用当前通用工具启动入口；与后台采集互不调用 |
| 可选 Workspace 绑定 | 仅本地 Git 工作确有需要时扩展，不作为监听或 API 工具的依赖 |

连接核验与通知来源使用独立静态注册点，独立工具不 import TeamX 内部包。废止旧提案中的服务 Python 查询工具、Workspace 前置条件及冻结工具桥接；不恢复已删除的 PC 授权/RPC。

## 查询与进度设计

优先评估专项 API：PR 列表/详情、仓库 Issue 普通评论、PR 行内评论。实施前核对官方 API、分页与限流行为；不直接照搬 GitLab 日期窗口，不以仓库 Events 时间线承担完整恢复保证。

- 初始化固定首次基线，建立已有 PR 快照；旧对象首次观察只作为基准，不虚构此前变化。初始化失败保留基线，新 PR/评论按真实创建时间接收。
- PR 状态和 head 变化与对象快照在同一次提交中保存，使用单调观察版本区分 A→B→A，不能把 SHA 或状态值当作永久去重键。
- 两类评论分别维护进度，按稳定 ID 去重；以创建时间区分新建和旧评论编辑。普通评论需核对父对象确为 PR，行内评论保留实际路径、行号及 commit，不假设属于最新 head。
- 初始调度可评估可接收实例 30 秒、未打开或操作中 120 秒，同账号汇总请求预算。扫描逐页保存收件项和检查点，完整结束后才推进水位；中断后重叠重扫，定期复核已跟踪开放 PR。
- 查询受页面、字节、耗时和存储预算约束；触顶明确显示积压，不丢页或误报完整。无法访问/删除数据与轮询间未观察到的中间变化明确报告限制。
- 条件缓存按账号、来源和完整参数隔离，页面持久化后才确认；304 不取消其他扫描。遵守等待及限流提示，区分限流和权限失败，不统一将 403 当凭据失效。

归一化对象保存 provider、实例、已核实仓库身份、来源/对象 ID、PR number、时间、账号、分支/SHA、标题和链接。来源标识按不透明字符串处理，具体分页和水位留在 GitHub 来源内。

## 可靠入房与验证

复用[现有通知链](notifications.zh.md)：先持久化收件箱，再原子提交 Room 消息与独立回执，最后确认收件项。向订阅所属且可接收的实例投递；未打开或操作中的房间采集暂存，不依赖页面选择。关闭/删除先停止接纳并结清查询，拒绝迟到结果；清空聊天不清同步进度。

消息只发布平台事实，不指派、不建议、不 @ 成员。Agent 通过独立工具重新核实对象和版本；外部内容不构成写入授权，不确定写入先查询，不自动重放。未来写回需考虑精确评论 ID 与自身事件反馈循环，不能只忽略整个账号。

实施顺序为连接与单页查询、来源扫描与存储、消息与设置、真实验收。重点覆盖 PR/Issue 区分、同时间戳和分页变动、初始化/离线补查、A→B→A、落盘失败、身份切换及迟到结果。真实阶段使用专用仓库，分别记录平台查询、唯一入房、Agent 读取、浏览器操作、请求成本和发生→首次可见→入房时间。
