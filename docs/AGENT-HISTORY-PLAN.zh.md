# Agent 统一历史读取方案

状态：**H1–H3 已完成；H4 入口收敛与生产默认路径验收已完成，当前运行服务尚未切换。** H1–H3 记录见 [H1](implementation/agent-history-h1.zh.md)、[H2](implementation/agent-history-h2.zh.md)、[H3](implementation/agent-history-h3.zh.md)。H4 已移除旧 CLI 并启用正常服务默认注册，代码与正式部署证据分开记录于 [H4](implementation/agent-history-h4.zh.md)。当前服务及既有 Session 保持运行，未为刷新工具集轮换 Session。

## 1. 目标与采用范围

Room 消息、Room 事件和平台通知已经通过统一 Inbox 交付。Inbox 回答“还有什么没有正式读到”，History 回答“这个上下文最近保存过什么”。

推荐首版沿用 Inbox 的参数风格，只提供两个只读 MCP 工具：

- `history_list`：列出当前成员有权读取、仍有保留记录的逻辑流。
- `history_read`：按 `stream_ref` 读取该流最近的 limit 条记录，需要更早内容时用 cursor 续读，直接供给正文和预算允许的图片。

这足以支持常见的最近讨论回看、当前 MR／群聊通知回查和 Session 轮换后的相关上下文恢复。已有事项、问题和动作结果仍通过原业务接口核实；重要进度仍写入事项或 Workspace，History 不恢复私有 Session 中未保存的思考。

首版提供必要的顺序正文翻页，不提供关键词／标签搜索、对象范围、跨流聚合、单条记录定位或前后文展开，不引入全文索引、独立归档库及新保留策略。它不能快速定位任意久远的一句话，也不承诺恢复已回收或未采集的内容；历史遍历仍受权限、快照有效期及回合预算限制。

### 1.1 与 Inbox 一致的参数，不同的读取语义

| 项目 | Inbox | History |
|---|---|---|
| list 首次请求 | `{limit?}` | `{limit?}` |
| list 续页 | `{cursor}` | `{cursor}` |
| list 范围 | 有待交付输入的流 | 有可见保留记录的流，包括全部已消费的流 |
| read 首次请求 | `{stream_ref, limit?}` | `{stream_ref, limit?}` |
| read 续读 | 重复 `{stream_ref, limit?}`，按消费位置继续 | 只传 `{cursor}`，按浏览位置向更早记录继续 |
| read 范围 | 最早未消费的若干条 | 最近保存的若干条 |
| 重复读取同一流 | 确认后取得下一批 | 重新观察最近范围，不隐式向前翻页 |
| 状态影响 | 正式交付确认后推进消费 | 不推进消费，不创建业务关联 |

History 可以返回未消费、已消费及已合法跳过的记录。比如最近五条包含三条未消费通知，历史读取后这三条仍由 Inbox 正式交付。History 不作为消费进展，不重置 Inbox 停滞恢复额度，不因查询而唤醒 Agent。

### 1.2 整体架构：同一输入体系的两种读取视图

综合推荐采用这一边界：**后端复用输入存储与交付基础，Agent 通过 Inbox 正式收件、通过 History 回看最近上下文；业务进度和动作结果继续由原模块管理。** History 是现有读取能力上的只读视图及薄 MCP 适配，不建设第二套收件系统。

| 层次 | 共同能力与保留的职责 |
|---|---|
| 来源与编码 | Room 生成原生消息／事件；平台适配器负责采集、原生身份、归组和保存正文的解码 |
| 存储与保护 | 共用已发布段读取、范围校验、快照、短期 pin、回收与确认原语，各 owner 保留唯一发布根和权威状态 |
| 读取与材料 | 共用流身份、位置访问、正文投影、图片处理及身份／生命周期设施；按视图区分选取规则、可见性和有效预算 |
| 读取视图 | Inbox 选择待交付输入并执行正式交付；History 选择保留输入及最近后缀，读取后不提交消费 |
| 业务状态 | Matters、operation、action 分别管理跟进、操作和动作回执；输入消费、业务办结、外部动作成功是独立事实 |

“统一”指共用可靠原语和清楚的调用协议，不要求将所有内容放进同一文件、全局序号、单个 owner 或第二套统一检查点。Room Actor 继续保存原生时间线、成员游标及证明；平台私有／共享输入沿用各自正文 owner 和成员消费权威；成员执行协调器继续负责正式页与 Session 交付结清。来源 owner 的待投递缓冲只表示采集／投递状态，未进入接收端保留存储的通知不属于 History。

实现中应提取确有共同调用方的只读 helper，复用记录投影和材料处理；不要求先进行全面重构。Inbox 独有的 reserve、业务关联、Session 证明和确认路径保持独立。共享身份与权限设施也不意味着复制全部过滤条件：History 的可见性、Inbox 的可交付性、远端图片下载授权分别核验。

对 Agent，四个工具保持“list 找流、read 读流”的同一操作习惯，stream_ref 可直接复用，工具名称明确是否消费。未来增加平台主要扩展 codec、原生归组及材料适配，正常收件和历史读取均可复用，不必为每个平台增加一组工具或让 Agent 填原生定位参数。

这一架构覆盖常见的持续消费、相关流回看和基于持久事实的会话恢复。任意条件历史检索、跨来源聚合、已回收正文恢复，以及仅存在私有 Session 的思考不在首版能力内。架构判断与功能验收分开：足以作为推荐实施方向，具体正确性、模型使用成本及恢复表现仍按第 7 节验证。

## 2. 流的含义及引用来源

复用已有流身份及 provider 归组，History 不建立另一套对象模型：

| 来源 | 当前正常归组粒度 |
|---|---|
| Room | 本 Room 的公共对话及该成员有权查看的事件 |
| GitLab | 指定实例、账号、项目和对象类型下的某个 MR 等对象 |
| 飞书 | 指定应用、账号下的某个群聊／会话 |
| 共享通知 | 原共享逻辑流，继续绑定接收成员与 Grant |

因此，“查这个 MR 的历史通知”通常就是读取已有的 MR 流。不自动合并同一 MR 在私有、共享或不同账号下的多个流；显示标签相同也不能视为同一身份。

原生上下文缺失时，现有归组可能退化为较宽的来源流。目录必须保留这种范围提示，不能把它包装成某个 MR 的专属历史。人类仅允许读取特定对象时，不得用较宽流的正文试探目标。

`stream_ref` 可以直接来自：

1. 回合开始的 Input directory 或 `inbox_list`，用于处理当前输入时回查历史。
2. `history_list`，用于主动回查或目标已无未读输入的情况。
3. 恢复材料或先前保存的流引用；正常重启／Session 轮换后重新核验权限即可复用。

History 不接受或解析 Matters 的 `object_ref`、`unit_ref`、`target_ref`，也不接受单条记录引用、URL 或标签作为读取参数。`source_ref`、Room Seq／reply_to、事件 result_ref 等原有来源证据仍可出现在正文结果中，但不是新增的 History 输入类型。不新增 `msg_...` 或 `scope_ref`，不为发现流引入前置解析工具。

## 3. MCP 契约

服务绑定 Room、成员、执行代际和当前回合。Agent 不传身份、turn、分区、序号、快照或调用 ID。两工具均使用固定 JSON Schema，禁止额外字段，声明只读。

### 3.1 `history_list`

参数直接沿用当前 `inbox_list` schema：首次接受可选 `limit`，默认 10、范围 1–20；续页只接受返回的非空 cursor，长度最多 128 字符。`cursor` 与 `limit` 互斥；不接受 `query` 或 `scope`。

```json
{"limit":10}
```

```json
{"cursor":"..."}
```

以下为响应示例：

```json
{
  "streams":[
    {
      "stream_ref":"stream_...",
      "kind":"platform_notification",
      "label":"project-a / MR !56 / 修复发布流程",
      "source_label":"GitLab / 公司实例 / 账号甲 / 私有通知"
    }
  ],
  "next_cursor":"..."
}
```

目录只返回定位和区分流所需的元数据，不预览正文、不下载图片，不额外返回保留条数、未读数或总数。`kind` 表示 Room 流或通知流，复用既有目录分类，Room 流内可包含消息和事件。

标签包含必要的来源、账号、项目／会话及共享属性，便于区分同名目标；范围退化时增加简短 hint。目录不查询事项状态，也不创建来源关联。没有输入消费额度、曝光公平性或当前来源阻塞条件的隐式过滤；仍须执行本地历史阅读权限。

按流最近的本地保存时间从新到旧列举，时间相同时以稳定流引用排序。Room 使用原生发布时间，通知使用 ReceivedAt；该顺序只用于浏览，不代表跨来源因果或业务优先级。

首次调用冻结可见流目录及保留元数据；新增记录不插入旧目录。cursor 绑定成员、执行、快照和偏移，重复调用同 cursor 返回同页。list/read 共用有界的回合内查询缓存，建议最多 4 个快照、空闲 TTL 5 分钟；回合结束、重启或失效后明确要求重新开始相应查询，不要求跨 Session 恢复 cursor。cursor 还绑定工具种类，list 和 read 的 cursor 不能混用。

续页重新核验身份和共享 Grant。清空／回收或授权变化使旧快照不再有效时明确失效，不静默跳过。返回 next_cursor 仅表示目录还有流，与正文是否有更早记录无关。

### 3.2 `history_read`

首次请求沿用当前 `inbox_read` 的参数形状及字段校验：必填 `stream_ref`，长度 1–128 字符；可选 `limit`，范围 1–10,000。History 默认 limit 为 20，上限只代表请求合法，实际供给仍受文本和图片预算约束。续页只接受返回的非空 cursor，长度最多 128 字符，与 stream_ref、limit 互斥；页大小由首次请求固定。

```json
{"stream_ref":"stream_...","limit":1}
```

```json
{"cursor":"..."}
```

不接受 scope、query、单条 ref、before/after 或 consume 参数。已知流可直接 read，无需先 list；即使流已全部消费，也必须能读取。

首次调用捕获该流的当前已发布上界，先按成员可见性筛选，再取最近 limit 条。流内沿用原生本地保存顺序，每页结果从早到晚排列。next_cursor 固定原流、快照、页大小及本页最早实际返回位置，下一页只读取更早的记录；新增不进入旧快照，持续续页不重复、不遗漏快照内记录，重复同一 cursor 则重供同页。

例如，首次取 81–100，续页取 61–80，再续页取 41–60；页内均从早到晚，页与页向过去推进。重新传 stream_ref 表示新建最近观察，不表示续页；增大 limit 也会重读最近窗口，不能代替 cursor 续读。浏览位置是短期查询状态，不是成员消费检查点，不隐式共享给另一次历史查询。

返回一个 JSON 文本块，以及零个或多个 MCP 图片内容块。以下为 JSON 文本内容示例，位于 MCP content[0]；对应图片位于 content[1]：

```json
{
  "context":"GitLab / 公司实例 / 账号甲 / 私有通知 / project-a / MR !56 / 修复发布流程",
  "entries":[
    {
      "source_ref":"src_...",
      "created_at":"2026-11-19T09:00:00+08:00",
      "text":"流水线失败，错误截图见附件。",
      "images":[{"position":1,"content_index":1}]
    }
  ],
  "next_cursor":"..."
}
```

完整 entry 复用现有 Inbox 的 `inputRoomBody`／`inputNotificationBody` 业务投影，保留 Room 作者／回复关系、事件类型／原 result_ref、通知来源证据／保存正文及材料位置。时间字段沿用 created_at，不另起 occurred_at；流类别由目录说明，事件以既有 event 字段表达，不为 History 逐条增加 kind。context 复用原来源及流标签组装能力，只在页顶按需提供一次，用于直接 read 或 cursor 续页核对目标，不同时回显 stream_ref、label、source_label 三套上下文。未经证实或不完整的来源证据、context_only、编辑／删除、提及和附件状态等必要业务字段也不能省略。不附加事项摘要或查询当前业务状态，不把内部访问证明、凭据、原始存储路径交给 Agent。

每页只需用 next_cursor 表示还有更早记录并给出续读入口；没有则省略，不另加 has_older、has_more 或 complete。正常成功、无 stop_reason 且没有 next_cursor，表示当前快照内可见的保留记录已经翻到头，不代表曾经发生过的全部历史都已覆盖。

单页文本预算不足时保留该页候选中连续的最近后缀，先省略较早的整条记录，不跳过中间记录，也不裁半条正文或 JSON；next_cursor 必须从实际返回边界继续，把尚未返回的较早候选留给后续页。页长少于 limit 也可能还有续页，以 next_cursor 为准，无需额外回显限额或裁剪计数。当前待返回的最新一条本身无法交付时明确返回 too_large，不能跳过它继续生成成功页。

回合预算耗尽或存在必须停止的操作限制时才返回 stop_reason，明确要求停止；不能通过省略 next_cursor 伪装成历史已经读完。权限、快照失效或损坏沿明确错误路径返回。固定快照、实际扫描边界及有效额度保留在后端，不作为每页常规展示字段。

工具说明固定写明“只读取本地保留快照、不消费、按页向更早内容翻阅”，无需每页重发 coverage.basis 或 snapshot_at。确知相关历史曾被清空／回收、因而会影响本次完整性判断时，使用可选 `warnings: string[]` 给简短事实说明；平时省略，不输出 none_known、unknown 或笼统的固定免责声明。warnings 不重复 stop_reason、条目截断或材料 reason 已经表达的事实。

保存正文在采集时已经截断时，保留既有 `truncated: true` 或对应的准确缺失说明；未截断时不输出 false。图片／附件未取得的状态仍需保留。不能把“记录已完整返回”解释成远端讨论完整，也不能把未读到的内容解释成从未发生。

### 3.3 图片及预算

read 自动准备所选记录的图片，无需 Agent 先列附件、拿 URL 或另外下载。图片通过带 MIME 的 MCP image 内容块供给，不能把普通 stdout 中的 base64 或文件路径当作模型已理解图片。

图片关联记录及原 position；供给成功时仅附 content_index，表示 MCP content 数组的零基下标，同图多处出现可共用一个块。未供给时不带 content_index，改为提供明确的 reason，例如预算省略、账号无权限、远端不存在、模型不支持；不再并列一个可由上述信息推断的 status。两种结果至少具备一种，不能只列附件存在就暗示已经供给；MIME 和实际像素由 MCP image 块提供，不在 JSON 中重复。

按最新记录优先分配图片预算，最终正文仍从早到晚排列。单次 read 内可去重，不能因为旧 Session 或正式 Inbox 曾看过图片，就认为本次读取已经获得像素。

首版集中定义操作预算，建议：list 最多 64 KiB 文本，read 最多 256 KiB 文本；History 每回合累计文本最多 512 KiB、图片最多 4 张／原始字节合计 4 MiB，同时不超过现有图片限制及 MCP 序列化上限。base64 膨胀计入总响应大小，预算需要通过实际模型及性能验收确认。

History 预算独立于正式 Inbox 额度，同一执行回合的重复、并发和不同传输共用计数；同调用 ID 的有效重放不重复扣费。耗尽时明确 stop_reason，不能反复 list/read 刷新额度。只需有界运行时计数和短期结果缓存，不持久建立另一套消费状态机。

### 3.4 Agent 响应精简原则

**只保留对来源识别、事实理解、业务关联、续读及真实完整性边界有贡献的字段。** 复用后端能力不意味着把内部状态或所有存储字段搬进 MCP 响应。

| 保留／移除 | 原因 |
|---|---|
| 保留正文、作者、业务时间、回复／结果及必要来源引用 | 影响事实含义、可信来源及后续核验 |
| 来源与流上下文沿用 context，页顶按需提供一次 | 直接 read 或 cursor 续页能核对目标，无需同时回显请求引用与目录标签或在每条重复 |
| 保留 next_cursor | 直接决定能否继续，并提供唯一续页参数 |
| 保留真实截断、未供给材料、必要 warnings／stop_reason | 防止把缺失当完整，或把预算停止当无更多历史；无异常时不填默认状态 |
| 图片成功用 content_index，失败用 reason | 供给状态可由这两个互斥分支确定，不另加 supplied 等 status |
| 移除 requested_limit、returned_entries、has_older／has_more／complete | 请求或数组长度已表达数量，游标及停止／错误已表达续读状态 |
| 移除整个 coverage 对象 | 静态范围写进工具说明，快照和扫描数据后端持有；实际缺口才单独提示 |
| 移除目录保留计数、普通页重复身份及内部收据／版本 | 不影响本方案的流选择和事实理解，避免增加模型负担 |
| 默认不展示 ReceivedAt | 本地保存顺序由服务固定，Agent 保留事件业务时间即可；确有延迟诊断价值时再在相应结果中提供 |

材料的位置、实际 image 内容块和未供给原因仍须准确对应；不要为了字段少而丢掉原生来源、用户限制或完整正文。新增字段须说明 Agent 据此会做什么不同的正确判断，不能仅因后端已有就默认公开。

### 3.5 与当前 Inbox 输入输出的对齐

| 内容 | 一致部分及有理由保留的差异 |
|---|---|
| 首次 list/read 请求 | 直接复用参数名和校验；History 的 read 仅增加互斥的 cursor 续页分支，因为没有持久消费推进 |
| 目录 | 复用 stream_ref、kind、label、source_label、hint；Inbox 的 pending_streams／pending_entries、attention 服务待交付判断和收件选择，History 不复制这些含义，也不另造对应统计 |
| 正文 | 共用业务字段名和事实投影；选取记录可以不同，相同记录的来源、正文、时间、作者、回复及限制证据应一致 |
| 读取进度 | Inbox 的 remaining_entries 表示固定观察中剩余待交付条数，重复读流即可继续；History 用 next_cursor 指向固定快照的较早页，无需 remaining_entries |
| 跟进摘要 | Inbox 正式关联后可提供当前输入相关的已有 followups；History 不做关联或业务状态查询，所以不附加这一层摘要 |
| 图片 | 都通过 MCP 实际 image 块供给，统一来源及位置的含义、下载与验证逻辑；History 使用本方案的精简描述，当前 Inbox 仍有页顶状态／复用来源等字段，二者组织方式并非消费语义必须不同 |
| 停止、错误和缺失 | 共用清楚的状态原则；正常字段省略默认值，真实截断／未取得材料不能隐藏，不把停止当查完 |

图片描述等展示差异应在共同材料模型上做薄投影，避免两套原生解析／授权实现；本方案不要求为了字段外观一致而重写既有 Inbox 的准备结果。后续如同步精简 Inbox，只影响新生成结果，已持久页及同页证明保持原字节。响应的差异必须来自用途或现有安全兼容边界，不能仅因工具名不同另起一套事实表示。

## 4. 存储、权限和生命周期

### 4.1 复用存储和流身份

正文仍由 Room 原生日志、成员私有输入分区和共享 Inbox 保存，不复制到 History 库，不新建 HistoryActor 或持久消费账本。复用 Group.StreamRef、Room 流和 SharedStreamRef 的现有算法；引用独立于 turn、Session generation 和 ServiceEpoch，继续区分 RoomInstance、Membership、账号及共享 Grant。

从所有已发布、仍保留的可见元数据构建可重建的流目录与位置索引。不能复用只包含待交付输入的 Catalog 作为全集，也不能用 Matters 来源文件枚举历史；未正式交付、没有事项、已消费或已跳过记录都必须可读。最新位置等内部目录信息优先从元数据取得，不为列目录解码整批正文。

流引用通过保留元数据及原生 Room 身份核验，按流只读取当前页需要的正文，复用同一流位置索引向前续读。正常重启／轮换后同成员的有效流引用可复用；若已无记录且无法可靠核实原流，返回 stream_unavailable，不凭 opaque hash 猜测流身份。短期 cursor 不具备流引用的跨重启寿命。

### 4.2 只读与图片授权

History 不调用正式 reserve、prepare、associate 或 confirm 流程，不产生 Session 消费证明，不推进游标、不创建事项／答复／授权，也不修改 operation 或 action 记录。

保存正文的本地阅读不要求启用平台工具或 Workspace。订阅停用、采集阻塞或输入被正式排除，本身不删除本地历史阅读权；成员可见性和真正的权限撤销仍生效。Room 历史使用原生 roomVisible 规则，包括可见的自身发言和公共事件，不误用仅针对正式投递的 roomDeliverable。

共享记录继续核验当前有效 Grant 及原冻结接收集合，新加入或重新加入者不继承旧记录。持有旧流引用或任一种 cursor 不授予权限，正文续页和结果重供也必须重新核验。

材料解析、图片定位、账号权限核验、下载、格式／大小验证及 MCP image 块生成继续共用现有流程。需要适配的是记录范围依据：Inbox 使用正式交付页中的记录，History 使用当前历史快照页中的记录；将目前耦合正式页的范围检查提取为可复用核验入口，绑定有效执行、具体已授权记录及图片位置，不另建 History 材料服务或权限证明体系。图片需要远端下载时仍核对成员自己的账号和绑定，不借用采集账号替代执行账号，不自动解析远端对象或补采讨论。Inbox 独有的材料结果持久化、重供与消费证明留在正式交付层。

保存通知和图片引用不等于永久保存图片字节。优先使用已有可验证材料，否则按当前权限下载；删除、失效、超时及模型不支持图片时逐张说明，正文仍可成功。新下载的字节不承诺与过去供给的像素完全相同。

### 4.3 并发、保留与错误

只在实际读取时使用短期段 pin；目录／正文查询缓存不长时间阻挡回收。清空／回收改变固定保留边界时，旧正文 cursor 明确失效，不能悄悄跳过缺失记录或切换到新快照。捕获各 owner 已发布范围即可，无需跨 owner 新增原子快照事务。Store 锁、manager Gate 和 owner 变更槽内只做必要核验及视图捕获，不执行批量正文读取、图片下载或输出编码；按现有锁序和生命周期实现。

请求 lease 覆盖准备至输出结束。共享撤权与历史响应 handoff 串行核验：撤权先发生则拒绝供给，已准入输出纳入结清等待；取消、关闭和异常都释放 pin、lease、缓存及图片字节。缓存命中仍须重新核验权限，不能借历史查询绕过关闭或 Session 轮换门禁。

首版沿用 Room 显式清空和平台现有保留／回收策略；默认三天是通知回收条件，不保证第三天立即删除，更不保证此前远端内容完整。正文回收不删除已有跟进、问题和动作回执，但 History 不从它们重建正文。

至少区分正常空目录、stream_unavailable、cursor_expired／snapshot_expired、access_denied、history_budget／too_large、storage_corrupt／storage_unavailable。已发布正文缺失、损坏、提交状态未知不能转为空历史；跨成员引用遵循现有防泄露规则。清空／回收发生在捕获后、有效 pin 前时失败或重新捕获，不能静默返回另一观察范围。

## 5. 接入、现有 read 与 Session 恢复

### 5.1 MCP 及旧入口

History 的两个工具以 HTTP MCP 为 Agent 主入口，复用身份、模型能力、响应大小及生命周期设施，不建设独立的通用工具框架。

History 可用性独立于 inbox_mode：CLI Inbox 模式仍提供 History MCP，同时禁止 Inbox MCP 正式读取。当前 mcp_access.go 对 CLI 模式整体拒绝 input MCP，需要按工具集合拆开注册与准入，并同时验收 tools/list 和实际调用，不能只改提示词。

Agent 的正常入口收敛为 Inbox 和 History，移除 teamx read CLI 及相应指引，不再为 --all 单独保留兼容命令。与现有能力的衔接如下：

| 现有能力 | 本次处理 |
|---|---|
| `teamx read` 默认／`--latest N` | 移除 CLI 入口，由 History 首次读取最近窗口承接 |
| `teamx read --all` | 随命令移除；需要更多保留历史时按需用 cursor 续读，不新增 all 参数或承诺一次无界读取 |
| `read --unread`／`--unread --peek` | 统一模式下 Agent 的旧入口已被拒绝，不作为 History 功能缺口 |
| 内部 ReadUnread + Peek:true | 统一 Inbox 仍用于扫描候选页，继续保留底层原语 |
| `matters sources/source` | 保留业务关联和旧响应；不作为 History 目录或前置解析依赖 |

删除的是 CLI 解析、帮助和调用指引，不删除底层 Room 读取原语；自动恢复、Inbox 内部扫描及 History 继续复用。相关测试和必要脚本改用 History MCP 或原生测试 helper；Matters 和其他 CLI 继续保留，如能安全共享只读 helper 就复用。正常 Inbox 的正式页、已保存图文结果及同页证明保持原字节，不为了 History 重写在途结果。首版不新增 teamx history CLI。

### 5.2 会话恢复

采用“基础上下文自动提供，更多细节按需读取”，保留现有恢复材料及供给时机，首版不改为完全按需恢复：

| 供给方式 | 内容与职责 |
|---|---|
| 自动供给 | 原有有效规则、Input directory、最多最近 20 条 Room 消息的只读预览、未完成事项摘要及未知动作提示；实际数量受可见性和既有预算限制 |
| Inbox 正式读取 | 交付尚未消费的相关输入，并按原 Session 证明确认 |
| History 按需读取 | 缺少相关流的更多上下文或平台通知时补读，不默认注入通知正文或整个历史目录 |
| 原业务查询 | 核实具体规则、工作进度、问答及操作／动作结果 |

Room 预览仍按首个业务回合的固定快照取最近窗口，不按消费状态排除记录；即使 Room 已经全部消费，也提供仍保留、可见的最近对话背景，避免新 Session 必须先自行判断是否查 Room。沿用首次成功业务回合完成后不重复供给、失败后可重供、预算裁减和安全结清规则；不额外调用模型，不改为每回合注入。

预览可能包含尚未消费的消息，它们随后仍会由 inbox_read 正式交付。**首版接受这部分有界正文重叠：预览一次、正式交付一次，只确认消费一次。** 不因预览已出现正文而跳过正式交付，不让 History 过滤未消费内容，也不增加专门的跨视图去重状态。正文再次出现不等于新增任务或重复执行动作，Agent 继续核对原请求、已有答复和动作回执。

恢复由原有有效规则、持久工作进度、已有问答／动作证据和相关流最近内容共同完成，不能假设最近 limit 条包含所有历史约束和决定。长期约束及关键进度仍应在原业务记录中保存；读取范围不足时先补核相关状态，不能把缺失事实当作不存在。执行层的未结清输入页仍凭原 Session 证明恢复，History 不代替其重供／确认协议。

恢复材料可在已有 Room 预览顶层补一个准确的 stream_ref；其他流沿用当前 Input directory 或以前已有的流引用。缺少相关流时调用 history_list 并按标签选择，不为事项补建对象到流的关联图。

Agent 工作方式：

1. 通过相关 Inbox 正式读取当前输入，确认本次意图；History 预览不代替正式交付。
2. 需要旧上下文且已有 stream_ref 时直接 history_read；没有时先 history_list。返回足够信息即可停止，需要更早内容就用该 read 返回的 cursor 续读，不靠重复首次请求或不断增大 limit 翻页。
3. 跟进状态、已有问答、操作结果和动作回执仍走 Matters／operation／action。未知动作先核实，不能凭旧通知重发。

历史内容保留原信任级别，旧请求、通知和图片不自动成为当前任务或动作授权。人类仅允许读某账号／对象时，先通过纯元数据确认流范围，不能读其他流正文寻找线索；确认不了就说明范围不足。目录翻完、预算不足或最近内容不足都需准确报告，不为恢复而遍历全部正文。

### H1：历史读取视图与续页

主要新增逻辑集中在本阶段：实现两工具的服务契约、全保留流目录、目录分页、最近可见记录选择及固定快照的正文续页，覆盖 Room、GitLab／飞书私有输入和共享输入。复用存储、流身份及既有正文投影，实现流引用恢复、完整记录的预算裁减和必要缺失提示；通过直接服务测试验证已读／未读／跳过、无事项、清空／回收、重启及权限隔离。本阶段不注册生产工具，不另写来源解析或材料下载流程。

完成标准：同一 stream_ref 在正常收件与历史读取之间直接复用；已无待交付输入的流仍能发现；所有读取均不改变消费和业务状态。

### H2：MCP 接入与既有材料能力复用

在隔离 MCP 服务注册两工具，接入现有执行绑定和输出生命周期。把 H1 选定并核验过的历史页接入已有材料流程：仅适配记录范围依据、操作预算及结果投影，必要时提取共享 helper。材料定位、身份／账号及归属验证、下载、格式限制和 image 块生成均复用；不要把本阶段实现为第二套只读材料系统，也不新增正式页或消费协调。

验收 HTTP／CLI 两种 Inbox 模式的工具集合、同 cursor 及调用重试、共享撤权和关闭；通过实际 MCP 输出检查图文位置及缺失原因，再用真实 DSH／ACP 做小样本验证，确认文字和图片确实进入模型上下文。扩展场景及完整恢复验收留给 H3，避免重复建设验收环境。

完成标准：已知流一次调用即可读图文，无额外 scope／ref 转换，无正式页或隐式业务写入。真实模型证据与 mock 组件证据分别报告。

### H3：恢复接入与完整集成验收

在隔离环境接入 Agent guide、恢复 guide 和必要的恢复引用，明确自动 Room 预览与按需 History 的分工，保留既有有界恢复材料及供给时机。将需要迁移的 CLI 调用测试／脚本改用新路径，更新 inbox、通知参考和存储文档，完成第 7 节的真实 DSH 场景、真实保存通知及性能核验。

本阶段保留旧 teamx read 命令，不正式切换运行中的 Room。真实模型／平台材料验收及工具集安全刷新方式须分别留下证据，不能用静态 schema 或隔离注册成功代替当前 Session 已可使用。

完成标准：隔离环境可通过 Inbox／History 及原业务查询完成消费、历史续读和恢复；正常收件、只读边界、已消费 Room 的初始预览及重叠不重做动作等回归通过。明确工具预算和目录定位成本达到可采用程度，没有影响切换的未决问题。

### H4：入口收敛与正式切换

H3 通过后，移除 teamx read 的 CLI 解析、帮助和最终调用指引，保留底层 Room 读取原语及其他 CLI／业务接口。核验删除后的构建、相关回归、脚本和恢复指引没有旧命令依赖；不再为旧命令保留长期兼容分支。

在已授权的服务范围及安全生效窗口启用 History，确认目标 Session 的 tools/list、实际调用和新指引均已生效。切换期间先结清旧在途执行；新工具集不能安全生效时停止切换并说明原因，不能先移除旧入口让仍依赖它的执行继续运行，也不为刷新工具集擅自轮换 Session。现有正式页及证明按原字节结清，不迁移历史数据。

完成标准：最终运行路径只依赖 Inbox／History 和既有业务工具，teamx read 已退出；服务上的工具发现、一次目录／图文读取、历史续页、正常消费及恢复检查均通过。正式启用证据与 H3 的隔离验收分别记录。

### 阶段边界与交付约定

H1 验收“选对并完整读到”，H2 验收“经真实工具安全交付图文”，H3 验收“与现有业务和恢复一起工作”，H4 验收“正式入口切换完成”。前一阶段通过再进入下一阶段；每阶段均交付对应代码、调用／帮助或指引、行为测试及验收记录，不把必要权限与失败恢复测试推迟到最后。

这四阶段是交付和核验顺序，不是四套子系统。主要新增选择／分页逻辑在 H1，H2 以适配及复用为主，H3 以集成验收为主，H4 以命令退出和切换检查为主。已有授权范围内可连续完成各阶段，不因分阶段额外增加审批；不需要为 H1／H2 各建运行时、状态库或重复的图片／权限实现。

H1 仅完成服务层，H2 隔离注册，H3 保留旧入口，H4 完成删除与采用；阶段号只用于计划和验收记录，不进入长期业务命名。实施发现确有必要的新契约决定时，先把决定及影响补入本方案再继续依赖它的工作；普通内部结构选择由开发按本方案边界处理，不为每个实现细节另开审批。当前 H1、H2、H3 已完成；H4 已实施入口收敛，正式服务切换尚未完成。

## 7. 验收与采用门槛

| 场景 | 必须验证 |
|---|---|
| 目录和参数 | 首次参数与 Inbox 对齐，list/read 续页均只传 cursor；两类 cursor 不混用，未知字段及与 cursor 混传被拒绝；没有 query、scope 或单条 ref |
| 保留记录范围 | 已消费、未消费、已跳过、无事项及自身 Room 发言均按原可见性读取；读完不推进消费 |
| 流身份 | 同名跨账号、私有／共享及不同 Grant 不串流；MR 流可复用，退化来源流不冒充精确对象 |
| 共用读取基础 | 相同可见记录的正文、来源及图片位置在两视图中一致；没有第二份正文、Room 游标、History owner 或业务完成状态 |
| 最近 limit | 先过滤可见性再计数，返回最近记录并从早到晚排列；扩大 limit 扩大最近范围，不隐式翻页 |
| 重复调用及并发追加 | 同调用重试保持原观察；新调用可见新增；未追加时不能因重复 read 读到更早一批 |
| 目录分页 | 固定元数据快照，续页无重复遗漏；新增不插页，回收／撤权使不再有效的 cursor 明确失效 |
| 正文续页 | 按固定快照向更早记录翻页，无重叠、遗漏或消费推进；同 cursor 重试同页，新增不插页，预算裁减从实际供给边界续读 |
| 正文与必要提示 | 预算保留最近连续后缀，完整记录不切碎；next_cursor／stop_reason、真实截断及必要清空／回收提示准确，无默认 coverage 和重复计数 |
| 事件与业务边界 | 私有事件不泄露；保留 result_ref，不把事件当成操作最新状态，不创建事项或动作 |
| 图片 | 实际 image 块、位置和状态一致；下载失败、模型不支持及预算不足不假报已供给 |
| 撤权和生命周期 | 缓存及旧 stream_ref 不越权；输出竞争有序，取消／关闭释放 pin、lease 和图文字节 |
| 命令退出与工具发现 | teamx read 解析／帮助／Agent 指引已移除，底层 Room 读取仍可用；CLI Inbox 下 History MCP 可用而 Inbox MCP 正式读取仍禁止，在途页证明不变 |
| Session 恢复 | 可重用流引用补上下文；未读仍由 Inbox 交付；已有答复和成功／未知动作不会重复执行 |
| Room 全部已消费时恢复 | 即使待消费目录没有 Room 流，初始恢复上下文仍有预算允许的最近 Room 预览，不依赖 Agent 主动查询 |
| 预览与未消费消息重叠 | 预览不推进消费，随后仍可正式交付同条消息且只确认一次；不得重复动作，也不额外建立去重账本 |

自动化验收核对真实权威状态，包括消费游标、正式页证明、业务关联和 action 记录；不能只看返回的“只读”标签。完成必要服务／传输／race 检查及正常 Inbox／恢复回归，不为文档示例编写镜像测试。

真实 DSH 代表任务至少覆盖：最近 Room 决策、已有 MR 流回查、无未读输入时从历史目录发现目标、飞书流图片读取、依靠正文 cursor 找到较早记录、轮换后恢复并核验已有动作结果。每类至少 3 次，保留实际工具 trace、答案及权威状态对照；已知流首批内容目标为 1 次历史调用，目录首屏可定位时目标为 2 次，必要目录／正文续页及业务状态核验另计。

使用已有并获准读取的账号，在隔离 Room 中分别验证 GitLab 和飞书的真实保存通知；远端仅读取，不发送、评论、合并或改订阅。真实图片失败要单独报告，不能用 fixture 图片理解替代真实平台材料证据。正式服务启用也是独立证据。

用满容量 Room、私有和共享输入以及至少 1,000 个逻辑流，测量冷／热目录、深页定位、已有流最近读取、连续正文续页、较大 limit 的文本／图片预算及内存。并行追加、消费、回收和另一 Room 的普通读取，确认目录和图片下载不长时间阻挡共同锁，报告 P95、目录定位调用数及实际供给范围。

最近内容不足时应按实际需要用正文 cursor 续读，额度耗尽或快照失效则明确停止并报告；大目录定位若频繁需要很多调用，应先检查标签、排序及真实使用成本，不能用自动遍历所有正文补救。标签筛选等复杂查询能力仍按需求评估，顺序续读属于本方案的基本读取能力。
