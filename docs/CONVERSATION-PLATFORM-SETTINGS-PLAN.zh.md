# 对话式平台设置方案

状态：S1–S2 已实施并通过本地验证；S3 已完成验收入口、模拟提供方组合验证，以及用户指定飞书单群的真实模型／浏览器和 GitLab 指定项目的真实模型验收；第二真实群、指定人员私聊及完整选择接续等仍未验收，S3 不标为全量完成；S4–S6 待实施。更新日期：2026-11-12。

本方案补齐飞书／GitLab 接入后的对话式设置。推荐先完成明确指令修改通知配置及其真实验收；完整编辑卡片、高级参数和共享草稿均为后续可选项。完成推荐部分即可独立交付，不以共享草稿作为最终完成条件。

S1 已交付范围与验证记录见[对话通知配置扩展](implementation/conversation-platform/NOTIFICATION-SETTINGS.zh.md)，S2 见[指定人员私聊](implementation/conversation-platform/PRIVATE-NOTIFICATIONS.zh.md)，S3 的入口、证据及未完成门槛见[设置组合验收](implementation/conversation-platform/SETTINGS-ACCEPTANCE.zh.md)。通知编辑卡片和共享草稿仍为拟议实现。实施 S1–S2 未修改运行配置或真实平台订阅；本次 S3 仅修改隔离成员配置。

## 1. 推进结论与范围

优先解决用户已经能“关注群”，却不能同样自然地“取消关注、替换范围、只接收 @我”的能力不对称。已有成员配置服务承接真实修改，已有选择卡片解决账号、群、项目歧义，完整设置保留复杂整理与异常恢复能力。

推荐部分的目标体验：

- “关闭你的飞书通知，工具保持开启。”——独立修改通知并反馈结果。
- “取消关注产品讨论群。”——从当前已关注项定位；唯一目标直接移除，同名时先澄清。
- “以后只接收研发群和产品群，私聊关掉。”——核验完整目标后一次修改范围，不追加确认卡片。
- “群消息只接收 @我，不接收 @所有人。”——准确设置两个独立条件。
- “私聊先关掉，以后再打开。”——保留已有范围，恢复时核对指定列表有效性。
- “私聊只接收张三和李四。”——在指定私聊能力完成后，核验真实人员私聊再修改。
- “GitLab 只保留分配给我的合并请求待办。”——复用已有筛选命令，无需新增完整编辑卡片。

“帮我整理全部接收范围”等开放式整理，前期先查询并说明当前配置，用户明确修改项后直接执行；需要批量可视化整理时使用现有完整设置。实时混合点选与对话编辑留到最后评估。

本方案仅涉及当前完整 Room／Agent／Membership 下的飞书和 GitLab 设置。不扩展其他平台、外部业务写入授权、Workspace、长期提醒规则、Inbox 调度或历史接收起点。“接收哪些消息”与“何时提醒我”保持独立，不把“少打扰我”“及时提醒”自动解释为缩小接收范围或调整轮询。

## 3. 推荐部分的交互边界

### 3.1 明确请求直接修改

目标、动作和参数明确时，读取当前成员配置及版本，沿成员配置服务直接执行，再核对回执和权威配置。通知和工具分别报告，不为了调整通知重新连接账号、启用工具或增加确认卡片。

同一请求、同一成员／账号的通知修改合成为一个配置操作，保留原真实 human 消息和稳定操作 ID。字段不足或对象存在歧义时，先查询、澄清；不能先提交半份配置，再用新 ID 绕过同一来源的操作限制。

前期不增加通知草稿、活动草稿查询或草稿优先规则。明确指向已生效配置的修改保持直接执行，不因为存在另一张未完成的选择卡片而变成“只编辑未保存草稿”。已有接入／选择结果仍按原规则核对较新的用户意图、原回执和接续状态，不能让晚到的旧结果覆盖新请求。

### 3.2 候选选择与完整编辑分开

- 账号、追加关注群、GitLab 项目歧义，继续使用已有固定选择卡片。
- 移除关注优先在当前已关注列表中定位，不能要求远端群仍可访问；多个匹配时展示可区分的名称和 ID，待用户明确后再提交。
- 完整替换范围不得把旧群卡片的未勾选项直接解释为删除。只有能表达所需目标的既有选择器才复用，否则通过查询和澄清收齐完整目标，不扩张旧卡片语义。
- 指定私聊先使用受控查询和对话澄清，不为了这项能力新建人员卡片或通用选择器。
- 用户询问未提交卡片内容时，如实说明当前可读取的服务端内容；不宣称已读到本地未提交输入，不将“就这样保存”解释为前期不存在的草稿确认命令。
- 完整设置继续独立保存，关闭设置或切换 Room 不自动取消已有接入／选择操作。

### 3.3 结果与恢复

配置冲突时读取最新配置并重新判断，不用新版本盲目重放旧补丁。请求超时或回执未知时先查原操作，不更换 ID。GitLab 存在来源应用中、待处理或错误时，沿现有恢复入口处理，不报告全部成功。

结果反馈包含目标成员、平台账号、已生效变更和必要的直接后果；移除最后一个指定群造成群接收关闭时应明确说明。保存配置、平台事件进入 Inbox、用户可见提醒送达是三项不同结果。

## 4. 受控配置修改契约

### 4.1 字段与阶段归属

扩展 `platformMemberInput` 的飞书专属类型化补丁，不允许 Agent 提交任意完整配置 JSON。省略表示保留，显式 `false` 表示关闭，显式空列表表示清空。输入结构和 CLI 必须保留列表是否出现的信息，不能依赖普通空切片或 `omitempty` 区分省略与清空。

以下描述字段语义。S1 的实际 CLI 参数已写入帮助、Skill 和实施记录；其余字段的拼写在对应阶段确定：

| 维度 | 字段／动作 | 阶段与约束 |
| --- | --- | --- |
| 群增删 | 原追加能力＋移除 ID | S1；增量与完整列表替换互斥，同一 ID 不能同时追加和移除 |
| 群完整范围 | `groups.enabled`、`groups.scope`、`groups.chat_ids` | S1；范围 `all/specified`，列表完整替换，只有明确范围意图才切换 |
| 群消息条件 | 原群模式＋`groups.at_me`、`groups.at_all` | S1；独立可选布尔值，“只 @我”同时关闭 @所有人 |
| 私聊开关／全部范围 | `private.enabled`、`private.scope=all` | S1；保留已有指定范围；尚无目标时不能启用空的指定列表 |
| 指定私聊 | `private.scope=specified`、`private.chat_ids` | S2；使用人员私聊原生 `chat_id`，不是用户 `open_id` |
| GitLab 来源与筛选 | 现有 `todos/events` 开关及筛选 | S1–S3 复用、回归，不新增同义字段 |
| 两平台轮询 | `interval_seconds` | 可选 S5；前期继续使用完整设置 |

保留原有 `enabled`、群模式和 GitLab 筛选语义，拒绝跨 provider 字段。新字段只能修改当前成员该账号的接收配置，不能修改目标身份、工具授权、历史起点或采集游标。S1 允许启停已有指定私聊分支，但不提前开放替换私聊列表或切换为指定私聊范围；这些写入随 S2 的查询核验一起交付。

### 4.2 启停与列表语义

- 原 `--add-chat-id` 的明确关注行为保留。新范围／条件补丁不因字段出现就隐式打开通知总开关；用户明确要求开启或关注时，按其意图启用相关分支。
- 若启用总开关会激活未请求的休眠来源，要求明确来源选择，不能顺带开启其他来源。指定列表为空时显式要求开启应返回冲突，不能暗改为全部范围。
- 指定范围内删除已有群只缩小该列表，不修改私聊。移除最后一个指定群时关闭群分支；指定私聊清空时同样关闭私聊分支。没有任何启用的接收分支时关闭总通知，并反馈直接后果；显式同时要求开启却不给有效范围时拒绝矛盾输入。
- 关闭分支保留其范围和条件。重新启用时检查指定列表非空，不能恢复为空的分支。
- 从全部群切到指定群，必须有明确的 `scope=specified` 和完整目标列表。全部范围下“取消某群”不支持排除语义，应说明限制并澄清；不能枚举当前可见群冒充“全部但排除 A”。
- 全部消息模式下提及条件不参与筛选，可保留旧值供切回使用。“改成仅提及”且两个提及条件均关闭时可沿用当前默认启用 @我的行为；用户明确要求仅提及且两者均关闭时返回冲突，不暗改输入。
- GitLab 待办原因／类型的显式空维度表示不匹配该维度，活动类型空列表表示全部活动；沿用现有不同语义。
- 未指定字段、历史起点和正常采集进度保持原样，修改范围不清空 Inbox 或撤回已排队提醒。没有已保存订阅时，关闭或移除不存在的关注返回未变更，不创建意外启用的订阅。

### 4.3 对象与身份核验

新增目标或完整替换提交的目标集合需在同账号下核验。移除目标使用当前配置内的精确 ID，即使远端已不可访问也可取消关注。只关闭来源无需先查远端，补丁中未修改的既有目标不因目录不可用而被删除或替换。

Agent 群查询保持默认 `Type=group`，精确核验只接受群／话题群。S2 已增加受控的 `chats --type group|p2p`，搜索和精确核验一致区分群与人员私聊；复用 `listLarkChats`、现有目录与 `NotificationChat` 关系识别，不引入第二套通讯录。人员搜索不查询机器人，候选和保存均核验当前账号的真实人员会话关系；参数与分页限制见实施记录。

私聊仅接受当前产品支持的真实人员私聊，不将机器人私聊、群聊或用户 ID 冒充会话。找不到可核验会话时说明前置条件，不发送消息创建会话。按服务返回的分页令牌继续读取，空页和权限不足不证明不存在，保留搜索权限提示。

GitLab 继续核验原生项目 ID 和完整路径。远端读取前后、真实写入前重查完整成员、账号、连接版本和通知配置版本，工具修订保持独立。复用未知提交围栏、原来源操作约束和同一配置服务，不增加新的订阅权威或协调服务。

阶段号表示推荐推进顺序，不代表后续全部必做；长期代码和测试按行为命名。

## 7. 推荐部分的验收

### 7.1 服务与 CLI

- S1：群追加、移除、完整替换、全部／指定切换；移除不可访问旧群；最后一群、无接收分支、空列表和无订阅操作有准确结果。
- S1：私聊关闭后范围保留，恢复指定范围时不改为全部；明确全部私聊可启用，空指定范围不能被隐式开启。S2 补齐指定范围切换及列表修改。
- S1：“只 @我”准确关闭 @所有人；组合条件、全部消息切回、显式无提及条件冲突均符合契约。
- S1：省略、false、空列表含义不同；增量与替换互斥，拒绝同 ID 同时增删及跨 provider 字段。
- S2：人员私聊搜索、分页、重名、机器人／群类型不符、精确 ID 核验、指定替换及清空；权限不足和部分结果不能当作不存在。
- 共用：完整成员／账号隔离，伪造来源、成员替换、连接换代、通知版本冲突，以及远端核验期间目标变化被正确拒绝。
- 共用：同一 ID／输入只返回原回执，改输入冲突，同来源换 ID 不能绕过限制；未知提交和重启不重放。
- 共用：未指定配置、工具、另一通知来源、历史起点和采集进度不受影响；休眠来源不被顺带开启。
- GitLab 回归：多值筛选及显式清空、精确活动项目、单项目限制、来源部分应用与错误反馈。
- 既有接入／选择回归：明确请求不额外建卡；必要选择沿原 Inbox 接续；旧结果核对较新意图，取消／过期不复活。

### 7.2 S3 真实模型与浏览器

1. 在当前已关注群上通过对话移除一个、添加另一个，再完整替换范围；每条请求核对实际修改和原成员回执。
2. 通过一句明确请求同时修改群范围、私聊开关和独立提及条件；不重复确认、不改变工具和起点。
3. 指定人员私聊覆盖唯一目标、重名澄清和不可核验目标；拒绝时不产生配置变化。
4. GitLab 通过既有命令修改待办多条件及活动项目／筛选，核对另一来源保持原样。
5. 浏览器完整设置展示对话修改后的真实配置，独立保存后旧版本直写被拒绝；冲突后依据新状态重新判断。
6. 既有账号／群／项目选择必要时能正常提交并自动接续；无必要时直接执行，不引入通知草稿等待状态。

真实验收使用隔离实例和用户指定目标，只修改验收成员接收配置，不发送额外平台消息制造业务事件。记录真实 human 消息、原操作 ID、配置版本、应用回执、最终权威配置及必要浏览器证据，不记录凭据。结束后停止隔离采集，并说明验收配置是否保留或恢复。

服务模拟、CLI、真实模型和真实浏览器证据分别报告。未实际收到平台事件或生成可见提醒，不能据配置验收宣称提醒送达通过。外部权限或模型阻塞记为未完成门槛，不用模拟结果替代。

## 8. 后置可选项及进入条件

本节保留未来设计边界，不构成前期实施要求或确定排期。每项真正启动时需结合最新源码补充字段、命令和专项验收，不将这里的概念视为已存在 API。

### 8.1 S4：完整通知编辑卡片

进入条件：用户反复需要预览全部已选项、批量增删或组合筛选，现有完整设置的导航确实造成负担。按出现需求的平台和区域交付，不为两平台形式对称同时建设。

- 复用 selection 增加固定通知编辑类型，以真实当前配置预填；范围与条件可在同一操作内提交，不建设通用表单 DSL。
- 首版仅浏览器编辑并通过按钮提交。Agent 可读取状态、解释结果，不为该新类型开放草稿修改、自然语言确认或实时混合编辑。用户指向未提交卡片时，说明需先提交或取消，不猜测本地输入，也不自动取消。
- 列表搜索与已选摘要分开，允许删除不在当前候选页的已选项；范围切换保留选择，GitLab 筛选支持完整多选。
- 草稿绑定完整成员、精确账号／连接、原 human 消息及通知配置基准版本；预填快照不成为第二套配置权威，未修改字段不能因预填被整份覆盖。
- 提交冻结精确草稿版本，由服务从不可变结果构造补丁和固定成员应用 ID，复用配置服务及既有 Inbox 接续。不能由 Agent 读取旧卡片、套最新配置版本手工重建整份配置绕过冲突。
- 显示“编辑中／已提交等待应用／实际保存完成／结果待核验／取消或过期”，不能把选择完成当成配置成功。Agent 暂停等接续阻塞沿既有机制如实展示。
- 完整设置独立保存；其成功保存后旧草稿因基准冲突被拒绝。首版不自动合并或重设基准，重新整理时从最新已生效配置初始化。
- 取消只终结未提交草稿，不撤回已保存配置；与提交竞争只允许一个终态获胜。旧卡片、晚到响应和重启不得复活取消／过期草稿。

验收覆盖预填、多选、提交到真实保存、双标签页版本竞争、侧栏基准变化、取消／过期、重启恢复、接续阻塞和窄屏操作。即便没有共享草稿，这些基础正确性要求也不能省略。

### 8.2 S5：对话高级参数

进入条件：用户确实反复需要用明确秒数调整轮询，完整设置不能满足便捷性需求。只增加类型化字段、CLI、帮助及配置核验，不建卡片，不依赖 S4。

飞书当前范围 3–3600 秒，GitLab 当前范围 3–120 秒；实施时核对平台归一化函数，复用其校验。调整间隔保持来源开关、范围、历史起点及采集进度；不得把“及时提醒”等模糊表达转成轮询修改。

### 8.3 S6：实时共享草稿，最后评估

进入条件：已有 S4 卡片后，反复出现“点选一半，再用对话修改，最后继续点选”的真实需求，且不能通过明确修改请求或单一编辑入口顺畅完成。仅为了让交互看起来统一，不足以启动本阶段。

本阶段会让用户需要区分草稿同步、提交、实际保存和冲突恢复，也使相同修改表达在草稿上下文中具有不同效果。进入前需重新评估这些认知成本与开发维护成本；可以长期不做。

决定实施时保留以下必要边界：

1. 同一完整成员／精确账号最多一份等待编辑的通知草稿。增加受控活动查询，关联原请求、目标及尚未处理的结果，不按最近卡片或显示名猜测。原直接配置入口不依赖草稿查询或草稿锁。
2. 点选串行同步服务端，可合并连续点击；明确显示同步中／成功／失败。只保证已成功同步内容可被 Agent 读取，最终提交等待同步完成；失败不提交旧版本。
3. Agent 读取最新完整草稿，以草稿版本比较更新，保留未改字段和多选项；竞争时保留本地输入、显示冲突，不盲目重试或首版字段级自动合并。
4. 对话明确针对该草稿时才编辑或确认，说明“尚未生效”。明确修改已生效配置不静默变成草稿编辑；不明确时澄清。直接修改成功后，旧草稿仍受通知基准版本保护。
5. 对话编辑／保存／取消依据服务读取的真实 human 消息，核验原操作者、房间、完整成员及消息时序；原创建消息不变。内部事件、外部平台通知和 Agent 自报 human 不构成确认依据，不开放旧类型的原 human 提交接口。
6. 可增加通知类型专用的 `selection active`、带意图消息的 `update/confirm/cancel`；拼写届时确定。确认冻结的结果与按钮提交一致，应用入口从结果取得补丁、基准、固定 ID 和消息依据，不允许客户端覆盖。核对同一来源的既有操作约束，不能换 ID 绕过。
7. 草稿版本、连接版本和通知配置版本分别保护混合编辑、账号变化及旧配置覆盖；工具修订继续独立。侧栏仍独立保存，不共享未提交输入或自动重设基准。
8. 取消仅针对未提交版本。已提交时先查原回执，未知提交沿原围栏恢复，不承诺强制停止或撤回。取消／过期后新请求从当前配置新建，不复活旧操作。
9. 沿 selection 持久化、既有 24 小时过期和 Inbox 接续；不另建唤醒、审批或业务停止队列。成员替换不换绑旧草稿，搜索和同步晚到响应不得覆盖终态。

专项验收必须包含点选同步后对话读取、自然语言与按钮分别保存／取消、离线与未同步输入、双方同时编辑、配置基准变化、取消提交竞争、提交后新意图、重启和接续阻塞，并分别记录真实模型及浏览器证据。共享草稿不能靠删除这些保障变成“低成本版本”。
