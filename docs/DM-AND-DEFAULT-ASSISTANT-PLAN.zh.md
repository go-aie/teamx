# DM、Room 与默认助理方案

状态：D1–D5 已实现。当前使用与接口见[会话与默认助理](conversations.zh.md)，持久化约束见[Room 架构](room-architecture.zh.md#私信与默认实例)，平台操作见[飞书使用说明](lark.zh.md#通过对话接入)，验证入口与未验范围见[测试说明](testing.zh.md#私信与默认助理)。本文件保留原设计与阶段依赖，不再单独保留阶段实施流水。平台接入 C1–C6 以其现有方案为准。

## 1. 目标与首版范围

所有会话底层继续使用 Room，以 `is_direct` 区分一对一会话和团队房间。UI 将二者分别呈现为「私信」和「房间」。每个 TeamX 数据目录首次启用此功能时，默认创建一个「个人助理」DM，内含一个 Assistant 角色的 Agent，作为用户日常交流、平台接入与设置引导的入口。

默认助理配备[对话式平台接入方案](CONVERSATION-PLATFORM-SETUP-PLAN.zh.md)中的接入 Skill，通过受控 CLI 辅助完成初始化与设置；Skill 随底层功能逐步开放。模型首次配置继续复用现有 `start init`，助理负责模型可用之后的平台接入，不承担启动自身所需的模型／密钥配置。

首版包括：DM 数据契约、DM／Room UI、内置助理角色、默认实例创建与恢复、平台接入 Skill 整合。不包括：全局独立 Agent 实体、跨 Room 共享 Agent 状态、助理代管其他成员、自动创建团队／分派任务、DM 转 Room、任意角色编辑器，以及原平台方案以外的初始化能力。

## 2. 现状与设计依据

- `RoomSnapshot` 保存消息、成员和游标，`managedRoomConfig` 冻结创建配置，`roomSummary` 提供目录信息；目前没有 DM 字段。
- 团队模板及托管创建允许 1–32 个 Agent，但创建请求要求 `team_id`，按整个团队初始化。UI 统一显示房间、成员列表，再打开成员详情。
- 平台连接由服务全局共享，通知订阅、工具绑定和长期规则仍按准确的 Room／Agent／Membership 管理。
- 当前工作区已有 `platform_connect.go`、`platform_connect_cli.go` 和 `skills/platforms/SKILL.md` 等进行中实现，包含飞书连接命令及基础 Skill；是否完成 C1 及验收需另行核对。群配置、对话组件及自动接续不能仅凭这些文件认定可用。

借鉴 [Matrix Direct Messaging](https://spec.matrix.org/latest/client-server-api/#direct-messaging) 的「DM 也是 Room」思路。Matrix 的 `is_direct` 用于创建与邀请信号，用户实际分类由账户数据 `m.direct` 记录，也不强制双人；TeamX 将其简化为服务端持久化的 Room 属性，并自行规定 DM 固定一个 Agent。首版不引入用户级分类映射。

## 3. 模型与不变量

### 3.1 会话类型

```go
IsDirect bool `json:"is_direct"`
```

| 属性 | DM：`true` | Room：`false` |
| --- | --- | --- |
| 用户语义 | 与指定 Agent 直接交流 | 与团队协作 |
| Agent 数量 | 必须恰好一个 | 创建时 1–32 个 |
| 创建来源 | 单 Agent 角色定义 | 现有团队模板 |
| 成员变更 | 禁止加第二个、移除或替换唯一成员；手动创建的 DM 可整条删除，默认助理不可删除 | 沿用成员管理约束 |
| 身份、执行与持久化 | 复用现有 Room／Membership／Session | 沿用现有机制 |

类型创建后不可修改，不从成员数量推断。旧 Room 即使只有一个 Agent，也保持 `is_direct=false`。零成员 DM 属于损坏或未完成初始化，不作为普通空态，也不自动补一个同名成员掩盖问题；已有 Room 的空成员状态另按现有恢复机制处理。

字段必须贯通创建入参、初始化记录、配置、快照、目录及 HTTP 投影。`managedRoomConfig` 冻结创建时的类型，初始化据此生成快照与目录；之后三者必须一致，运行时 Add／Remove 按快照约束，目录只供展示。加载发现不一致时明确报错，不根据 UI 选择、成员数或默认零值覆盖。`RoomIdentity`、`MemberIdentity` 不加入此字段，身份及已有平台目标的含义不变。

旧数据中缺少字段按 `false` 读取，不扫描改写历史、不自动迁移成 DM。新增字段要求与格式校验、创建重试比较一起处理；若实际实现必须提升文件版本，则提供明确的离线升级路径，不顺带迁移通知或 Agent 数据。

### 3.2 单 Agent 创建

扩展现有创建契约，示意如下，最终字段以实现时帮助为准：

```json
{"create_id":"稳定请求ID","is_direct":true,"agent_role_id":"assistant","name":"个人助理"}
```

- 普通 Room 继续使用 `team_id`；DM 使用 `agent_role_id`，二者互斥。省略 `is_direct` 的旧请求沿用 Room 行为。
- 新增最小的只读 Agent 角色定义，首版仅内置 `assistant`。名称、职责及指令由该定义提供；模型和 DSH 使用服务默认 runtime，创建时冻结。单角色时 UI 不增加无意义的角色选择器。
- 角色来源与 `team_id` 明确区分，不伪造隐藏团队。复用现有身份分配、资源安装、Workspace、初始化日志和失败恢复，仅抽取必要的共同构造逻辑，不建设通用模板框架。
- 每次显式新建 DM 都有独立 Room、Membership、Session、Inbox、规则与工作目录。角色 ID 只是模板来源，不是全局运行实例；名字相同也不共享状态。
- `create_id` 的比较包含类型、来源与名称，相同请求重试复用原结果，改变参数报冲突。创建完成前必须同时具备唯一成员及其配置，不能先交付可使用的零成员 DM。

UI 可提供「新建私信」，首版创建同一内置角色的独立实例，默认命名「个人助理」，允许修改会话名称。会话别名不改 Agent 身份或内置角色名称，也不影响默认实例识别。自定义角色与从团队抽取某个成员后续再评估。

## 4. 默认助理的职责与生命周期

### 4.1 角色定义

显示名称建议「个人助理」，角色说明为「Assistant：梳理需求、协助设置、汇总进展」。指令保持简短，完整平台流程按需读取 Skill。

| 职责 | 首版行为 |
| --- | --- |
| 需求澄清 | 将用户目标整理成可执行步骤，只询问影响执行的缺失信息 |
| 平台接入 | 查询现有连接，发起飞书授权，核验账号和连接结果 |
| 当前助理设置 | 能力上线后，为自身 Membership 配置明确的群关注及所需工具 |
| 进度与恢复 | 查询原操作、解释部分成功和阻塞原因，继续尚未完成的步骤 |
| 日常协助 | 使用已有对话、事项和长期规则机制，不宣称具备未提供的定时／跨房间能力 |

Assistant 是职责定位，不是管理员权限。保留公共 Agent 指南的成员与委派边界，不赋予 impersonate-human、读取凭据或跨 Room 写配置的能力。默认 Skill 可被其他符合条件的 Agent 读取，不能靠角色提示词承担服务端授权。

平台连接属于全局资源，应说明可供其他会话复用；通知、工具和规则只绑定当前助理。用户要求配置另一个 Room／成员时，首版引导进入明确的目标会话或现有管理入口，不偷换当前身份，也不隐式将其他会话需求配置给助理。

助理对需要答复的直接用户消息，通过现有 `send` 发布可见结果；普通模型输出仍为私有。不能仅把私有最终输出当作用户已收到回复，也不把每条状态变化刷成公共消息。

### 4.2 一次性创建与恢复

默认范围为当前服务的数据目录，与当前单操作者模型一致；不按浏览器、标签页或登录会话各建一份。未来引入多用户时再扩展归属。

1. 托管服务完成目录锁及索引加载后，检查持久化的默认助理初始化记录。新数据目录及升级后首次启用的既有目录均执行一次，已有 Room 不变。
2. 无记录时，用保留的稳定创建 ID 预留默认创建操作，记录目标完整身份；复用普通 DM 创建流程。角色来源与成员配置一并冻结，再生成唯一 Membership。
3. 初始化记录与创建预留在同一索引提交中关联，区分待完成、已完成；保留旧版本的删除中和已删除状态读取。崩溃后按原创建 ID／身份恢复，不能“找不到现成 DM 就新建”。不通过显示名称猜默认实例。
4. 创建完成后记录默认 Room 引用；成员身份从该 Room 校验取得。多个浏览器只观察同一结果，不触发各自创建。角色随包内置，不要求用户先建团队目录。
5. 默认助理作为固定入口不可删除，保留重命名、暂停和重新开始；UI 移除删除入口，服务端按持久化的完整默认 RoomIdentity 拒绝删除，重命名不影响限制。手动创建的私信继续可删除。旧版本已受理但中断的默认删除允许沿原流程显式结清，不能恢复部分删除的数据；已删除状态不在升级或启动时自动复活。用户可点击“恢复默认助理（新建会话）”，服务核对原删除引用后持久化恢复意图，再复用默认初始化创建新的独立 Room／Membership，不继承原消息、规则或订阅，也不接管同名手动私信。恢复受阻或中断后继续原初始化，陈旧／重复恢复请求不重复创建。

最小记录可包含创建 ID、状态及完整 RoomIdentity，直接关联既有创建／删除日志；不另建后台任务系统，也不建立第二份默认 Agent 状态库。保留 ID 属于系统初始化用途，普通创建接口不能冒用。

默认 Agent **仅在首次成功初始化时保存启用意图**，打开后可处理用户消息；之后暂停、失败、Session 轮换、服务恢复均遵守现有语义，不在每次启动／选中时重新启用。自动创建和打开本身不投递虚构的人类任务，不发起模型回合、平台登录或外部操作。

模型／DSH 配置不满足创建条件时，显示准确的初始化阻塞及 `start init` 引导，配置补齐后核对并重试原默认创建操作；真实运行错误不伪装成模型未配置。默认助理初始化受阻不应阻断已有 Room 的使用。创建成功后模型 API 不可达，按普通 Agent 的失败状态处理，不重复创建替代实例。

默认只在没有有效历史选择时优先进入助理 DM。尊重用户上次选中的会话；初始化待完成时显示进度及重试入口，不反复跳转。欢迎语和建议问题属于 UI 引导，不保存为伪造的 human 消息，不作为 Skill 的用户授权依据。

## 5. UI 设计

### 5.1 导航与创建

保留现有三栏结构，左侧按「私信」「房间」分组，各自显示数量并按最近消息排序。默认助理在私信组首位，使用轻量的「默认」说明，不新建一个与它重复的顶部入口；旧版本已删除的实例显示显式恢复入口，不显示失效固定项。

私信用单 Agent 图标，房间用 `#` 或群组图标；同时使用分组和可访问文字，不能只靠颜色区分。创建使用一个「＋」入口，提供「新建私信」「新建房间」两项，避免多套重复按钮。私信默认内置助理角色；房间沿用团队选择。删除、加载、异常和重试文案随会话类型调整。

### 5.2 会话与详情

| 位置 | DM | Room |
| --- | --- | --- |
| 顶栏 | 会话名称、Agent 图标与运行状态 | 房间名称及原有房间操作 |
| 输入框 | 「给个人助理发消息…」；无需先 @ Agent | 沿用协作输入与提及 |
| 右侧栏 | 默认直接展示唯一 Agent 详情 | 保留成员列表，点击进入详情 |
| 详情导航 | 保留平台、活动、收件箱、规则等既有 Tab；无“返回成员列表” | 沿用列表／详情返回关系 |
| 成员控制 | 启用、暂停、恢复等照常；隐藏添加、移除成员 | 沿用现有控制 |
| 空态 | 助理职责简介和少量可点击建议 | 原有房间引导 |

首版沿用 Agent 详情默认「平台」Tab；用户切换后保留选择与滚动，不在每次刷新强制打开平台页。普通单成员 Room 仍走 Room 布局。将“自动选中 DM 唯一成员”与“用户手动打开详情”解耦，避免每次轮询重置请求、Tab 或焦点。

DM 的启用／暂停在顶栏或现有详情内可发现，默认启用不等于移除控制。小屏保留聊天主视图，通过单一「助理详情」入口展开详情，关闭后返回聊天，不默认遮挡输入框；复用已有响应式布局和键盘焦点规则。

页面标题、侧栏标题、输入标签、重命名、删除、重新开始、空态及无障碍文本统一采用相应会话用语。现有草稿、引用、未读提及、活动／Inbox 分页及切换后的迟到响应保护继续按完整身份隔离。

### 5.3 通知与设置

DM 默认突出助理的平台和 Inbox。会话消息流通知与 Agent Inbox 仍为不同目标，不合并、不双投、不改写旧订阅。

隐藏成员列表后，将原「房间通知」管理入口保留在 DM 的会话菜单，文案为「会话通知」，复用原组件与目标校验；关闭详情返回 DM 主详情，不跳到隐藏的成员列表。Room 保留原位置。平台来源跳转、异常订阅及高级设置都需能在对应布局定位，不因隐藏列表丢失入口。

全局「设置 → 平台」继续完整管理连接。对话授权与候选组件占用聊天内区域，右侧保持 Agent 详情，不将详情栏改造成常驻审批中心。

## 6. 接入 Skill 的配备与能力开放

复用 `teamx platforms skill` 以及内置只读 Skill 资源，不把整个方案文档塞入角色提示词，不复制出 Chief 专用的第二套连接流程。助理指令明确：遇到平台初始化需求先读取该 Skill，并以当前命令帮助和返回能力为准。

| 能力 | 与原方案的关系 | 助理可承诺的体验 |
| --- | --- | --- |
| 查询／连接飞书 | C1：连接 CLI 和基础 Skill | 发起授权、查询原操作、同回合短等或用户主动继续 |
| 搜索群并配置自身 | C2：成员配置 CLI | 按核验账号和候选 ID 配置，不擅猜同名群 |
| 聊天内授权交互 | C3：最小对话连接 | 授权按钮／二维码、可见进度和结果 |
| 内部事件与自动接续 | C4＋C5 | 授权结束后经 Inbox 续接；受启用、准入与预算约束 |
| 完整接入对话 | C6 | 在同一 DM 完成账号／群选择及设置，必要时转完整管理入口 |

只有已完成并验证的能力进入 Skill 与可点击建议；不能在 C1 阶段展示“自动关注群并唤醒”的可执行承诺。当前连接 Skill 中的临时授权链接处理需随 C3 交互引用方案收敛，不另建一套持久化授权内容。

统一流程：检查原操作／已有连接 → 根据明确需求连接 → 用户完成官方授权 → 核验账号及保存回执 → 按需搜索群、配置自身通知／工具 → 核对并反馈。用户只说“连接飞书”时只完成连接；默认助理创建不自动启用任何平台订阅、发送权限或额外工具。

身份、真实用户消息依据、固定操作 ID、版本检查、共享连接锁、未知结果恢复及凭据保护，全部沿用原方案服务端契约。使用默认角色、启用 Agent 或读取 Skill，均不能代替用户的业务指令。目标不明确时只澄清该目标，已明确且有权限的步骤不重复请求确认。

用户体验示例：

> 初次打开：进入「个人助理」，展示“我可以帮你梳理需求、连接平台和调整当前助理设置”。
>
> 用户：连接飞书，关注产品讨论群，需要我处理时在这里提醒我。
>
> 助理：核对已有连接，展示官方授权组件；授权完成后搜索群，必要时让用户选择；将通知配置给当前助理，回报实际账号、群、接收范围和未完成事项。

以上完整示例以 C6 为验收门槛。中间阶段只演示已开放步骤，长等待是否能自动续接必须准确说明。所有“完成”均来自服务回执；部分成功、连接成功但订阅失败等情况分别展示，不靠角色措辞掩盖。

## 7. 实施阶段与依赖

阶段编号只用于本方案和实施记录，长期代码与测试按领域／行为命名。

| 阶段 | 交付 | 验收出口 |
| --- | --- | --- |
| D1：DM 模型与创建 | 类型贯通、内置角色、独立 DM 创建、人数约束及旧数据读取 | 无团队目录也能创建助理 DM；相同请求不重复创建；旧单成员 Room 保持原类型，Room 创建和恢复回归通过 |
| D2：默认助理生命周期 | 一次性初始化、固定默认引用、首次启用、删除保护与历史恢复 | 新旧目录仅创建一次；崩溃按原身份恢复；暂停后重启不启用；默认不可删除，历史已删除实例仅显式恢复；无用户消息不启动模型或授权 |
| D3：DM／Room UI | 分组、创建、直接详情、文案、通知入口和小屏 | 真实浏览器能区分类型；默认选择可用且尊重历史选择；DM／Room 切换不串草稿、详情、Inbox 和交互 |
| D4：助理 Skill 整合 | 角色指引、基础 Skill 发现、已完成 C1–C3 的能力接入及准确降级 | 未绑定平台工具也能由助理发起连接；真实 Agent／飞书／浏览器连接成功，当前未支持步骤不误承诺 |
| D5：完整助理接入 | 随原 C2、C4–C6 完成群配置与三种接续整合 | 真实完成上一节示例，暂停、阻塞、晚到事件和高级设置回流均有准确结果 |

D1 → D2 → D3 构成可独立交付的 DM 与默认助理基础，不以平台方案全部完成为前提。D4 依赖 D1–D3 及原 C1；C3 尚未完成时可先验证官方链接与主动继续，但不能宣称对话组件验收通过。D5 复用原 C2、C4–C6 的交付与验收，不另算一套 Inbox 改造或连接引擎。

开发时先核对进行中的 C1 实现，沿用其最终操作／Skill 契约，不覆盖并行改动。可以先交付 D1–D3，再逐步接入平台能力；只有 D5 和原 C6 均通过，才宣称默认助理完整平台初始化体验完成。
