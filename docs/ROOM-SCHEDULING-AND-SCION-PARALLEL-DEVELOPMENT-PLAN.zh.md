## 1. 目标与范围

为 Room 提供两种成员回合调度模式：

| 模式 | 行为 |
| --- | --- |
| `serial` | 整个 Room 最多一个成员持有执行名额，其余按现有 FIFO 排队 |
| `parallel` | 所有符合条件的成员均可取得执行名额，每个成员仍最多一个回合 |

省略配置时保持串行。先实现并发调度，再新增并行软件开发团队，使用已有 `csgship` 平台账号验证 architect 拆解需求、多个 developer 同时在 Scion 独立工作副本中编码、发布任务分支并在 Room 交接。不同 Scion 身份留到闭环通过后按需采用，不作为本轮开发或验收的前置条件。

首版不提供数字容量、角色专属名额、服务全局配额、运行中切换或设置页面；不增加任务认领系统、Scion 通知轮询、自动账号签发、自动 approve／合入／关闭。现有软件开发团队继续采用串行流程。

本次是调度策略的局部泛化，不引入新的执行框架。Session、Workspace、消息存储及工具生命周期先沿用现有实现；测试发现依赖全房间串行的具体问题后，再做对应的最小修复。

## 2. 当前依据与改动位置

| 位置 | 当前行为 | 拟议调整 |
| --- | --- | --- |

| [teams.go](../internal/room/teams.go) | 读取团队，创建 Room 配置及资源快照 | 读取、校验并冻结 `scheduling` |
| [management.go](../internal/room/management.go) | `managedRoomConfig`、初始化和持久快照校验 | 保存模式，接受旧快照缺省串行，拒绝非法值 |
| [recovery.go](../internal/room/recovery.go)、[runtime_assembly.go](../internal/room/runtime_assembly.go) | 服务配置与受管 Room 恢复装配 | 将已保存的模式传到调度器 |
| [turn_scheduler_test.go](../internal/room/turn_scheduler_test.go) | 串行公平性、取消、退出、Session 打开和关房等测试 | 保留串行回归，补并发与混合房间用例 |

当前 MemberAgent 由 Room 未读或 Inbox 待处理共同唤醒，两者共用同一 Session 与调度器。因此模式作用于整个 Room 的成员回合，也覆盖 Inbox 触发的回合，不按来源拆分名额。

Room 业务状态仍由 Room Actor 有序提交。成员 Session／状态目录以 membership 隔离，Workspace 也是独立目录。Scion 调用使用所选平台的私有凭据副本，调用前核对实际 subject；这些基础无需因并发模式另建一套。

核心调度修改主要集中在调度器及服务装配；完整产品配置还需要上述读取、保存与恢复链路。生命周期是回归重点，不预设所有相关模块都要修改。

## 3. 配置与兼容

### 3.1 唯一配置入口

在团队 `team.json` 顶层增加字符串字段：

```json
{
  "scheduling": "parallel"
}
```

这只是字段示例，不是完整团队定义。采用统一的模式类型和校验／缺省解释函数：省略或空字符串解释为 `serial`，显式值只接受 `serial`、`parallel`；拼写错误、大小写变体和其他类型拒绝，不静默回退。

这是 Room 调度属性，不放入模型／DSH 配置，不作为模型或 Session 的恢复指纹。首版不增加服务级开关、成员环境变量或独立 CLI 参数作为第二配置来源。

### 3.2 创建与恢复

```text
team.json.scheduling
  → teamDefinition
  → 创建时 managedRoomConfig.Scheduling
  → room-config.json／初始化回执
  → runtime_assembly → serviceConfig
  → turnScheduler
```

- 新建 Room 保存明确的有效模式，包括缺省得到的 `serial`。
- 已有快照没有该字段时按串行读取，不要求批量迁移或重写旧文件，不因新增可选字段单独升级存储版本。
- 启动与恢复先校验模式，再启动成员；非法快照失败，不用串行掩盖损坏。
- 模板修改只影响重启加载模板后新建的 Room；已有 Room 始终使用其创建快照，即使模板被删除。
- 私聊及没有团队模式的现有装配路径默认串行。
- 成员增加／移除不改变模式；并发模式不缓存“创建时成员数量”作为容量。
- 检查 Workspace 应用、重启讨论、模型更新等配置复制和重写路径，确保保留字段。检查 `equalWorkspaceRoomConfig` 与初始化／操作回执中的配置比较，避免读时规范化旧文件导致原本相同的快照被判不一致。
- 不持久化持有者集合或等待队列；重启继续遵守现有中断回合和 Session 恢复规则，不据此自动重放业务写入。

首版运行中不能切换模式。需要另一模式时创建新 Room，不手工改正在使用的配置快照。

## 4. 调度器的最小改造

### 4.1 数据与授予

保留现有 `members`、FIFO `queue`、申请编号及消息类型，将单个 `holder` 改为以完整 `MemberIdentity` 索引的持有者集合。集合记录本次申请及其编号，不用裸 agent 名称作键。

```text
serial：无持有者时，从队首授予一个申请
parallel：将当前有效等待申请依次加入持有者集合，并发出授予
```

授予发出前先登记持有者。投递失败仍保留责任，由既有维护过程重发相同授予；并发模式中，一个成员邮箱暂时满不阻止其他有效成员取得名额。保留一个 Room 维护任务，不为每个持有者增加定时器。

`parallel` 不需要计算成员总数或剩余容量。调度 Actor 依次处理申请，成员取得授予后的 Session 打开、模型调用和工具执行可重叠；这不构成全员同时启动的屏障。

### 4.2 必须保留的规则

1. **单成员不重入。** 同一 membership 在请求、核对或运行中只有一个有效申请／回合；持有期间收到更大申请编号也不能覆盖当前申请记录。
2. **精确释放。** 只有匹配成员身份和申请编号的释放才能移除持有者；重复、迟到的授予／释放不能影响后续回合。
3. **取消不等于结清。** 排队申请可以撤回；已授予申请不能仅因取消信号释放。成员确认未启动或执行与清理已结束后，才发送释放。
4. **退出逐个回收。** 维护过程确认某 Actor 已退出后，只回收该成员的等待／持有记录，不影响其他执行者。
5. **关闭先冻结。** `frozen`／`closing` 阻止新授予；Quiesce 清空等待申请但保留未结清持有者。服务仍须等待全部成员、工具和清理完成，才释放 Room／Store 归属。
6. **最新资格核对。** 保留 `Granted`／`StartGranted` 对成员代际、启用状态、输入和轮换条件的核对；排队不消耗模型回合或预算。
7. **公平性和隔离。** 串行模式保留 FIFO 与执行后重新排队；不同 Room 独立选择模式。一个成员失败不应冻结并发房间内其他健康成员。

不拆分为两个调度器，也不移除并发模式的授予／释放协议。持有者集合用于跟踪执行归属和结清，不能因为“全员可运行”就省掉。

## 5. 消息、任务和生命周期边界

### 5.1 消息仍有序提交

多个成员可以同时读消息、编码和请求发言；Room 消息序号、已读确认和持久提交仍走现有协议，不改成并发覆盖同一份状态。

当前 `Room.writable` 在提交期间返回 `ErrBusy`，CLI 发送失败会保留消息 ID，但没有对这个业务 busy 的自动重试。需要用并发用例验证发言和已读确认竞争：

- busy 必须可识别并能恢复，不丢失交付，也不错误推进游标。
- 如实测影响正常协作，优先复用现有回执，在相应调用入口增加针对明确 busy 的有界等待／重试；发送始终复用相同消息 ID、正文与目标，已读确认沿用其 receipt 规则。
- 不通用重试所有 HTTP／平台写入。网络中断或写入结果未知仍按既有协议核查，不能换新 ID 重发。
- 不为本方案预先重写 Room 存储、引入通用消息队列或更改读取协议；具体修复以失败用例为依据。

### 5.2 调度不承担任务分配

模式只决定执行能否重叠，不保证谁先读到消息、谁先发言、谁拥有任务，也不保证所有人基于相同的最新上下文行动。提及仍是共享消息中的受众提示，不是服务端独占路由。

首轮由 architect 发布完整任务表并指定负责人，developer 只执行自己的任务。独立任务并行；依赖任务必须取得前置任务的准确交付版本后开始，不以同伴一句“完成”代替依赖交付。

自主认领、原子抢占、动态重分配另行评估，不加入调度器。

### 5.3 生命周期沿用并验证

单成员暂停、删除和 Session 轮换应只结清相应成员及相关工具调用；房间级 Workspace 应用、重启讨论、退出等操作按既有门禁处理所有受影响成员。共享平台账号或认证配置变更仍结清实际引用它的调用。

保留原有故障恢复、轮换和状态显示。对多个 active 成员进行验证，不先引入新的生命周期状态机。模型限流、网关实际并发限制及外部工具内部串行要单独记录，不能把调度授予成功表述为后端并发验收通过。

## 6. 最小并行开发测试团队

### 6.1 新建模板，不改原团队

以 [.teamx/teams/software-development](../.teamx/teams/software-development/README.md) 为参考，新增 `.teamx/teams/scion-parallel-development/`，包含独立 `team.json`、README 和角色提示词。原团队继续保持原流程。

新团队建议四个成员：`architect`、`developer-a`、`developer-b`、`developer-c`；设置 `scheduling: parallel`。三个开发成员可以引用同一份通用 developer 提示词，以当前成员 ID 和任务表确定负责范围，不把它们都硬编码为同一个 developer。

原软件开发提示词要求逐阶段评审，并让 developer 等待设计无阻塞结论；不能原样复制后只增加成员。新测试模板应明确：

- architect 根据用户需求拆分独立任务，给出任务 ID、负责人、修改范围、接口约定、依赖和完成标准，发布带版本的设计／任务表；本轮由 architect 主持拆解，不沿用“简单任务直接由唯一 developer 接管”的规则。
- developer 只执行分配给自己的任务，无独立任务时保持沉默；拿不准时在 Room 问清楚，不重复同伴的工作。
- 设计优先通过发布后的文档提交交接；平台发布暂不可用时，在 Room 提供带版本的完整必要设计，不能只给同伴本地路径。
- 本轮不设置 reviewer，不保留“等待不存在的 reviewer 放行”的条件；成员测试通过后交付，明确这是并发编码测试，不冒充完整独立评审流程。
- 所有任务交付后由 `developer-a` 在独立集成任务分支核对、集成各版本并运行整体验收；该职责不授予合入目标分支的权限。architect 核对需求覆盖，业务取舍交用户。

公开消息以实际变化为准，不轮流报“收到”、重复任务表或催促其他成员。参考交付格式：

```text
[任务完成] T2 / developer-b
仓库：OpenCSG/teamx-demo
分支：teamx/<room>/<membership>/T2
设计版本：<文档完整原生 ID 或 Room 消息版本>
发布版本：<完整 Scion head>
完成：……
验证：……
依赖／未验项：……
```

源码模板入口是当前服务实际加载的团队目录：仓库开发通常为 `.teamx/teams/`，安装通常为配置旁的 `teams/`。不要直接编辑 `teamx-space/share/...` 等生成副本。若需要让新模板随发行包提供，再更新 `packaging/bundle-files.json` 的显式清单；本地测试不以重新打包为前提。

### 6.2 Scion 平台、身份与工作副本

Scion 与 GitLab、飞书共用具体平台模型：一个具体平台代表实例上的一份明确账号接入，成员通过 `platform_id` 绑定该平台。首轮所有测试成员绑定已有的同一个 Scion 平台，实际 subject 为 `csgship`；不需要创建三个平台或多份 PAT。`CLIProfile` 是平台内部的认证引用，不另建公共“连接”实体。配置入口为“全局设置 → 平台”，成员入口为“Room → 成员 → 平台”。

身份分为两层，实施时分别记录，不用成员名称或提交署名推断远端账号：

| 身份 | 用途 | 核验依据 |
| --- | --- | --- |
| TeamX 成员身份 | 确定成员代际、Session、Workspace 与工具绑定归属 | 完整 RoomIdentity、agent ID、membership ID |
| Scion 平台身份 | 确定远端请求的实际操作者及其权限 | 所选平台及其 profile 经 `scn whoami` 核实的 subject |

首轮允许多个 TeamX 成员映射到同一个 Scion subject：

```text
architect、developer-a、developer-b、developer-c
  → 各自 membership 的工具绑定
  → 同一个 Scion 平台／受管 profile
  → csgship
```

- 复用已有平台及登录。每个执行 Scion 命令的成员仍须分别绑定并启用工具；共享账号不会自动授予成员工具能力。
- 每个 membership 保持独立 Session、Workspace 和 `.scion` 状态，任务分支名包含 Room、membership 和任务标识。这些隔离是并发编码的必要条件，与平台账号是否共享分开核验。
- 从各成员正常工具入口运行 `scn whoami`，本轮预期均为 `csgship`；核对实际实例、仓库权限和绑定，不要求 subject 互不相同。
- 提交时为各成员明确不同的 `--author`，便于辨认代码贡献；远端认证与发布操作主体仍然是 `csgship`，不能把署名差异当成平台身份隔离。
- Workspace 初始化使用的平台与成员日常工具绑定的平台分别配置；本轮可以选择同一个平台，但初始化不会自动启用工具。
- 凭据由现有受管 profile 管理，不放进团队文件、Room 消息或成员环境。平台账号已有目标仓库开发权限即可，本轮不需要系统管理员权限、不签发新主体、不修改全局 ACL。

以后需要独立权限、独立操作审计或不同身份的正式评审时，再按第 7.4 节切换到多个 subject。共享账号并发验收可以正式完成本轮目标，但不覆盖多身份隔离。

固定使用当前接入的 `scn 0.1.13`。developer 在自己的任务分支明确作者、指定文件 commit，再用 `scn land` 发布；发布后重取实际 head，若发生重写则核对内容并补测。`scn review land` 是 Review 合入，不在本轮流程内。

不要求创建 Review、轮询 Scion Inbox／评论或等待通知回流。完成后直接通过现有 TeamX Room 发送交付消息即可；Scion 通知接入仍由[独立方案](SCION-NOTIFICATION-INTEGRATION-PLAN.zh.md)处理。

## 7. 实施顺序与验收

本轮分为三个必做阶段，依次完成调度、team 示例和共享账号下的真实并发编码闭环。不同身份是最后按需进行的可选扩展，不阻塞前三阶段完成。

| 阶段 | 交付范围 | 完成条件 |
| --- | --- | --- |
| 1. 调度能力 | 调度核心、配置保存与恢复、必要的并发问题修复 | 串行回归、并发、防重、生命周期、配置恢复及 race 测试通过 |
| 2. team 示例与环境配置 | 新团队模板、角色指引、使用说明；所有测试成员绑定现有 Scion 平台 | 模板可加载并创建并发 Room；共享 `csgship` 账号、独立成员绑定、工作副本与基线核验完成 |
| 3. 共享账号真实并发验收 | DSH＋Scion 编码、发布、Room 交接和集成验证 | 实际执行重叠，远端版本正确，操作主体符合共享账号预期，整体验收通过 |
| 后续可选：不同身份 | 为成员选用不同 subject 的具体平台，验证身份隔离 | 各成员实际 subject、权限、操作归属及重新运行结果与预期一致；不计入本轮完成条件 |

本轮环境准备只需要已有 `csgship` 平台可用、具备测试仓库所需开发权限，以及模型和项目测试工具可用。实际写入前明确目标仓库和可写任务分支范围。无需协调管理员创建多个身份；账号签发、系统权限变更及新的凭据系统均不加入调度开发。

调度和模板开发不依赖新增账号。已有平台或模型暂不可用时，单独报告代码／模板完成及实际环境待验；不同身份尚未准备不会使已通过的共享账号并发验收变成未完成。

### 7.1 阶段 1：调度核心与配置

先完成模式类型、持有者集合、授予／释放／退出回收，再贯通 team → 创建快照 → 恢复装配。默认串行保持现有测试通过，增加以下行为测试：

| 场景 | 必须证明 |
| --- | --- |
| 三成员并发 | 用可控 Backend 阻塞各成员，在任何一个结束之前三个都进入执行；单纯观察三条完成消息不算并发证据 |
| 串行回归 | 同条件下最多一个执行，FIFO 和重新排队行为保持 |
| 防重与迟到消息 | 重复申请／授予不重复打开 Session；旧释放不能结束同成员的新回合，其他持有者不受影响 |
| 取消与退出 | 未结清的成员仍保留执行归属，其他并发成员可继续；Actor 退出准确回收 |
| 暂停／删除／轮换 | 操作只影响目标成员；未启动的授予被撤回，不影响其他成员和预算 |
| 关房与清理失败 | 冻结后不启动新回合，等待所有执行者／工具；未结清不能释放资源归属 |
| 输入与发言 | 多成员读取／确认、同时发言和中途新增消息不丢失、不重复、不越过未确认内容；明确 busy 能恢复 |
| 配置与恢复 | 缺省串行、非法值拒绝、模式随创建冻结；模板变化／删除、服务重启及 Workspace 配置重写后仍保留模式 |
| 房间与成员隔离 | 同时运行串行和并发房间；并发房间动态增加成员无需改容量；同成员 Room／Inbox 回合不重叠 |

测试通过受控通道／屏障证明执行重叠和结清顺序，不用长 sleep 或时间碰巧重叠代替断言。保留既有测试入口，新增测试按行为命名，不以实施阶段编号命名。

按当前测试标签安排验证：

```sh
go test ./internal/room -run '^(TestTurnScheduler|TestRoomTurns|TestRoomSlot|TestServiceShutdown|TestTeam|TestRotation)' -count=1
go test -race ./internal/room -run '^(TestTurnScheduler|TestRoomTurns|TestRoomSlot|TestServiceShutdown|TestTeam|TestRotation)' -count=1
go test -tags=integration ./internal/room -run '^TestManagedTeam' -count=1
```

新增用例若不匹配这些前缀，须加入实际选择范围；上述命令是实施后的验证建议，本文未执行。配置复制和恢复测试应覆盖具体受影响路径，不把测试函数名前缀当作完整覆盖证明。

调度器和配置链路共同构成一个可使用、可恢复的功能，不再拆成两个独立交付阶段。取消、关房与消息竞争验证在本阶段完成，不推迟到真实 Scion 验收。

### 7.2 阶段 2：team 示例与环境配置

已于 2026-11-13 完成；模板、真实四成员绑定、共享账号和独立副本核验结果见[阶段 2 实施记录](implementation/scion-parallel-environment.zh.md)。以下保留本阶段的实施及验收边界。

阶段 1 通过后，按第 6 节新增团队及说明；本阶段不启动真实编码任务，不为验证模板而发布代码或制造评论。

模板开发的出口：

- 团队具有唯一 ID 和四个独立成员 ID，加载、校验与创建快照测试通过，新建 Room 的模式为 `parallel`。
- architect 拆解、明确分配、依赖等待、开发者交付及最终集成职责完整；不保留不存在的 reviewer 或全房间逐阶段串行等待条件。
- README 写明共用已有 Scion 平台、成员分别启用工具、独立 Workspace、交付格式及验收方法；模板与资源不包含凭据或某个测试 Room 的绑定数据。将不同身份标为后续可选，不要求先完成账号申请。

共享平台绑定／环境准备的出口：

1. 复用现有 Scion 平台，在正确 Room／membership 上为各成员分别绑定并启用工具；不复制 PAT、不创建多份相同账号的平台记录来模拟不同身份。
2. 通过各成员正常工具入口执行 `scn whoami`，确认均为预期的 `csgship`；只检测操作者全局账号或平台展示名称不算通过。核对账号对测试仓库的必要开发权限，不通过试写未知目标探测权限。
3. 使用现有 Workspace 初始化流程准备独立工作副本，核对实例、canonical repo、基线及本地路径归属；初始化使用的平台不覆盖成员日常工具绑定。
4. 记录非秘密的成员／平台映射和核验结果，实际写入前再次核对目标与范围。为各成员明确提交 `--author`，同时注明它不是独立平台身份。

这部分使用已有真实账号和已明确的仓库操作范围。凭据不可用或仓库开发权限不足时保留模板交付，标记环境准备待完成；不要转为申请全局管理员权限。正常绑定／初始化可能涉及本地登录记录和工作副本，不等同于开始远端编码写入。

### 7.3 阶段 3：共享账号真实并发验收

已于 2026-11-13 完成，详见[实施与验收记录](implementation/scion-parallel-acceptance.zh.md)。developer-b／developer-c 的真实编码至单项测试通过区间重叠 1.949 秒；三项交付及集成 head 经独立远端核对，62 项整体验收和外部契约检查通过。误建 `list` 分支先记为范围偏差，经用户明确授权清理后完整复验通过。没有浏览器验收，不声明三人同时编码或不同身份隔离。以下保留本阶段验收要求。

阶段 1、阶段 2 通过后，使用已准备的新 Room、共用的 `csgship` 平台和明确允许写入的测试仓库／任务分支范围执行真实验收；不要直接重跑原串行协作测试并声称覆盖了并发。

1. 复核各成员均绑定预期共享平台，检查实例、仓库、独立 Workspace、基线和独立任务分支，确认没有账号切换或权限变化。
2. 选择能拆成三个独立模块、有可运行测试的需求；约定接口与文件边界，architect 发布任务表后让三个 developer 开始。
3. 记录实际回合起止及工具执行证据，证明至少两个开发成员的真实执行区间有交集；若声称“三开发者同时编码”，须给出三者共同重叠的证据，不能只依据先后发出的消息。
4. 核对三个成员均在正确副本／任务分支发布，远端内容、完整 head、提交署名与交付一致，实际平台账号均符合 `csgship` 的预期；不只采信 agent 自述，不声称远端能据此区分三个认证主体。
5. 在 Room 收到完整交付；`developer-a` 取得准确版本，在集成任务分支验证组合结果并报告。不能用互不关联的三个单项测试代替整体验收。
6. 核对正常退出／重启后模式与已发布交付仍可识别；不重发业务写入来验证恢复。

每轮报告分别列明组件／race、真实 DSH、真实 Scion 和浏览器证据，明确账号模式为“共享身份”。首版无需新增 UI，程序化创建和检查可用于验收；没有实际浏览器操作就不标为浏览器验收通过。共享账号下的实际并发、发布和集成通过，就是本轮正式验收通过，不降格为必须等待独立身份才能完成的“预验”。

不同任务分支上的并发通过后，可另设实验测试同一 ref 并发发布、重叠文件、rebase 和冲突。第一轮不把这些压力场景、自主任务认领或强版本保证的 Review 合入作为完成条件。

### 7.4 后续可选：按需改用不同 Scion 身份

仅在需要区分平台操作权限、审计主体或不同身份的正式评审时开展。前三阶段通过后，可以直接结束本轮实施，不要求完成此项。

1. 准备已有的不同账号，或由 Scion core 系统管理员为不同 subject 签发服务凭据并授予测试仓库权限。`scn token create` 为同账号创建多个 PAT 不会产生不同身份；当前跨主体签发仍依赖系统管理能力。自动身份委派、自动开户或 Scion 本身的权限产品改造另行设计，不加入本方案核心逻辑。
2. 通过现有平台登录流程保存各账号的受管 profile，为不同 subject 建立不同的具体平台；使用稳定且不冲突的 subject 命名，只记录非秘密的成员／平台映射。
3. 在已结清的测试环境中通过正常成员平台设置分别替换绑定，或创建新 Room 配置；不直接修改凭据文件，不覆盖现有平台的其他成员引用。
4. 从每个成员工具入口核对 `whoami`、预期 subject 和仓库权限；此时才要求各测试主体互不相同。工作副本、提交署名和远端认证身份继续分别核对。
5. 在明确的写入范围内复跑必要的编码／发布场景，验证身份归属、权限隔离、Room 交付和集成。若包含正式评审，另按其能力和授权边界验收，不顺带启用自动合入。

独立身份凭据仍只经现有登录入口管理，不进入团队文件或 Room 消息。外部签发权限或账号准备阻塞只影响此可选项，不影响前三阶段已经完成的结论。

## 8. 完成定义

完成调度功能需满足：两种模式可由团队配置并随 Room 恢复；旧房间默认串行；并发成员独立执行且保留精确结清；必要组件、竞态、配置与生命周期测试通过。

完成测试团队准备需满足：模板开发通过，各成员分别绑定现有共享 Scion 平台，正常工具入口身份均为预期的 `csgship`，独立工作副本／基线与任务分支安排已核验。模板可用、实际绑定和环境就绪分别报告。

完成本轮 Scion 并发编码目标，还需新团队真实运行、多个开发者实际重叠执行、远端交付、共享账号核对、Room 消息交接及最终集成验证。本轮完成不依赖不同 subject、跨主体签发或系统管理员权限。已有账号的仓库开发权限或模型服务阻塞仍需明确报告，不能把只完成调度代码或模板开发当作实际并发通过。

后续多身份测试单独报告，只有按第 7.4 节核验不同 subject 及其权限／操作归属后，才能声明身份隔离通过；共享账号下的提交署名差异不构成该证据。

阶段 1 仅交付调度、配置与相应验证，不创建上述团队或账号、不修改现有运行房间、不启动真实模型回合、不写入测试仓库，也不提交或推送代码。后续实施继续以本文的阶段 2、3 边界为准。
