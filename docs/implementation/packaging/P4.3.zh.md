## 工作流

1. 推送干净 `vX.Y.Z` tag，由 `release.yml` 构建全部 8 项候选并在原生 runner 下载复验。无真实验收时生成 `incomplete` 报告，候选 job 可成功结束；损坏／身份错误仍失败。这只表示候选构建与传递成功。
2. 收集同一批候选的人工验收，准备下述公开 JSON。签名／公证不是当前必需项，macOS 仍要记录带 quarantine 的实际下载与用户允许运行过程。
3. 在同一个 tag 上手动触发 `release-publish.yml`，指定候选 run ID、完整运行的 attempt 和人工 JSON。运行来源必须是当前仓库的 `release.yml`、`push` 事件、同一 tag/commit，且最新 attempt 已成功。所有 16 个候选／下载复验 artifact 均须唯一存在、未过期；其他仓库／workflow、过期产物、缺项和旧 attempt 均拒绝。
4. 发行 Workflow 下载原候选，在匹配平台重新核对身份及 smoke，再用包内真实 DSH 和生产页面执行已有 `package-acceptance.sh`。验证机 Go/Node 和 Playwright 是验证器工具，服务 PATH 继续隔离。8 项矩阵最多并行 2 项，不恢复构建缓存，不重建候选包。
5. `assessCandidate` 校验本次私有证据的归档、manifest、依赖、源码、原生架构、验证器及所有子报告摘要，合并对应归档的人工记录。真实 DSH／浏览器、干净机器、下载后的系统安全全部必需，full 另需 Git/TLS/clone/commit 与 GitLab/飞书登录／只读／绑定。完整时才返回 `passed` 和 `release_ready=true`；未执行／部分成功仍退出 2，坏证据退出 1。
6. 独立汇总 job 再检查全部矩阵和报告，生成发行材料及全资产 SHA256SUMS；独立发布 job 才获得 `contents: write`。创建 draft、上传原归档、逐项下载远端资产计算摘要，确认完整后才公开。签名／公证、归档、运行时和 manifest 都不会在汇总／发布时被修改。

版本 tag 工作流没有发布权限，也不需要模型和平台凭据。只有手动发行工作流运行真实模型；平台账号仍由维护者在隔离环境手动验收，不放进 Actions。GitHub Environment 可限制 tag 与 secrets，是否配置人工审核由仓库设置决定，本实现不强制额外审批。参考 [GitHub 跨运行下载 artifact](https://github.com/actions/download-artifact#download-artifacts-from-other-workflow-runs-or-repositories)、[Workflow Run API](https://docs.github.com/en/rest/actions/workflow-runs) 和 [Playwright CI 安装](https://playwright.dev/docs/ci)。

## 首次配置和触发

这三个 Workflow 文件须先进入 GitHub 默认分支，发行代码也须包含在候选 tag 的 commit 内；本地工作区未提交文件不会触发 Actions。应在 GitHub 仓库操作，不能仅推送到 GitLab。

在仓库或 `release-acceptance` Environment 的 Secrets 中配置：

- `TEAMX_RELEASE_MODEL_CONFIG`：测试 TOML，至少含有效的 `[runtime.model]` 配置。`protocol`、`base_url`、`model_id` 按测试提供方填写，`api_key_env = "OPENAI_API_KEY"`；按需保留 reasoning／兼容选项，不复制本机 Room、平台连接和其他凭据。
- `TEAMX_RELEASE_MODEL_API_KEY`：测试模型 Key，在模型服务商控制台创建，须有 runner 可达的服务地址与足够额度。

通过 GitHub 仓库 Settings → Secrets and variables → Actions，或对应 Environment 的 Secrets 添加；密钥不进入代码、触发参数或聊天。模型配置和模型 Key 只在真实验收步骤传入，私有日志、Session、截图和回答不上传 artifact，步骤结束无条件清理。

发行 Workflow 使用 GitHub 自带 token，读取候选所需 `actions: read`；只有最终发布 job 有 `contents: write`。无需另建 PAT 或 Apple 凭据。Playwright 固定 1.61.1，npm 完整解析及 integrity 位于 `packaging/verifier/`；验证机在临时目录 `npm ci`，下载 Chromium 及所需系统库，不把它们打进用户包。

```sh
# 使用 GitHub 仓库与真实版本；RUN_ID / ATTEMPT 来自已成功的候选运行。
# -F 从文件读取公开 JSON，不把多行 JSON 拼进 shell。
gh workflow run release-publish.yml --repo OWNER/REPO --ref vX.Y.Z \
  -f candidate_run_id=RUN_ID -f candidate_run_attempt=ATTEMPT \
  -F qualifications=@/absolute/public-qualifications.json
```

也可先不提供 qualifications 运行自动验收，缺项报告会公开列出，发行停止。每次重新运行验收都消费模型额度。Artifact 保留 30 天；过期后必须重建候选并重新绑定验收，不能借其他运行的同名文件补齐。

## 人工记录协议

人工记录是**维护者对实际操作的确认**，与自动检查分开记录；校验器能核对身份、观察项和私有证据摘要，不能代替维护者判断操作是否真实完成。只能由可信维护者使用手动 Workflow 提交。

先从对应候选生成未验收模板：

```sh
node scripts/package-release.mjs qualification-template \
  DOWNLOADED_CANDIDATE_DIR TARGET PROFILE FULL_COMMIT vX.Y.Z NEW_QUALIFICATION.json
```

模板默认所有项 `not_run`，观察值为 false，时间和证据摘要为空，直接提交会失败。测试机原生 OS/arch 和实际系统基线须与 environment 相符；模板中的目标值是待核对条件。执行每项检查，保留私有证据，计算证据文件／归档 SHA-256 后填写对应 `evidence_sha256`、实际 UTC 时间 `tested_at`、`status=passed`、`fixture=false`、`method=maintainer_manual` 与观察值。最终 JSON 顶层格式为：

```json
{
  "schema_version": 1,
  "version": "vX.Y.Z",
  "commit": "完整40位commit",
  "records": []
}
```

将各模板中的 record 合并到同一 records 数组，不重复 target/profile；归档 SHA-256 不得修改来匹配重建包。JSON 只填固定观察项及证据摘要，不放账号、主机路径、模型内容、日志、截图或密钥。公开 assessment 再经过固定字段投影，不保留额外内容。

| 检查 | 实际验证与固定观察项 |
| --- | --- |
| `clean_machine` | 全新解压、独立 home、没有宿主 Go/Node/平台 CLI、系统依赖满足声明基线；full 还没有宿主 Git。验证器需要的开发工具不能充当用户运行环境证明 |
| `downloaded_system_security` / macOS | 实际下载带 quarantine、保留隔离属性，记录 `first_launch=blocked/allowed`；被阻止时通过系统允许运行，记录 `user_approved=true`，最终能启动。不能把移除 quarantine 当作验收 |
| `downloaded_system_security` / Linux | 在声明系统上运行，检查实际动态库及所需运行能力均在基线内 |
| `git_tls_clone` / full | 使用包内 Git，没有宿主 Git；真实 helper、验证证书的 HTTPS clone、本地 commit 全部完成 |
| `platform_login_read_bind` / full | 使用隔离账号完成 GitLab 与飞书登录、只读查询和 TeamX 连接绑定，远端写入为 0 |

缺少某个 record 或某项检查会保留缺项。纯 `passed`、fixture、错包、错误架构／基线、缺少详细观察、未知检查、重复目标及未来时间均拒绝。不提供跳过 full 或把外部人工检查改称自动检查的开关。

## 发布资产及恢复

每个包保留原 `.tar.gz`、`.tar.gz.sha256`，额外生成对应 `-assessment.json`。全局资产为 `release.json`、`SHA256SUMS`、`LICENSES.tar.gz`、`README.zh.md` 和 `release-notes.md`。

`LICENSES.tar.gz` 汇总各归档自身的 LICENSE 和 THIRD_PARTY_NOTICES；完整 Git 对应源码仍在各 full 原归档中，不重复复制到汇总许可包。运行时附带的其他许可仍在原归档中。独立使用说明涵盖首次使用、未签名 macOS 的系统提示、声明系统基线，以及保留旧 runtime 路径的升级限制。

候选包内的 `manifest.distribution.release_ready=false` 保留构建时事实；发行资格由外部 `release.json` 和绑定该候选归档摘要的报告确认。没有为了修改状态重新归档，也没有改变已验收字节。

发布前后都核对远端 tag，附注 tag 逐层解引用到同一 commit。先创建 draft；已存在的公开 Release 或其他资产的 draft 拒绝覆盖。同一 draft 只有版本、commit、说明及 checksum seal 完全一致时才允许恢复，已有资产先下载校验，再只补传缺失资产，不用 `--clobber`。上传后再次下载全部资产并计算 SHA-256；远端摘要错误、缺失／多余资产、改动的本地文件或移动的 tag 都阻止公开。

发布 job 失败时可在**同一发行运行中仅重跑失败的 publish job**，消费原汇总 artifact 与原 seal；中间 draft 保留供检查。验收或汇总失败时应完整重跑 Workflow，避免混用 attempt。新的验收运行生成新 context 和 seal，不能覆盖之前不同 seal 的 draft；需检查并由维护者显式处理旧 draft 后再发起新发行。公开动作响应不明时也先检查远端状态，不自动覆盖已公开版本。
