# 存储架构

Room 时间线保存一份公共正文，每名成员独立确认自己的读取进度。平台通知投向成员的私有 Inbox 或共享项目 Inbox，正文按 provider 分区，同一分区可以交错保存多个逻辑流。成员的执行协调、平台消费和来源关联分别持久保存。

## 权威与所有者

| 内容 | 唯一写入者 | 发布及恢复依据 |
| --- | --- | --- |
| Room 成员、公共消息、原生游标和同页证明 | Room Actor | `room.json`，包含日志发布范围及 `ReadProofs` |
| 私有 Inbox 正文、去重回执和回收边界 | MemberInputActor | 各 provider 的 `partition.json` 及成员容量预留 |
| 共享项目正文、冻结接收集合、Grant、页保护和配额 | InboxActor | `shared-inboxes/project/partition.json` 与已发布段 |
| 共享按流检查点、跳过和同页证明 | 各成员的 MemberInputActor | `agents/<membership-id>/shared-input/project.json` |
| 平台按流检查点、跳过和同页证明 | 同一个 MemberInputActor | provider 的 `consumption.json` |
| 输入执行、额度、固定页、结果及恢复状态 | MemberInputActor | `input-state.json` 和 `input-results/`；`agent.json` 仅保存引用 |
| 来源订阅、待投递与来源确认 | 每 Room 的 NotificationActor | `notifications/` 下各订阅快照 |
| 来源关联、跟进、授权和动作结果 | 原业务模块 | 成员的跟进目录；不以输入消费推断业务办结 |

`MemberInputActor` 的受理消息分别携带 Inbox 身份和消费成员身份。私有映射目前使用 MembershipID，保留既有分区、DeliveryID、stream_ref、source_ref 和磁盘格式。`internal/inputstream` 通过正文、成员消费、执行协调和回收四组普通 Go 能力供 owner 调用；provider 解释和执行权限仍由领域适配器核验。共享项目 Inbox 的正文 owner 按 InboxID 唯一，配置与预览入口见 [Agent 收件箱](inbox.zh.md#配置共享项目收件箱)。

成员 owner 在 Store 内预留并加载，每个 Membership 只有一个实例；service 复用该地址。存储变更在受控 task 中串行，最多保留 64 个未结清请求；相邻维护请求合并为一个后续批次。材料下载、来源解析及来源释放核验在存储变更槽之外等待。业务关联适配器在 Store 的局部锁内只读取已发布正文或证明，不另建 writer。Inspect 读取原子安装的投影，不扫描正文、执行维护或等待 Store 的文件 I/O。

## 磁盘布局

下列路径相对于单个 Room 目录：

```text
room.json                                  # Room 发布根、成员、原生读取证明
room-input/records/<segment>.jsonl          # Room 消息与交互事件
notifications/<provider>.<channel>.<id>.json # 来源订阅及待投递
inboxes/<membership-id>/<provider>/
  partition.json                           # 发布范围、摘要、去重及回收意图
  records/<segment>.jsonl                  # 平台正文
  consumption.json                         # 按流检查点、跳过及确认凭证
shared-inboxes/project/
  partition.json                           # Grant、配额、发布范围、回执及持久页保护
  records/<segment>.jsonl                  # 共享正文与冻结 Grant 接收集合
agents/<membership-id>/
  shared-input/project.json                # 该成员的共享按流消费、跳过及同页证明
  agent.json                               # 回合及 input-state.json 引用
  capacity.json                            # 跨平台容量与未结清追加预留
  input-state.json                         # generation/turn/call/page 和额度
  input-results/<page-id>.json              # 可重新交付的文字及原生图片结果
  input-preferences.json                   # 来源关注度与目录曝光
input-upgrade.json                         # 旧输入自动升级进度（发生升级时）
input-upgrade/<id>/backup/                  # 转换前文件与备份清单对应的备份树
input-upgrade/<id>/staging/                 # 未完成转换的临时发布树
```

Room 的唯一发布根是 `room.json`。日志文件中完整但尚未由根发布的尾部不构成新消息；纯游标或证明更新复用已发布段，不重写公共正文。平台的发布根、消费文件与协调器仍使用各自已有格式。Room、私有及共享 Inbox 复用 `internal/inputstream` 的段范围校验、已发布前缀读取、逐条边界检查、同步写入及尾部截断；Room 消息和事件的编码、连续序号、成员可见性及候选提交仍由 Room 适配器负责。共同内核不保存额外的 Room 根或游标。

## 追加与可靠收件

来源先持久保存带冻结目标的待投递项。成员 owner 核验完整 Room、成员和路由，调用 provider 编码器后预留容量，写入并同步正文，再发布分区根和去重回执，最后结清容量预留。成功回执返回后，来源才保存确认。

相同 DeliveryID 和摘要返回原回执；同键异摘要报冲突。目标发布后来源确认丢失时，来源继续使用原 ID。重开只按发布根核实容量预留，不用段尾推断成功。序号单调且不复用；不同分区出现同一个数字不代表同一条记录。

## Room 原生发布、清空与恢复

Room Actor 构造包含成员、消息、事件、游标和同页证明的原生候选。Store 先校验既有发布根及保留消息不可变性，再准备段；新段文件同步、重命名和段目录同步成功后，才原子替换 `room.json` 并同步 Room 目录。根中的每段保存首尾序号、已提交字节数及摘要，Room 段序号连续；平台导入分区允许既有序号空洞。读取只校验已发布字节，完整的未发布行和不完整尾部均不成为消息。

追加复用完整旧段，只重写未满的末段；纯成员确认只更新 `room.json`，所有正文段原样复用。清空先检查原生未过期读页、成员协调器中的持久正式页和未消费的定向事件；仍有保护时返回 busy。成员 owner 未加载而持久协调器存在时同样保守阻挡，恢复并结清后重试。成员页终止或回合封存前不删除可能重供的正文。Room 扫描到成员正式页保存之间还会在 Store 锁内重验已提交清空边界和原生游标：清空先提交则旧扫描被拒绝且不留下未决页，正式页先提交则清空返回 busy。

允许清空时，保留后缀需要的新边界段先同步，再把清空边界、保留段范围和成员有效起点一同发布。发布后才删除旧段；新到达消息、回复的原序号、事件去重回执和原生确认证明保留。根发布前失败仍恢复旧历史；根已替换但目录同步失败按未知提交冻结，重开以实际根核实；发布后清理中断由重开补做。重开在准入前清理孤立段并截断未发布尾部，已发布正文缺失、摘要或序号不符则拒绝打开。

Room 的确认和平台确认复用物理页范围及检查点比较原语，成员身份、执行权限、可见性和精确条目仍由各 owner 校验。Room 的唯一 `ReadThrough` 与同页证明同次提交到 `room.json`，不另写平台检查点。确认成功而应答或成员页结清丢失时，原请求匹配持久证明即可重放；异常反向范围、乱序或跨分区条目不能推进游标。

### 自动升级与备份

正常 Server 在取得目录独占锁后、启动来源采集和开放 Room 前运行已有输入升级框架。原生分段格式及平台分区格式保持兼容，已采用分段根的 Room 直接校验并重开，不重复转换或生成新升级备份。旧内联消息和旧输入文件仍通过 `input-upgrade.json` 记录进度，转换期间保留 `input-upgrade/<id>/backup/`、备份清单和 staging。

升级依次校验备份、转换树和来源摘要，写入升级围栏，发布目标文件，最后发布 Room 根并清理临时树。任何已记录边界中断后，使用同一配置和新版本重新启动即可继续；摘要、身份或文件不匹配时停止，保留证据。已清空边界、序号、成员及消费身份按原值转换；已分段 Room 的原生证明和事件回执不因切换共同内核改变。

自动转换备份仅覆盖此次升级的输入权威文件。升级后已有新业务写入时，旧备份不包含新增消息、消费或 Session 结果，不能只覆盖 `room.json` 或正文段回退。整实例一致备份、恢复及外部目录范围见[安装与运行](installation.zh.md#备份与升级)。

## 共享正文、成员交付与释放

共享项目使用同一分段内核的单分区实例。正文先同步，再把日志范围、回执及冻结的活动 Grant 接收集合原子发布到共享根。容量从该根的已发布记录和段范围核实，不另外建立成员容量预留文件。失败后重开只恢复已发布范围；原 ID 的成功回执先于新接收集合查询，同键重投不会增加新成员。

成员加入先在共享根持久登记 joining Grant，再由该成员 owner 保存初始消费文件，最后激活。中断后复用原 Grant 完成；活动 Grant 的消费文件缺失不会被当作初始零进度。关闭先持久停止新准入，未结清保护留在 closing 中；全部页结清后才记录 closed。移除成员先完成这个过程再删除其输入 owner。

成员先在 `input-state.json` 保存准备意图，固定 Inbox、成员、Grant、物理流、generation、turn、page、检查点起点、观察上界、排除位置和有效额度。InboxActor 按请求摘要幂等固定实际位置、扫描与可推进边界、剩余数量、页摘要及保护凭证。同页改起点、Grant、范围或额度返回冲突；后来追加不改变原页。

成员持久保存 reserved 页和材料结果后，先经共享 owner 串行授权 handoff，再记录成员输出交接。撤权与 handoff 由这个共同边界排序。完整 Session 结果证明到达后，成员先原子保存按流检查点及同页证明，结清成员页，再凭相同证明解除共享保护。确认、结清或解除应答丢失均可重试；已撤权页只允许相同持久结果结清，不重新供应正文。重开先恢复共享保护，再由成员证明补结清。

共享维护由 Inbox 的受控周期任务及来源变化唤醒，每批最多 128 条候选，一个运行实例合并后续请求；源及成员证据查询在共享变更槽之外。`CheckMemberRelease` 绑定成员、Grant、分区、物理流、实际位置和记录摘要，逐项返回 unknown、held、released、原因和持久修订。已确认仍需核验来源关联；到期跳过即使没有正式页也先由成员 owner 保存；已关闭 Grant 的终态由共享根核实。成员 owner 未加载时只读取校验过的已提交文件，缺失或不匹配返回 unknown。

回收提交在同一共享 owner 中重验来源 activation、当前根、Grant、固定候选及全部页保护，再复用连续前缀发布和删段算法。消费文件不重写共享正文。旧执行已失去重供权限且共享页已解除后，成员先压缩旧页证明，再通知正文 owner 压缩对应已结清页；闭合 Grant 在冻结接收集合及保护全部消失后压缩，ID 计数保留。独立保留边界使旧跳过、流目录和消费视图可有界压缩。

来源身份保留采集账号，成员的来源引用绑定当前 Grant 并保存在原成员跟进目录。目录、预览、正文、附件和结果重供均核对当前接收授权；业务解析及动作继续按成员真实执行账号核验。共享根和成员文件的证据均可在重启后重新加载，不能由离线或订阅缺项推断释放。

## 来源提交与生命周期

每个完整 RoomIdentity 对应一个通知 owner。订阅快照只由该 owner 的任务保存；每次最多一个持久变更，等待队列有界。状态读取使用发布后冻结的投影。`StepHost.Read` 固定来源配置版本、数据修订和连接证据，`Commit` 重验数据修订、连接 revision 和 credential stamp。查询候选与来源确认冲突时重查，不能把已确认身份重新带入 pending。配置恢复在同一配置版本下基于最新来源进度构造候选，保留并发确认。

投递固定原项和路由，在来源变更槽之外向精确 runtime 收件。目标成功后，来源 owner 从最新 State 核对原项再持久确认；期间配置变化不回滚已受理收件。首次投递先检查目标背压，后续投递与查询可并行，每订阅同时最多一个查询及一个投递。通知停用、凭据和容量阻塞分别处理。

正常停机先拒绝新操作、取消来源查询，再等已受理投递、确认及排队保存，最后 quiesce owner、关闭 actor runtime 并释放 Store。删除 Room 在删文件前完成同样的来源结清。超时仍保留 owner 和目录锁，可继续等待。关闭 Room runtime 后来源仍按原订阅规则存在；暂时没有可收件目标时保留 pending。唯一写入者不随 Session 轮换而变化。

## 正式读取与确认

服务绑定提供成员、Session generation 和回合，Agent 仅使用 `inbox_list`、`inbox_read`。目录列举不消费，平台按逻辑流分别推进；读取 A、B、A 不会让 A 的检查点跳过 B。默认平台额度为每回合 25 条，Room 默认页为 20 条，另有目录和图片额度。

正式页保存 `reserved → prepared → awaiting_confirmation → settled`。准备时固定快照、检查点起点和实际位置，保存来源关联与可重供结果；首次对外输出前先持久记录 handoff。HTTP 或 stdout 写出只完成交接，匹配的持久 Session 工具结果证明才允许确认。

平台确认原子保存该流的检查点与同页证明，再结清成员页。Room 确认通过 Room Actor 保存原生游标和证明，成员协调器随后结清；如果后一应答丢失，重开凭原生证明补结清。未匹配的执行、流、页或结果不能推进检查点；Session 轮换保留正文和平台消费。

## 历史只读视图

History 与正式 Inbox 共用 Room 原生日志、成员私有分区、共享正文及流身份，不增加历史正文库、owner 或持久消费账本。保留元数据构建目录与位置索引；目录包含已消费／合法跳过的保留记录，正文按可见性取最近后缀并向更早位置续页。业务投影和图片解析／下载共用既有适配，访问范围绑定服务端选定的历史记录。

目录和正文共用最多 4 个回合内快照、5 分钟空闲 TTL；cursor 绑定工具、成员、执行和观察范围。新增不插入旧快照，清空／回收改变保留边界时明确失效。实际请求才持有段 pin 与成员 lease，覆盖准备至输出结束；缓存不长期阻止回收。共享撤权与输出 handoff 串行核验，取消、关闭和回合结清释放查询及图文字节。

History 不经过正式 reserve／associate／confirm，不创建 Session 消费证明或修改 Room 游标。每页文本上限为目录 64 KiB、正文 256 KiB；每回合独立累计文本 512 KiB、图片 4 张／原始字节 4 MiB，且服从更小的服务／模型限制。重复有效调用复用结果和计费；正文预算按完整记录保留连续最近后缀，后续 cursor 从实际供给边界继续。额度耗尽明确停止，已发布正文缺失或损坏沿错误路径处理。

History 在正常服务路径默认提供，旧 Room 读取 CLI 已退出；部署与既有 Session 的切换边界见 [H4 实施记录](implementation/agent-history-h4.zh.md)。恢复仍自动供给原有有界 Room 预览；更多保留上下文按需读取，业务事实由原记录核验。

## 有界回收与预览

每批固定一个分区、最多 128 条连续候选，领域事实规划达到 10ms 时先结束本批。消费释放只覆盖给定候选，规划和提交不外推到新记录。段级保护同时覆盖正式页和预览 pin；最多重写一个约 1MiB 的边界段，正常清理仅删除本批旧段，并增量安装索引与字节计量。重新打开时才完整校验发布范围和清理孤立文件。原格式的根文件与检查点编码仍有固定大小上限。

回收需要保留期已到、来源已释放、成员已消费并有可释放关联，或已有合法跳过，同时没有在途页或未知提交。过期跳过使用服务配置并单独持久保存。来源缺失或不可核实时继续保护；核验到精确来源终态后才允许压缩对应去重回执。未消费的成员离线不是释放依据。

成员 owner 先固定本批目标位置及正文摘要，再在变更槽之外调用通知 owner 的 `CheckSourceRelease`。查询只读已提交来源投影，不复制全量历史库存。结果逐项绑定 Room、Inbox、订阅、DeliveryID、冻结路由、位置、正文摘要、来源修订和 owner activation。`held` 表示仍有匹配的 outstanding 项；`released` 必须有 provider 的持久观察或单调准入下界；缺失历史、身份不符、关闭或来源 writer 不健康返回 `unknown`。disabled／retired 仍保留其原命名空间。回收前重验 activation、writer 健康、本地消费、业务关联及页保护，不把同批证据外推到新输入。

来源确认和成员周期任务进入同一个成员维护操作；本地执行仍由成员 owner 合并和串行化，不持 manager 锁或来源变更槽等待。来源安装使到期缓存失效；同一修订的空闲检查复用下次到期时间，到期及策略变化会重新核验。后台周期任务补足丢失的唤醒和未核验来源准入，状态 Inspect 不承担维护。

预览先取得段 pin，渲染完成或失败后幂等释放，不建立正式页、不修改消费或业务关联。旧预览游标跨过已发布回收边界时明确过期；重新打开最新页，不把缺失正文解释为空输入。

## 关闭与故障恢复

成员移除先按现有生命周期结清 Session，再 quiesce、Stop/Wait 输入 owner。正常服务关闭在释放 Store 目录锁前结清输入任务；超时保留 owner、阻塞状态和目录锁，重试继续等待。重复打开复用同一 owner，旧代际通过执行身份校验失效。

### 持久 writer 的准入与路径所有权

文件使用同目录临时文件、文件同步、关闭临时文件、原子替换和目录同步。业务 owner 负责冻结保存值及串行修改同一份状态，writer 不协调跨文件业务事务。同一路径另有串行保护，等待者取得路径后才检查健康并登记在途；完成后释放该路径的临时登记。不同 Room 的不同路径可以并发执行文件 I/O，不持共用健康锁或目录缓存锁。各 Room 的局部 `Store.mu` 仍保护原有业务关联及原子操作。

健康锁仅保护关闭、提交不确定及在途计数。所有 `save` 调用都在接触磁盘前经过同一准入入口，包括管理快照、通知来源快照及来源确认；Workspace 快照删除也经过相同入口。预先调用健康检查不代表后续保存已经获准。目录缓存按目录保护，首次准备成功后记录目录及父目录 inode；任一被替换时重新准备。一个目录的准备或文件同步阻塞，不阻止其他 Room 不同目录的保存。

文件算法及健康准入由普通 Go `snapshotWriter` 提供。`Store` 组合该 writer 并额外核验 OS 目录锁；访问会话、首次设置及模型管理/迁移使用各自 writer，仍由原模块的锁和生命周期管理，不冒充 Room Store。浏览器会话 writer 的未知提交继续冻结自身后续保存，未取得目录所有权或已经关闭的 Room Store 仍拒绝保存。

冻结范围是同一个 Store。管理目录与通知来源使用共用 Store，任一替换或替换后目录同步结果不确定，都会冻结该共用 Store 的后续准入。Room 局部 Store 保留原有冻结范围；独立的业务存储继续遵循各自的健康协议。不同 Room 的来源由独立 NotificationActor 受理，因此一个 Room 的来源保存、收件或维护等待不占另一个 Room 的状态与写入路径。

### 并发结果与重开核实

每次已准入保存独立结清，不在文件同步或替换后重新以全局健康状态改报结果。例如 A 的替换后目录同步失败，返回 `ErrCommitUnknown` 并冻结新准入；B 若已经准入，仍继续完成自己的文件算法。B 替换和目录同步均成功时返回成功；B 在替换前失败时返回明确未提交；B 自身替换结果不确定时也返回未知。若 B 已成功，随后发起的来源确认属于新保存，仍被 A 的冻结拒绝。排在同路径后、尚未准入的保存同样被拒绝。

明确未提交保留旧快照，未知提交保留磁盘证据。重新取得独占目录锁后，按原快照身份、完整文件及发布根重新加载，再核对容量预留、去重回执、正式页和 Session 证明。不能从超时、内存候选或日志尾推断提交结果，也不能删除状态文件来重置。来源确认未成功时保留 pending，目标已收件则以原 DeliveryID 和回执幂等重投。

关闭先按 service/成员 owner 生命周期停止业务准入并结清已受理的完整操作。Store 关闭再冻结 writer 准入，在健康锁及 `Store.mu` 之外等待全部已准入保存完成，包括临时文件清理；最后等待局部 Store 操作并释放 OS 目录锁。并发关闭串行结清；等待期间原调用者取得各自真实结果，提交未知不会缩短其他任务的等待。目录锁释放前，第二个服务仍不能接管；关闭完成后直接调用底层 writer 也返回 `ErrStoreClosed`。
