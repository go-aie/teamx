# Agent 收件箱

Inbox 是 Membership 的可靠通知输入和短期排查记录。平台来源先保存待投递项，写入目标 Inbox 后再持久确认来源投递；Agent 的消费确认表示输入已交付，跟进事项办结、平台动作成功和 Todo 完成分别记录。

服务默认将原始消息／事件时间满 3 天的通知视为过期，跳过尚未消费的过期输入，并在后台分批清理符合条件的旧记录。服务重启后，此策略也适用于已有 Room；需要继续处理旧积压时，在启动前关闭跳过。

## 配置与过期判断

在启动 TOML 中配置：

```toml
[server]
inbox_expire_after_days = 3
inbox_skip_expired = true
```

对应启动参数：

```sh
teamx serve --inbox-expire-after-days 7 --inbox-skip-expired=false
```

命令行显式指定的值优先于配置文件，未指定时默认 3 天、开启跳过。期限须为正整数，且能表示为服务内部时间长度。配置在启动时读取，对该服务管理的现有和新建 Room 统一生效；修改后需要重启，不保存在各 Room 的冻结配置中。

判断只使用通知的 `Item.CreatedAt`：GitLab 事件用事件自身时间，Todo 用待办自身时间，飞书用消息原始创建时间。达到期限即过期；本地 `ReceivedAt`、历史补查、重投、消息编辑和 Agent 消费不会重置期限。直接发往 Room 消息流的通知沿用 Room 自身生命周期，不使用 Inbox 清理规则。

| 状态 | 开启跳过 | 关闭跳过 |
| --- | --- | --- |
| 未过期 | 正常采集、投递、消费并保留 | 相同 |
| 过期且未消费 | 持久记录过期跳过，不再交给 Agent | 保留，继续正常分批消费 |
| 过期且已消费、来源投递已确认 | 可清理 | 可清理 |
| 过期且来源确认尚未落盘 | 先持久确认来源过期，再清理符合条件的 Inbox 记录 | 保留去重回执，重试原投递；确认且已消费后才清理 |

来源保存必要的查询进度、去重记录和单调过期边界。过期跳过不生成投递成功回执，不增加 Todo 成功投递记录，也不代表 Agent 已消费或事项已完成。延长期限或关闭跳过只影响尚未确认跳过的输入，不能恢复已经跳过或清理的数据；需要更早的当前平台内容时，按需读取平台。

## 存储与容量

每个 Membership 独立保存通知正文、结构化内容、来源定位和投递去重回执。默认容量仍为 10,000 条或 64 MiB；单条和分页限制继续生效。Agent 消费通知本身不会释放容量。

后台维护复用成员的定时同步和来源投递循环，每次最多回收 128 条符合条件的连续旧序号前缀。遇到未过期、未消费且没有确认跳过、或来源仍有待确认投递的记录即停止该前缀；有效记录后面的迟到旧消息可以先持久跳过，暂时保留正文，待前面的记录也可清理时再删除。不能用直接删除 JSON 文件代替回收。回收同步删除原通知文件、释放内存中的逐条投递索引，并按实际保留记录重新计算条数和字节容量；跟进记录中的来源解析、目标、问题、授权、进展和动作回执继续保留，不另存一份历史正文。

通知序号一直递增，不复用已清理序号。`latest_seq` 表示最大序号，`retained_entries` 表示当前保留条数，`bytes` 表示保留记录的编码大小，不能再用最大序号代替条数。

`expired_through` 是已经持久确认可清理的连续旧序号边界，与 `consumed_through` 的 Agent 消费进度分别保存。跳过旧输入不会立即推进消费进度或办结事项。后续有效通知仍使用固定快照批次，完整输出并核实业务关联后才确认消费。

活动回合或未结清的消费批次会阻止该轮过期维护与物理回收，先按原固定快照结清；读取、写入和删除使用同一 Store 锁协调。保留记录的去重回执继续生效，已回收记录的逐条回执不会永久占用接收名额。

跳过序号在独立检查点中记录，只保留与当前队列恢复有关的有界记录，清理后继续压缩，不永久累计逐条墓碑。`skipped_entries` 表示尚保留的跳过检查点数，`skipped_through` 表示合并消费、清理与连续跳过后的输入定位边界；它不能当作 Agent 消费数量。批次读取、准入检查和模型图片材料使用同一跳过结果。

Inbox 满时保留现有输入，来源显示 `inbox_capacity`，继续重试投递和维护，并暂停该来源新增查询，避免继续增加积压。释放容量后自动恢复投递；原投递使用相同 Delivery ID，确认失败或服务重启不会创建另一份输入。来源自身因容量暂停的查询也在空间释放后继续。用户停用、凭据失效和绑定变化等独立阻塞不会因清理被解除。

关闭跳过时，未消费的旧积压可长期保留，10,000 条／64 MiB 上限不会放宽。先让 Agent 处理积压，检查未结清批次和来源确认；已消费但未达到期限、或排在受保护记录后的数据仍占容量。若希望放弃过期积压，修改跳过配置并重启；凭据或绑定异常需要单独修复。

## 原通知过期后的读取

| 情况 | 读取结果 |
| --- | --- |
| 序号在已确认过期边界内 | 明确返回原通知已过期，不读取或恢复旧正文 |
| 序号超过最新序号，尚未接收 | 返回不存在，与过期区分 |
| 保留区间内文件缺失、格式损坏或身份不符 | 返回数据错误，不能视为过期或空收件箱 |

新的预览快照从首条保留记录开始，返回 `expired_through`。固定快照的续读位置落入已清理区间时返回 `inbox_expired`，需要建立新快照重新定位。

已有跟进仍可通过 `matters list`、`matters read` 和 `matters sources` 读取。`matters source --seq SEQ --source SRC` 保留现有来源解析、原生身份和目标引用，并单独说明原通知正文状态：

- Agent 读取返回 `entry.status=expired`，省略原通知的 `item` 和 `received_at`。
- 人类管理读取返回 `entry_status=expired`，省略原通知 `entry`。
- 原通知仍保留时分别返回 `retained` 和原通知内容。

例如，通知 `#1` 已清理但其跟进尚未办结，原有问题、授权和未知动作结果仍有效；读取来源会告知正文过期，不能据此重做动作。需要当前平台内容时，使用现有平台读取能力，仍须核对当前成员、账号和准确目标。依赖原通知的重新解析和建立新来源关联会明确返回过期，不从跟进记录伪造原通知。

## 中断恢复与排查

系统先持久保存清理边界，再回收文件。若在删除前或删除途中停止，重新打开 Inbox 时会按已保存的边界继续完成物理回收，不需要每条通知的永久墓碑。写入结果不确定时停止后续写入，重新打开 Store 后依据持久记录恢复。

现有有效 Inbox 可以直接加载；旧版头文件没有生命周期字段时，按完整保留区间校验后补齐序号检查点。成员已完成回合的历史检查点可以指向合法清理的通知；保留区间内缺文件、跟进目标损坏或来源身份不符仍会报错。

遇到 `inbox_expired` 时重新读取保留区间或已有跟进；遇到数据错误时保留现场排查，不要手工删除头文件、消费检查点或跟进记录来重置收件箱。已确认回收的正文不会因重启而恢复。

## 页面查看与更新

打开成员的「收件箱」时，默认展示最近一页，最多 25 条，页内按消息序号从早到晚排列。「保留 N 条」是当前尚保留的记录数，包含已消费但尚未清理的通知，不是历史接收总量或人类未读数。统计的提示信息可查看容量占用、最新序号与清理边界。

页面复用现有定时同步，在页面可见并获得焦点时轻量检查状态。新增通知会自动更新保留条数，将「最新」按钮提示为「有更新」；正在浏览的页、来源详情展开状态、滚动位置和焦点继续保留。点击「最新」或「有更新」才建立新快照并返回最近一页顶部。平台后台采集和 Agent 处理不依赖此页面是否打开。

- 页码只表示本次浏览的位置，不显示总页数。初次进入为第 1 页，「较早」加一、「较新」减一；「最新」或清理导致重新定位时重置为第 1 页，普通刷新保留页码。「较早」「较新」在同一固定快照内翻页；新增记录不会插入当前历史页。页内可能因较大正文分多次读取，但一次最多展示 25 条。
- 刷新图标按钮用于重试读取当前页及统计，保留当前位置和仍存在记录的展开状态；它不会自动跳到最新。读取失败时保留原页面，可再次刷新或重试翻页。
- 当前页或翻页位置已经涉及清理区间时，页面显示「当前记录已过期」，建立新快照并回到最近保留记录的第 1 页。全部清理后显示空收件箱。仍存在的记录尽量保留位置；已删除记录的焦点移到分页提示。
- Room、服务实例或 Membership 切换后，页面重新核对上下文，旧请求的迟到结果不会覆盖新页面。同名新成员不会继承旧成员的 Inbox。

过期清理提示只表示原通知正文不再保留。通过「查看跟进与待你答复」进入成员规则页中的已有跟进记录，可以查看问题、待核实结果和原通知过期状态；需要你答复的事项继续通过 Room 对话处理。查看通知、刷新和翻页均不会确认 Agent 消费、启用协作、办结事项或重做动作。

页面沿用成员运行状态和平台通知状态显示受阻原因，来源有待投递项时显示来源积压。来源积压数与 Inbox 保留数含义不同，不能相加当作未读数：前者尚未完成持久投递，后者已进入该成员 Inbox。

- 有新记录但 Agent 没有处理：查看成员是否暂停、会话是否受阻，以及来源证据是否待核验；打开收件箱本身不会启用协作。
- 容量已满且来源有积压：后台会继续处理和清理，释放容量后自动重试；关闭过期跳过时，还需等待 Agent 消费旧积压。
- 凭据、绑定或来源异常：点击页面中的平台异常提示进入现有设置查看和修复；容量恢复不会解除这些独立阻塞。
- 同步或读取失败：当前内容可能落后于后台状态，先点击「刷新」重试。数据损坏会明确报错，不会统一显示为过期。
