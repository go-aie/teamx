# Agent 收件箱

Inbox 是成员的可靠输入入口。Agent 用相同的两项工具选择并读取 Room 消息、交互事件和保存的平台通知。Room 公共正文只保存一份，各成员独立确认；平台通知可以进入成员的私有 Inbox，或进入多人独立阅读的共享项目 Inbox。成员暂停时仍可收件。

来源投递成功、Agent 消费、跟进办结和外部动作成功是分别记录的结果。预览通知不会启动 Agent、确认消费或授予操作权限。

## 选择与正式读取

回合开始的目录提供逻辑流、来源标签和待交付数量，不提前注入正文或图片。同一 GitLab MR 的通知可以交错保存在一个 provider 分区中，仍作为同一逻辑流读取。Agent 自主选择流，当前人类指令有待阅读时应先读 Room。

```json
{"limit": 10}
```

这是 `inbox_list` 的首次请求；省略参数也可以。更多目录项只传返回的目录游标：`{"cursor":"…"}`。目录列举不会消费；列举及曝光受成员的持久额度约束。

```json
{"stream_ref": "stream_…", "limit": 5}
```

这是 `inbox_read` 的请求。成员与回合由服务绑定提供，无需传 `turn_number`、read ID 或正文续读游标。成功后继续读同一个 stream_ref，即取得该流下一页；`remaining_entries` 是该流固定观察范围内尚待交付的条数。跨流读取互不推进对方检查点。

平台输入共用每回合 25 条额度，Room 默认每页 20 条，并受既有页数、正文和图片预算限制。结果保留来源引用及必要的跟进摘要，图片准备失败按结果中的材料状态表达。额度耗尽或当前流已空时遵循 stop_reason，不反复刷新目录来绕过额度。

## 配置共享项目收件箱

团队房间的「房间详情 → 共享项目收件箱」提供接收成员、GitLab 项目设置与只读预览。每个房间目前提供一个共享项目 Inbox、一条项目活动订阅，支持房间中的多名成员；个人 Todo 和飞书通知继续使用成员私有 Inbox。

1. 勾选接收成员并保存。之后加入的成员只接收新保存的记录。
2. 选择已有 GitLab 连接，在复用的项目活动设置中搜索并选择项目，保存接收设置。切换到另一个连接前，先暂停原共享订阅。换项目或实际账号会建立新的来源订阅。
3. 点击「刷新」查看保留正文、最早受保护的位置、待阅读成员和等待确认的页。成员自己的「收件箱」也显示共享记录，并标注该成员的待阅读、已确认或已跳过状态。

共享正文保存一份，各成员独立消费。甲确认 MR 流 A 不会推进甲的流 B，也不影响乙的进度。成员通过同一 `inbox_list` / `inbox_read` 入口读取，共享和私有平台输入合用每回合 25 条额度。

取消勾选会先停止该成员的新读取。已有页等待 Session 确认时，页面提示先结清并刷新；原证明仍可结清已交接页，正文查询和旧引用同时停止授权。重新加入会产生新的 Grant，旧记录重投仍使用原接收集合。移除成员沿用同样的结清屏障，其他成员可继续阅读。没有有效接收成员时，来源暂停新增采集。

共享权限只允许阅读已经保存的通知。来源保留采集账号的真实证据；远端解析、图片下载和动作仍核对成员自己的绑定与权限，权限不足会显示为业务或材料不可用，不把采集账号冒充为执行账号。

## Session 证明与恢复

正式页先保存固定范围、实际位置、预算和可重供的图文结果，再记录输出交接。HTTP／stdout 完整写出之后，仍须由 DSH 保存工具结果并提供匹配的 Session 证明，服务才推进检查点并结清页。仅写出不能视为消费。

未确认页与结果会保留以便恢复；相同调用重试复用原页。确认应答丢失可以凭同页证明核实，不能换身份、流或结果重复确认。Room 页继续使用 Room Actor 的原生游标和证明；平台按成员、分区及逻辑流保存进度。Session 轮换保留已保存正文与消费状态。

完成回合但固定输入没有消费进展时，调度器最多提供 3 次恢复机会，退避为 15、60、300 秒。暂停、模型故障、取消未结清及未知动作结果仍受原门禁约束。「继续读取收件箱」只重置输入恢复机会，不额外授予动作或回合权限，也不发送聊天。消费或合法排除造成的实际进展可以结清原停滞范围；新通知和 Session 换代本身不重置原范围的额度。

默认使用 HTTP MCP。需要 CLI 模式时，在 `[server]` 设置 `inbox_mode = "cli"` 并重启，使用服务提供的 `inbox list/read`；两种传输共用同一输入协调和 Session 结果证明，不能通过切换传输重复消费或刷新额度。

## 保留与容量

```toml
[server]
inbox_mode = "http"
inbox_expire_after_days = 3
inbox_skip_expired = true
```

也可用 `teamx serve --inbox-expire-after-days 7 --inbox-skip-expired=false`。显式命令行值优先；配置在启动时读取，对该服务管理的新旧 Room 生效。

过期按通知原始 CreatedAt 判断，本地接收、重投、编辑和消费不重置期限。关闭跳过时，尚未消费的旧通知继续保留。已经持久跳过或回收的数据不能通过延长期限恢复。Room 时间线遵循自身显式清空规则。

私有 Inbox 默认容量为 10,000 条或 64MiB，跨平台共享成员容量，provider 各有分区。消费本身不立即释放空间。后台每批最多核验 128 条候选，只回收符合条件的连续前缀：保留期已到、来源释放、已消费且业务关联可释放或已有合法跳过，并且没有未结清页或预览保护。

来源保护分为仍待投递的 `held`、已有持久终态的 `released` 和无法核实的 `unknown`。缺失历史订阅、来源故障或证据未知时保留正文和回执；停用订阅不等于删除历史证据。后台维护与状态轮询分离；关闭、移除和轮换按原生命周期结清在途操作。Inbox 满时保留旧输入，来源显示容量阻塞并重投原 DeliveryID；空间恢复不会解除凭据、绑定或人工停用等其他阻塞。

共享项目 Inbox 另有独立的 10,000 条或 64MiB 配额。只有记录冻结接收集合中的每个 Grant 均已消费且关联可释放、持久跳过，或撤权结清后，才允许回收。未消费且没有正式页的记录仍会阻挡前缀；默认到期跳过也会为这类记录保存成员证据。成员暂时离线、owner 未加载或证据缺失不会解除保护。

正文按段保存在 JSONL 日志中，检查点和执行状态分别保存。不同 provider 的同一数字序号不是同一记录，来源定位应使用返回的 source_ref。持久路径、发布及恢复关系见[存储架构](storage-architecture.zh.md)。不要手工删除段、分区根、消费文件或协调器来腾空间。

## 页面查看与排查

成员「收件箱」默认显示最近 25 条保留通知，页内从早到晚排列。有共享输入时分别显示私有和共享数量；这些保留数量包含已消费但尚未回收的数据，不等于未读或累计收件数。页面可见时通过已提交状态与更新信号提示新数据，后台收件不依赖页面打开。

- 「较早」「较新」在固定历史快照内翻页，新增数据不插入正在浏览的页；「最新」建立新快照。
- 刷新重试当前页并保留仍存在的展开项和位置；跨过回收边界时明确提示过期，重新打开最近保留页。
- Room、服务代际或 Membership 变化后重新核对上下文，迟到结果不能覆盖新页面；同名新成员不继承旧 Inbox。
- 原通知过期后，已有跟进、问题、授权和动作回执继续保留。通过「查看跟进与待你答复」读取，不从跟进记录重建或重做已确认动作。

来源按 Room 独立保存和投递；一个 Room 的慢收件或来源文件等待不会占住另一 Room 的来源 owner。目标已收件而来源确认失败时会使用原 DeliveryID 重投，成员继续得到同一条记录。

有记录却未处理时，检查成员暂停、模型状态、来源准入及未结清执行；有来源积压时，检查通知投递、容量和绑定。数据损坏与已回收分别报错，不能统一当作空收件箱。提交结果不确定时保留现场、结清并重开核实；未知外部动作先查远端结果。
