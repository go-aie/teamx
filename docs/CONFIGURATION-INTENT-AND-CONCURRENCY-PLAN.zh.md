# 配置变更意图与并发协调方案

状态：阶段一、二已实施；阶段三的本地组合、桌面／手机浏览器和真实 DSH＋模拟提供方验收已执行，真实平台隔离配置门槛仍未执行，不能宣称完整发布。阶段一见[工具绑定实施记录](implementation/configuration-intent-tools.zh.md)，阶段二见[通知观察保护与规则记录级并发](implementation/configuration-observation.zh.md)，阶段三证据、复验命令和发布边界见[组合验收与发布检查](implementation/configuration-combination-acceptance.zh.md)。基于 2026-11-15 源码及飞书／GitLab 连续启用故障整理；下文仍规定完整交付合同。

## 1. 结论与交付范围

采用长期修复：让并发前提与准确业务目标一致，保留必要的观察、授权和运行前提。独立目标可合并保存，同一目标的真实冲突明确拒绝，未知操作不重放。

必须交付：

1. 工具配置由 Room 全局版本检查改为准确绑定的检查，解决连续开启飞书／GitLab 时互相阻塞的问题。
2. 单条长期规则写入保留记录版本，解除整个规则文件版本造成的无关阻塞。
3. 工具与通知继续使用已有成员配置流程，共用准入、幂等／来源检查、诊断和提交结果边界；通知复用已有准确订阅版本。
4. Agent、完整设置和 onboarding 在各自入口保留正确前提，进入同一领域权威写入点。

控制复杂度的决定：

- 保留现有文件、锁、采集器及操作记录；只为缺少目标标记的工具文件补充元数据。
- 通知继续携带 `notification_version`，规则继续携带目标 `version`；这些是业务观察前提，不能与工具文件全局 revision 一并删除。
- 沿用现有回执状态，不新增持久 `incomplete` 或通用 continue／重试状态机。
- 直接扩展 `configurePlatformMember` 及既有检查／诊断辅助函数，不另建配置执行器、领域注册表或通用 patch 框架。
- 不改 Room 调度、Session、模型发布、Workspace 切换、事项办理及外部动作执行核心。

## 2. 已核实的问题与共用边界

故障顺序是两个工具命令都带 `--tool-revision 0`。飞书成功使 Room 工具文件版本变为 1，GitLab 随后因旧版本被拒绝。版本 1 来自飞书配置，不能据此推断存在 GitLab 授权。

| 领域／源码落点 | 当前事实 | 本次安排 |
| --- | --- | --- |
| `tools.go`、`tools_lark_configuration.go` | 工具准入和远程准备复查依赖全局 revision／整份文件相等 | 改为准确绑定版本及账号证据检查，合并最新文件 |
| `platform_member.go`、`platform_member_store.go` | 工具和通知已共用身份、回执、来源和提交流程 | 扩展现有骨架，分开业务输入与内部执行快照 |
| `platform_notification_lark.go` | 按平台和接收 Target 定位当前订阅，再检查 subscription ID／version | 保留准确订阅前提；普通采集进度不造成伪配置冲突 |
| `platform_gitlab_notifications.go`、`platform_member_gitlab.go` | 按平台和接收 Target 隔离；events／todos 共用总开关、起点及 desired config version | 保留聚合检查与 `Applying/Pending/Errors`，不重构采集器 |
| `policy.go`、`followups_policy.go` | 单条规则更新同时检查文件 revision 和记录 version | 解除前者，保留准确规则版本、human 证据及建议确认 |
| `tools_http.go`、`features/members.mjs`、`platform_onboarding.go` | UI 和 onboarding 的工具步骤也依赖全局版本 | 同步改为准确目标准入，不能只修 Agent 命令 |

其他主要路径的结论：

- 改名已经比较准确对象的 `expected_name`；已读已经使用 max／集合并集合并，保持现状。
- 动作的 `policy_token` 关联完整有效策略，事项 `unit_version` 关联同一办理聚合，均保留。
- Workspace、模型及 Session 涉及跨资源状态，目前没有证明其组合前提可缩小，本次不动。

本次解决的共性是“存储范围大于业务目标”和“业务意图混入内部执行前提”，不是消除所有版本冲突。审查不构成所有 Room 写路径的形式化证明。

此前已运行四项现有 integration 测试：`TestGitLabUnifiedConfigurationPersistenceAndVersion`、`TestGitLabPlatformsIndependentDefaultsPauseRecoveryAndDelivery`、`TestGitLabPlatformsApplyLockAndFailuresAreIndependent`、`TestLarkMultiplePlatformsCollectPauseAndRecoverIndependently`，均通过。它们使用本地模拟提供方，支持现有通知隔离行为的判断，不代表本方案已实现。

## 3. 通用并发合同

### 3.1 分清三种前提

| 前提 | 含义 | 处理方式 |
| --- | --- | --- |
| 存储版本 | 整份文件的保存顺序 | 留在服务端，不把其他目标的保存视为本目标冲突 |
| 目标观察前提 | 用户／Agent 正在修改的原状态 | 需要时随请求携带；只能核对，不能自动换成最新值 |
| 授权／运行前提 | 准确账号、generation、凭据、有效策略、活动进程 | 保持现有强校验，不因配置合并而放宽 |

通用处理顺序为：识别准确目标及请求语义 → 核对原回执／来源 → 校验观察前提 → 准备 → 复查真实依赖 → 在最新状态中只修改该目标 → 返回可核实结果。

### 3.2 绝对意图与基于观察的编辑

- 明确的工具启停／既有动作增补可使用绝对意图：服务端在准入时读取当前绑定，冻结本次目标版本并复查准备期间的变化。多工具分别处理，不携带 Room 全局工具版本。
- 完整表单、范围替换／清空、授权整份替换／减少、规则修改等基于已读状态的编辑，必须保留准确目标的观察前提。
- 为保持接口简单，通知的所有现有类型化补丁统一保留 `notification_version`；本次不按字段推导可交换性，也不按自然语言猜测能否省略前提。
- 服务端自动刷新内部文件不改变业务意图；刷新目标观察前提则可能改变编辑含义，不得自动进行。

必须覆盖的反例：Agent 读到仅关注 A，用户随后通过 UI 加入 B，Agent 再提交旧范围替换为 A。该请求必须因准确订阅版本变化而拒绝，不能到提交时才抓最新版本并删除 B。

服务端准备快照只能保护准入后的变化。绝对意图按准入时状态执行；需要保护更早观察的调用必须带目标前提。Agent 负责核对后续 human 指令，服务端不解析任意聊天判断撤回。

### 3.3 共用实现的上限

沿用 `configurePlatformMember` 的工具／通知分支、稳定操作 ID、原来源限制和提交防重放记录。仅提取已经被多个分支使用的准确目标检查、提交效果说明和诊断；可以保留少量显式类型／kind 分支。

规则继续在 `Store.mu` 下单文件写入，复用相同检查原则和已有 `versionConflict` 等诊断，不强行进入管理器操作记录流程。领域校验、锁及权威保存函数保留在原位置。

不新增隐式 CLI 状态缓存、快照引用服务、回调注册框架、任意字段合并器或跨存储事务。共性通过同一并发合同、现有共用流程及跨领域验收证明。

## 4. 工具绑定改造

### 4.1 目标与变更标记

完整目标为 `RoomID + RoomInstance + AgentID + MembershipID + Tool + PlatformID`。文件已有 Room 归属，内部键使用后四项的规范 JSON 四元组编码，避免分隔符歧义；无平台独立 CLI 工具的 PlatformID 为空。不能按显示名或 provider 模糊定位。

保留全局 `revision`，工具文件提升为 schema 2，增加 `target_revisions`。每次真实目标变更将保存后的全局 revision 赋给该目标，允许跳号；其他目标的标记不变。

- 从未配置的目标为 0；启停、generation、实际授权或持久能力证据变化均更新标记。
- 禁用／删除后的标记保留，阻止“关闭再开启后内容相同”的 ABA 变化漏检。
- 查询、瞬时能力观察和确定无变更的 preserved 不递增。
- 目标内容与标记在同一次原子保存中写入；所有工具写入入口必须经过该更新逻辑。
- 复用现有目标容量与文件大小约束，包含保留标记的目标；超限明确失败，不能静默丢弃标记。

schema 1 读取时在内存中以原全局 revision 为已有启用／禁用项补齐标记；第一次实际变更时保存 schema 2。查询不写文件，`LegacyUnknown` 的历史语义保留。

### 4.2 Agent 与 UI 入参

拟议普通绝对意图命令：

```sh
teamx platforms member tool \
  --platform-id ID --platform-version V \
  --operation-id TOOL_STEP_ID --source-seq SEQ \
  --enabled true
```

移除 `--tool-revision`。保留 false 和现有飞书 `--action` 的增补语义；默认动作、self proof 和发送授权含义不变。

`member get` 返回目标 `binding_revision`。若调用要以已读绑定为前提，可传 `--binding-revision N`，HTTP 对应 `expected_binding_revision`。省略表示上述绝对意图；显式 0 表示观察时未配置，两者必须区分。

human `/v1/tools/bind` 的表单与授权编辑一律要求 `expected_binding_revision`。UI 从 `/v1/tools/bindings` 获取目标标记，拒绝旧全局 revision 写合同。新页面不展示内部版本，也不新增常规确认流程。

### 4.3 准备与提交

1. 在锁内核对可选观察前提，捕获准确绑定版本、账号与动作计划。
2. 按现有流程释放锁完成必要的飞书远程核验；继续注册可取消的平台调用。
3. 加锁读取最新文件，复查原目标版本、成员、账号／凭据及证据有效期。其他目标变化允许继续；本目标变化明确拒绝。
4. 沿原提交防重放顺序写入，只替换准确目标，保留最新其他绑定、禁用项及标记。
5. 用实际提交版本确定授权／能力投影和回执，完成调用收尾后返回。

替换 `preparedLarkToolChange.Before` 整份文件比较，包括权限缺口分支；不能只删掉 `f.Revision` 检查。准备阶段不得把 `f.Revision+1` 当最终授权／回执版本。preserved 返回当前实际状态，不返回准备时旧文件。

纯禁用和授权减少继续及时取消准确目标的活动调用，不等待无关远程准备。完整设置、Agent 和 onboarding 共用 `changeToolBindingLocked` 等权威提交点。

## 5. 通知与规则适配

### 5.1 通知保留已有目标前提

不改变 `--notification-version` 及其语义：它是准确订阅／desired config 的观察版本，0 表示未配置。CLI／HTTP 必须区分合法的 0 与未提供前提，不能把缺少输入解释成自动使用最新版本。

飞书继续核对 subscription ID、version、退休状态和准确账号；GitLab 继续核对 `notificationScopeFor(platform_id, target)` 下的 desired version，并独立核对 collector 应用状态。不新增第二套通知目标版本表，不迁移采集状态文件。

同一订阅的群／私聊或 events／todos 保持一个聚合，保留总开关、休眠来源、历史起点和范围约束。同一请求的相关补丁合成一次操作，不能借跨字段合并意外恢复另一分支。

远程核验前后都检查同一观察前提，准备后不能自动改成最新目标版本。保存时从最新权威状态保留游标、积压、投递及基线；普通采集进度不能造成伪冲突，账号／凭据变化仍须拒绝。

GitLab 沿用 desired config 与 `Applying/Pending/Errors`。配置已保存而来源未应用时，准确报告当前配置和逐来源情况，走既有显式同步／核对入口；不重新提交原意图来修复应用。`platformMemberNotificationContext` 只推进到本次实际接受的 desired version，不能跳到任意最新值。

### 5.2 规则只约束准确记录

Agent 的 `changeConversationPolicyLocked` 与 human 的 `changePolicy` 都解除文件 revision 的单条写入前提，保留 RuleID／记录 `version`。在原 Store 锁内加载最新 history、检查目标版本、原 human 身份／来源、状态转换与容量，追加本条并递增文件 revision。

写入后返回本次准确记录、当前完整有效策略和重新生成的 policy token。更新规则 B 不阻塞版本未变的规则 A；同一规则被修改或撤回仍拒绝旧版本。

建议确认继续核对原建议版本、正文、公开问题回执及 human 回复。执行动作的完整策略 token、事项版本和授权检查不变，不自动刷新 token 重发动作。

幂等继续使用原 human 来源及规范化请求证据；新请求 digest 排除文件 revision／回合，保留准确规则版本和业务输入。必要时仅增加 digest 版本标记，保留旧证据读取；无法证明历史请求等价时返回原记录与核对说明，不能再追加“相似”规则。原请求复用先于当前目标版本检查，避免重试重新激活已撤回记录。

## 6. 幂等、提交结果与诊断

### 6.1 业务输入与执行快照

稳定操作 ID 固定准确成员／平台、kind、原 human 来源、连接前提、启停／动作／通知补丁及显式观察前提。动作集合规范化；省略默认动作与显式列表分开。服务端准备时展开的默认动作计划在提交记录中冻结。

内部捕获的工具版本、整份文件快照和瞬时能力观察不参与业务意图比较。显式 `expected_binding_revision`、`notification_version` 则是编辑含义的一部分，不能在原 ID 下修改后重放。

复用已有来源／成员／平台／kind 防绕过检查；工具与通知不能互相占用原操作。已登记的较新同目标配置不得被旧来源新执行覆盖；原 ID 历史查询仍可返回原结果。未登记的自然语言替代仍由 Agent 核对。

### 6.2 沿用现有状态与持久化顺序

- 原 ID、同业务输入：返回原回执，不重新准备或修复绑定。
- 同 ID 不同输入，或同来源用新 ID 绕过既有操作：明确冲突并提供原操作引用。
- 准入／准备时能够证明未保存：通过诊断返回 `outcome=not_applied`；不为此强制新增一种持久状态。
- 已预留记录但明确在目标保存前拒绝：可使用现有 failed 终态，前提是提交点能可靠证明未尝试保存。
- 一旦目标保存已尝试，错误、超时或取消均按可能保存处理；原 unknown 防重放和 Store 不确定写入保护继续有效。

先保存原防重放记录，再尝试目标写入。回执与目标文件不是同一事务；原记录存在而无法确认目标写入时不能重放，不能仅凭内容一致或全局版本 before+1 推断成功。

请求超时后一次 status 查询未找到记录，也不能证明原请求已停止或确定未应用；必须结合原请求结算和权威状态核对，不能据此换 ID 重发。

不新增持久 incomplete；通知的部分应用继续由原 Applying／Pending／Errors 和权威读回说明。保留原操作状态边界，不能把未确认的操作升级成 completed，也不能把已确认的部分效果描述成“完全未保存”。status 查询始终不触发配置或来源应用。

### 6.3 复用现有错误诊断

扩展现有 `requestDiagnostic`、`versionConflict` 与 CLI 错误呈现。至少能区分：准确目标变化、账号／成员变化、意图不一致、结果未知、用户授权缺口。

返回准确 field、expected／actual version、原 operation_id 及 hint；能证明未应用时再提供该结论。hint 是恢复指导，不授予重试权限。配置冲突不能被 Agent 解读成未经证实的授权历史，也不要求用户重复已经明确的授权。

## 7. 各入口及兼容边界

- Agent 工具命令不再接收 Room 工具版本；通知保留订阅观察版本，规则保留记录版本。同步帮助、平台 Skill、HTTP DTO 和测试示例，明确零值／省略语义。
- UI 工具改为准确绑定前提；通知表单和规则编辑继续保留各自观察前提。本目标冲突保留本地输入，不能自动换版本保存。
- onboarding 工具步骤在目标确定后冻结原绑定版本、账号与动作计划，等待 OAuth 后仍复查。解除新工具步骤对 `BeforeToolRevision+1` 的结果推断；通知步骤保留原订阅／desired 前提及应用逻辑。
- onboarding 及成员工具回执仅因新工具合同采用必要的新 schema（当前成员回执为 1／2，新工具可用 3；当前 onboarding 新合同可用 4）。不为统一外观升级通知回执、规则文件或采集状态格式。
- 旧工具文件可读、首次实际变更升级；旧回执和未知步骤保持原证据及防重放语义。旧待处理工具步骤缺少准确前提时明确要求核对，不能自动转换后执行。
- 旧 `tool_revision`／全局工具 `revision` 写合同明确拒绝并提示新用法，包括显式传 0；历史解码继续支持。规则新写入口不再接受文件 revision，历史 digest 不重算；通知观察版本不受这项拒绝影响。
- 部署时停止旧进程，配套更新二进制、前端及指引；备份工具文件和操作记录。新 schema 写入后使用支持它的版本，不能单独还原工具文件或删除 unknown 记录回退。

直接 human 工具编辑继续读回核对不确定结果，本次不为它新建独立回执系统；规则继续使用 Store 原锁和幂等证据，不强行套用成员操作 ID。

## 8. 实施顺序与验收

以下是同一长期方案的开发拆分，各阶段的实现和验收放在一起。全部完成后才宣布交付；长期函数与测试按行为命名。

阶段按完整行为切分，不按存储、服务端、CLI、UI 横向拆开。每个阶段同时完成其接口、帮助／Skill、兼容处理和必要测试；共享检查与结果边界随第一个使用它的功能落地，不能留到后续阶段才补安全保证。前两阶段可独立完成代码审查和本阶段验收，完整发布仍须经过阶段三。

### 阶段一：准确目标检查与工具修复

实现工具目标标记、可选观察前提、最新文件合并、飞书目标复查及实际提交版本投影；同步 Agent、UI、onboarding 工具入口和必要的历史读取。工具合同所需的共用准入／诊断、幂等／提交结果边界，以及 CLI 帮助、平台 Skill、调用示例和对应测试一起完成。

本阶段工作最多，内部按“目标标记与兼容 → 准备／提交复查 → 各入口及指引 → 回归”推进，可分多次审查或提交；不把这些拆成可独立发布的半套协议。

验收：

- 同一 human 请求下先后开启飞书和 GitLab，两项均成功；逆序、重叠准备也不会丢失另一项。
- 读取两个绑定均为 0 后依次带各自目标前提保存，第二项不会因全局版本改变失败。
- 两个成员绑定同一平台相互独立；修改同目标、关闭再开启的 ABA、账号／成员替换均拒绝旧准备。
- 纯禁用和权限减少及时生效，原授权、self proof、能力有效期和活动调用收尾保持正确。
- 文件 schema 升级、容量、版本溢出、响应丢失及重启均有明确结果；旧 unknown 不重放。
- 真实 HTTP／CLI 与本地模拟提供方覆盖原故障、同 ID 重复／变更输入、保存尝试前后的失败及回执丢失；UI 自动化覆盖目标前提和冲突反馈。不能把这些正确性测试推迟到阶段三。

### 阶段二：跨领域一致性与观察保护

在现有 `configurePlatformMember` 内复用阶段一形成的检查／诊断和提交效果表达。内部有两项可分别审查的工作：通知保留准确订阅前提并补齐诊断／回归；规则两条写入路径改为记录级检查并完成规范化幂等证据兼容。通知已有隔离机制直接沿用，不为证明通用性重写采集器。

本阶段变更的规则 CLI／HTTP、human 管理入口、帮助／Skill、调用示例和对应测试同步完成；不在阶段三首次切换写合同。

验收：

- 修改规则 A 后，目标版本未变的 B 仍可保存；同规则并发修改／撤回继续冲突，原请求复用不重新激活规则。
- 更新有效规则后，动作的旧 policy token 仍被拒绝；建议确认仍绑定原问题和正文。
- Agent 读通知范围后，UI 新增 B，再提交旧范围替换必须拒绝；同目标完整 UI 表单也不能覆盖新修改。
- 不同账号／接收成员通知相互独立；同订阅真实变化拒绝，普通采集推进不制造伪冲突。
- 飞书群／私聊和 GitLab events／todos 的总开关、休眠来源和起点约束完整保留；部分应用通过现有状态呈现，不重提原配置。
- 工具、通知、规则复用相同目标／观察／授权分类和诊断，无新增通用执行器或持久结果状态。所有入口均进入各自原权威保存函数。
- 本阶段完成通知应用失败／未知结果、规则历史请求复用及准确观察前提的接口与集成测试；阶段一工具用例继续回归通过。

### 阶段三：组合验证与发布检查

在前两阶段功能和各自测试已完成的基础上，执行跨入口、跨领域及真实后端组合验收，审查兼容与部署说明。帮助／Skill 和示例在本阶段仅核对一致性，不首次实现。该阶段不承接尚未实现的授权、观察前提、幂等或未知结果保护，也不增加新功能；发现缺陷回到所属实现阶段修复，再重跑受影响验收。

验收：

- 模拟提供方下覆盖顺序、并发、准备窗口变化、来源应用失败及写入／最终回执前后断开或重启，核对实际保存内容与写入次数。
- 桌面和手机浏览器验证工具开关、通知观察冲突、规则编辑及本地输入保留；无新增常规审批或版本展示。
- 真实 DSH 在隔离 Room／成员上完成“双工具启用”和“两条规则更新”；通知操作正确使用准确观察前提，不臆测授权或重发未知操作。
- 真实模型＋模拟提供方、本地浏览器＋模拟提供方、真实平台配置分别记录，不互相替代。真实平台验收仅使用另行明确授权的隔离目标，不修改用户现有配置或触发评论／消息。
- 未完成真实后端或真实平台门槛时明确列出，不用组件通过宣称全量验收。

优先扩展 `tools*_test.go`、`platform_member*_test.go`、`platform_onboarding*_test.go`、现有通知隔离／应用测试、`policy*_test.go` 和相关 Web／浏览器入口；并回归旧 policy token 拒绝用例。按依赖层运行 Go、Node、integration 及显式浏览器／真实 DSH 验收，不把真实外部依赖混入普通单元测试。

## 9. 最终检查与复杂度上限

交付必须同时证明：原双工具故障消除；工具／规则独立目标不再无关阻塞；通知及其他编辑的已读状态得到保护；真实授权／运行依赖保持；旧 unknown 不重放；跨领域采用同一并发合同。

新增机制限于工具目标标记、现有配置流程中的准入／提交边界，以及必要的类型化诊断与工具合同兼容。已有订阅版本、规则版本、采集应用状态和 Store 幂等证据直接复用。不得以“通用”为由新增独立配置中心、通用事务、持久状态机或批量版本迁移。

按中等规模改造安排，主要成本在飞书准备／提交复查、工具三入口适配和兼容验收。通知无需重做采集器，规则无需改变授权执行；这样既修复同类问题，也限制对 Room 核心逻辑的侵入。
